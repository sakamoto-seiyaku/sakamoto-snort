# POC-5 / POC-6 paired execution plan

这两个 POC 共用同一个 Pixel 6a、同一个 VPP/HEV 构建、同一套环境审计和
raw ledger。POC-5 先把成本拆开；POC-6 再把相同路径接到真实 VpnService
TUN，并比较单 worker 与每 worker 独立 owner。二者都是 test-only，不改变
生产接口或所有权语义。

## POC-5: packet-path cost attribution

每个 cell 记录：packet build、VPP ingress alloc/copy、HEV/lwIP pbuf alloc/copy、
lwIP/echo、HEV output、VPP egress alloc/copy、queue/wakeup、总耗时，以及吞吐、
延迟、CPU/RSS/thermal/affinity。`submit-ns` 不能再被当作单一 copy 成本。

arms：

1. `full`：现有真实 UDP/TCP echo 闭环；
2. `prebuilt`：复用已构造 wire packet，只测边界和协议栈；
3. `builder`：只构造 packet，不进入 HEV；
4. `memcpy`：只做同尺寸 buffer copy，给设备上的 memcpy 下界；
5. `full` 的真实 HEV metrics：单独报告 pbuf alloc/copy 与 TCP write-copy。

payload 为 33/512/1400，burst 为 1/32；低负载 10k、高负载 1M；每格 warmup
10s，正式 3 次取 median/p95。UDP/TCP 均须闭环、计数和错误为零。

## POC-6: real VPN/TUN and multi-worker path

真实 `VpnService.establish()` TUN fd 进入 VPP plugin，VPP worker 上的独立
FlowStack/HEV/lwIP owner 做 UDP/TCP local echo，再从同一个 TUN fd 回给 app。
先跑单 worker baseline，再跑 2 worker（可选 4 worker）；每个 worker 只访问
自己的 owner，TUN 读入按 canonical flow hash 投递。

payload 为 33/512/1400，flow 为 1/8/32，burst 为 1/32，UDP/TCP 各跑低/高
负载。记录 TUN ingress/egress、丢包/乱序、TCP 建连/关闭、每 worker queue/
wakeup、POC-5 的 copy/alloc 计时、吞吐/延迟、CPU/RSS/thermal/affinity、
残留和 teardown。单 worker 与多 worker 必须使用同一 build/hash 和同一流量
生成器。

## 判定

- POC-5：给出各段时间占比和设备上的 memcpy 下界；不以经验判断瓶颈。
- POC-6：给出 TUN 闭环正确性、worker 归属和扩展曲线；若多 worker 有误，
  只记录失败证据，不提前改 lwIP 或冻结架构。
- 两个 POC 的 raw 记录和 memo 分开：journal 只写原始事实，memo 只写可回顾
  的结论、风险和下一步。
