# S327 — DTLS real SNI filtering

Task authority is SAKAMOTO-327 under the [application DNS specification](../product/APPLICATION_DNS_SPEC.md)
section 11 and the [unified rule engine specification](../product/UNIFIED_RULE_ENGINE_SPEC.md), which selects
DTLS for SNI processing with its own real handshake facts. Host and Pixel 6a Root/VPN N1 evidence are kept apart.

## Implemented contract

- [`product_flow_dtls.c`](../../src/product/vpp/product_flow_dtls.c): DTLS 1.0/1.2 ClientHello from the flow's
  origin direction. Handshake fragments of the first ClientHello are reassembled by fragment offset into the
  Flow's existing UDP reserved storage; identical retransmitted fragments are absorbed, conflicting ones are
  malformed. The complete body is rewritten into TLS ClientHello form (DTLS version mapped, cookie removed) and
  parsed by the shared TLS parser, so extensions and host_name rules are the same as TLS. A cookie retry
  (later message_seq) is not assembled; it carries the same SNI.
- Terminal results: name, confirmed absence (no server_name extension), malformed (record/fragment bounds,
  conflicting bytes), unsupported (not a ClientHello, a non-handshake or epoch>0 record before completion), byte
  budget (message above the 4092-byte storage, 8 records or 16 fragments per datagram), packet budget (20
  datagrams) and the existing 5 s recognition timeout. Server flights never feed the client hello.
- The first origin UDP datagram picks the producer: a plaintext DTLS handshake record selects DTLS, anything
  else stays with QUIC. The choice is kept in the SNI state and survives the stop that clears the storage.
- A completed DTLS result publishes the DTLS catalog fact (1020), never QUIC. SNI rule applicability now includes
  DTLS. The existing heuristic `sakamoto:dtls` label alone is not a name: domain conditions stay unknown and never
  match on it.
- Nothing is held: every datagram, including a first fragment without a complete name, is forwarded under the
  current verdict. Once the name is known the flow's later datagrams are evaluated with it. The association
  qualification hook is not consulted; nameless results stay unavailable and no association enforcement is
  enabled.

([`capture_dtls_hello.py`](../../tests/host/fixtures/capture_dtls_hello.py)): DTLS 1.2 named, allowed and
nameless, DTLS 1.2 fragmented at MTU 256, DTLS 1.0 named, each with OpenSSL's own timeout retransmission.

## Pixel 6a qualification

Native stage `android-native-r1` and APK `android-apk-r1` (SHA-256 `385b08f1…`) from the committed sources;
unchanged repeats compiled nothing. Ordinary App entry; the App sends the captured datagrams to an independent
UDP echo peer on the host; the Product's own `flow.sni`/`flow.lpi` status of the very flow; normal stop.

| Run | Scope | Result |
| --- | --- | --- |
| `device-root-n1-r2` | Root N1, 12 cases | PASS |
| `device-vpn-n1-r2` | VPN N1, the same 12 cases | PASS |

Cases: allowed name over IPv4 and IPv6 (hello, retransmission and an application datagram all echoed, DTLS fact
and no QUIC fact); refused name over IPv4 and IPv6; fragmented refused hello (the first fragment without a name is
forwarded, the completing fragment and later datagrams are not); no SNI (allowed, absence recorded); DTLS 1.0
refused name; a DTLS record envelope without a ClientHello is not a name; QUIC regression (RFC 9001 Initial,
`example.com` refused, QUIC fact); TLS regression over TCP with real OpenSSL TLS 1.3 ClientHellos (allowed and
refused); allow-all after the rule is removed.

On Root the refused named hello itself never reaches the peer. On VPN the App UID of a new UDP flow is learned
asynchronously (as for S325/S326), so the first hello of a new flow is forwarded before the App-bound rule can
apply (`first_hello_delivered=true` in both IPv4 and IPv6 runs); the retransmission and every later datagram are
refused. This is recorded, not hidden: on VPN a single-datagram ClientHello to a refused name reaches the server
once.

After the runs the original APK and all 4861 private-data members were restored at the fresh maximum generation
(`original-restoration-r1`), with no NFQUEUE entry, Product hook or owned route left.

## Not covered

Root/VPN N3, handover, DTLS 1.3 (RFC 9147 unified headers carry the same plaintext ClientHello, but no client was
exercised), a server-driven HelloVerifyRequest exchange, cookie-retry-only names, real WebRTC/VPN DTLS clients
and the association fallback for nameless results.
