# VPP-owned packet parsing behind capture adapters

Root/NFQUEUE and VPN/TUN Packet capture Adapters are platform ingress and completion channels, not packet parsers or policy modules. For the Android Functional Closure, each Adapter transfers the complete received L3 packet unchanged into the shared VPP graph with platform-owned hints and an Adapter-owned completion obligation; the shared VPP dataplane parses the packet once, constructs PacketFacts, performs fragment and flow steering, evaluates policy, and returns the disposition that the Adapter must complete. This seam prevents two capture profiles from acquiring different parser or policy semantics and replaces the current C++ POC shape in which `PacketCaptureAdapter` performs IP/L4 parsing before graph injection.

The transfer also follows User-Space Single Materialization: after the kernel-to-user boundary, packet bytes are received directly into VPP-owned buffer data and processed in place. TUN reads into a preallocated VPP buffer or chain; NFQUEUE receives its netlink datagram into VPP-owned ingress storage and projects the contained L3 span. The current POCs' scratch-buffer-to-VPP copies are not the production contract. This does not promise absolute kernel or transport zero-copy, but it forbids an Adapter-to-VPP full-packet copy unless a later POC proves direct materialization infeasible and an explicit measured fallback decision is accepted.

Inside VPP, normal graph execution and worker distribution transfer buffer indexes/ownership and side metadata without copying, cloning, or reserializing complete packets. The inspected `stellar_lpi` baseline reads current L4 payload in place and retains small derived session state, so protocol identification by itself is not a packet-copy exception. Protocol-required fragment/TCP reassembly and any future recognizer that demonstrably requires selected payload retention are named bounded exceptions, not general permission for modules to retain packet content.

Packet bytes are also read-only for normal parser, policy, session, recognition, distribution, and observation nodes. Root completion never supplies an NFQUEUE replacement payload, and VPN policy hands unchanged L3 bytes to HEV. Only named nodes whose semantics explicitly alter traffic, such as reassembly, a future enabled NAT, or packet synthesis, have mutation authority and own checksum, length, capacity, and evidence correctness.

The first release also retains the modified `flow_dissector`'s contiguous-buffer envelope rather than preemptively building chain-aware parsing. The inspected fork sets `VLIB_BUFFER_DEFAULT_DATA_SIZE` to 9000 bytes; Android Functional Closure initially inherits that data size and the fork's default pool sizing, then records RSS, peak occupancy, and exhaustion evidence before any tuning. It verifies that target Root/VPN paths and the VPN Profile's fixed 1500-byte Android TUN and HEV-facing MTU stay inside the parser envelope. The IPv6 minimum MTU of 1280 is reserved only as a future evidence-triggered compatibility fallback; the dual-stack profile does not use 1250 or 1200. This release does not choose Linux `NFQA_CFG_F_GSO` policy or alter host offload settings. Generic length validation prevents partial interpretation; an unexpected oversize packet produces no Policy Verdict, completes Root `ACCEPT`, and records bounded `UNSUPPORTED_CONTIGUOUS_ENVELOPE` evidence. Linux GSO/jumbo support, chain-aware parsing, buffer sizing, or an operator workaround requires later deployment evidence and a new decision.

## Considered Options

- Parse and normalize PacketFacts inside each Packet capture Adapter. This was rejected because Root and VPN would duplicate packet semantics and could diverge before reaching VPP.
- Transfer the received packet into VPP and parse once in the shared graph. This is accepted because the capture mechanism varies while packet semantics do not.

## Consequences

- Adapter faults cover receiving, buffering, handoff into VPP, and platform completion; they do not classify packet contents or create Policy Verdicts.
- Mandatory completion identity is an ingress precondition. An NFQUEUE event missing its queue instance/generation or packet ID creates no PacketLease and never enters VPP; it records bounded `INGRESS_IDENTITY_MISSING` fault evidence without inventing an Adapter Completion result or claiming kernel `ACCEPT`.
- Packet-content validation follows the modified VPP fork: an invalid L3 envelope is runtime-dropped before policy with no Policy Verdict. This is distinct from a parser-execution infrastructure fault and from a valid L3 packet whose deeper L4 facts are unavailable or unsupported.
- For valid L3 with unavailable or unsupported deeper facts, PacketFacts preserves the parser status and available facts; predicates requiring missing facts do not match, while the remaining evaluable stages continue.
- Adapter-specific queue IDs, file descriptors, packet IDs, and transport handles remain outside PacketFacts and policy Interfaces.
- Adapter Completion remains one terminal operation and one physical operation attempt in the first release. For NFQUEUE, `nfq_set_verdict(..., NF_ACCEPT/NF_DROP, ...)` is the NFQ-defined terminal operation: a nonnegative function return is `SUCCEEDED` for successful completion of that operation, while a negative/native error or deterministic rejection before the native call is `FAILED_DEFINITE`. `OUTCOME_UNKNOWN` is reserved for a genuinely ambiguous path in which no trustworthy operation result was obtained; an observed nonnegative return is not subsequently downgraded to UNKNOWN. NFQUEUE has no separate ACK, and `SUCCEEDED` does not prove later host/network delivery or downstream traffic success. There is no automatic retry: failure or uncertainty updates bounded low-cardinality counters and diagnostics and exposes a Runtime-health reason, without re-entering VPP or re-evaluating policy. Health latching/automatic-recovery timing and detailed Product UI presentation are deferred beyond Functional Closure.
- On VPN outbound, HEV accepting packet ownership completes the Adapter obligation; later connection, socket, or network-send failure is a Transport Outcome and cannot rewrite completion. On the return path, the terminal TUN write is Adapter Completion. Root completion records the result of the NFQ terminal operation according to the return value above; it does not claim a separate receiver ACK or subsequent host/network delivery.
- Adapter teardown first quiesces ingress, performs a fixed short drain while completion and transport channels remain available, and only then removes those channels. Existing Policy Verdicts complete normally; at the deadline ordinary unevaluated Root leases accept when still completable, while ordinary VPN leases record completion or transport failure and release. Previously classified fragment or repeated-owner runtime drops remain drops, and no packet is replayed into a replacement Adapter generation.
- Android RuntimeService/VpnService maintains an event-driven Network Context Snapshot and attaches it at ingress; VPP does not synchronously query Android for each packet, and VPN Runtime Profile does not force the packet's network context to VPN.
- NFQUEUE bounded-prefix copy is deferred until measurement justifies it and a later contract preserves fragment, IPv6 extension, and recognition correctness; the first closure does not assume that 512 bytes is universally sufficient.
- Functional Closure evidence must demonstrate direct TUN read/readv into VPP buffer chains and NFQUEUE receive into VPP-owned storage, with no Adapter-to-VPP full-packet memcpy on the normal path.
- Distribution and handoff evidence must demonstrate index/ownership transfer without packet-byte copies. Every fragment or recognition content-movement exception requires its own capacity/lifetime budget, counters, and stress evidence.
- Graph review and tests must enumerate every byte-mutation-authorized node; all other nodes are read-only, including a prohibition on temporary mutate-and-restore parsing.
- Existing C++ Flow/Adapter classes are evidence and tests, not a structure to translate mechanically into the production VPP/Rust implementation.
