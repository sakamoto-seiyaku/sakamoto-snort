## 2. 已确认结论总览

| 议题 | 本轮结论 |
| --- | --- |
| 名称 | 对本项目使用“L4 规则”，不再把用户配置称作 ACL；外部源码中的原名除外 |
| 执行分工 | 保留进入 Flow 之前的静态 L4 执行能力，以及之后的通用规则引擎 |
| CT 与 LPI | 是不同事实来源，不拆成两个独立、固定先后的策略裁决阶段 |
| 优先级 | 由用户规则定义，不由事实来自 CT 还是 LPI 决定 |
| 完整排序 | 沿用 `priority 升序 → order 升序 → ruleId 升序`，编译成内部 Rank；不追加隐含精度权重 |
| 规则版本标识 | 用户接受的初版工程起点：一个 64 位 ID，高 48 位固定随机规则部分、低 16 位递增修订号；消息直接使用 8 字节值，见第 27.6 节 |
| 有效规则集 | 每个应用展开全部适用规则；组 / 集合只组织、复用与溯源，不各自先选赢家 |
| 引用去重 | 同源规则、同有效模式的多路径引用去重；同源模式冲突拒绝；不同规则 ID 不按内容静默合并 |
| 联网禁用 | 配置入口维护最高优先级的普通 DROP；不增加独立 Gate 分支或后端保护特权 |
| 缺省动作 | 空规则集或完整匹配无赢家时 ALLOW；默认拒绝用最低优先级兜底 DROP 表达 |
| 表达式 | 支持 AND、OR、NOT；表达式及编译、执行资源必须有界 |
| 编译 | 小组合直接展开，大组合因子化，必要时剩余校验；不做无界全量 DNF |
| 索引 | 同一匹配器内，同 mask 跨 priority 共用子表；按完整 Rank 选择赢家和剪枝 |
| 编译成本 | 看整个应用有效视图的 mask 复用、候选 / 合取工作量和内存，不只数单条规则片段 |
| 初始展开预算 | 暂取每条逻辑规则 32 个完整条目；是保护性工程默认，不是理论性能最优值 |
| 实现独立性 | L4 与通用规则的编译 / 匹配 Module 可以独立实现 |
| 发布 | 一次 Apply 发布完整、一致的组合快照；编译或发布失败不产生半更新 |
| 查询临时状态 | 预分配的 worker-local 单次查询状态；半命中不跨包累积、不直接成为赢家 |
| 快速路径 | worker 私有固定容量结果缓存；保存完整 Match / NoMatch，命中仍走统一归因与计数路径 |
| 缓存依赖 | 编译整个适用程序的保守依赖摘要，不只看上次赢家；包含相关值、可用性与视图身份 |
| 策略变更 | 新快照身份使旧决策惰性失效；保留 Flow / CT / LPI 事实，不追求精确最小失效集合 |
| 协议输入 | 尚无可用结果与明确的 Unknown 结果不同；后者可正常参与比较 |
| SNI 规则适用性与输入 | 含 SNI 条件的整条规则仅在流已识别为 TLS / QUIC 后参与匹配，布尔组合不能绕过此前提；SNI 尚无确定结果时不可用，正常解析确认无 SNI 后域名命中为 false、其 NOT 为 true，见第 26 节 |
| 确认无 SNI 条件 | 可直接用于规则，例如“确认无 SNI → DROP”；沿用 TLS / QUIC 前提，仅有效解析确认缺失时成立，见第 26 节 |
| 持续识别 | 已产生的可用结果立即参与匹配，不必等待整个 LPI 过程结束 |
| LPI / SNI 过程 | 按参考 fork 的明确正常过程及既定不扣包 / 单缓存等差异作为初版起点，遇到实际问题再调整，见第 22 节 |
| 解析预算耗尽 | 结束受限尝试，释放不再需要的解析数据，保留 Flow / CT 和已有事实；未取得的信息保持不可用并记录原因，按当前事实继续执行规则，见第 25 节 |
| NOT | 对当前已发布、可用的结果求值，不额外要求 LPI 全过程结束 |
| 动作 | 当前共享策略能力是包级 ALLOW / DROP，不引入“终止连接”能力 |
| 自动编排 | 先标必须后置，再按完整 Rank 传播可能重叠的后置约束；无法证明安全就后置 |
| 分配粒度 | 一条逻辑规则只在一个位置；其展开片段、合取条件与完成节点不跨 Flow 两侧拆分 |
| 前置结果 | 无匹配则继续；实际 DROP 立即终结且不进入 Flow；已定案 ALLOW 不被同组低排名后置规则推翻 |
| 核心不变量 | 相同规则版本、相同匹配输入及可用性，前后置编译计划不能改变平坦规则集的获胜规则和动作 |
| 验证顺序 | 测试内顺序参考求值器对照赢家 / 动作 / 归因，再验证状态变化与生命周期，最后做 Android Root / VPN 接入及性能比较，见第 24 节 |
| 方向与端点 | src / dst 永远表示当前包端点；in / out 相对设备；ORIG / REPLY 相对 Flow 首次观察方向，不隐式交换端点 |
| 重叠证明 | 使用简单保守静态包络；可证明任一对应字段不相交才判不重叠，不做完整 SAT / DNF |
| 事实轨迹边界 | 不新增“全部 CT 历史等价”或应用级观察范围作为隐藏前移门槛；遵守明确成立的生产者约束 |
| 本版域名输入 | 本版包含 TLS / QUIC SNI 提取及 VPP 域名谓词；暂不解析隧道内流量 |
| 后续 DNS | 独立 DNS 请求过滤、DNS-IP 关联采集后移；未来关联输入采用显式默认关闭开关 |
| 规则共享边界 | 可共享名称、名单与匹配能力；不能删掉应用、方向、端口等条件，将包规则扩大为 DNS 拒绝 |
| TCP 解析缓存 | 流还原拥有一份有界字节缓存，TLS / SNI 引用；不为等待 SNI 扣原包，不另限 32 个解析名额 |
| 域名匹配 | 初版支持精确名称与自身及子域，复杂 glob / regex 后置；规范化与导入按第 23 节，最终库选型留实验 |
| 库选型 | 暂留 libdatrie、维护中的 Valkey rax，与 VPP hash 基线比较；Knot QP 备选，真机测试前不选赢家 |
| UI | 不要求用户为每条规则手动选择前置 / 后置；具体交互仍待讨论 |
| 可观测性 | 必须说明哪里丢、哪条规则导致、丢了多少、何时发生；宏观方向已收敛，具体合同见第 21 节及剩余议题 |
| 可观测性定位 | 面向个人设备，覆盖网络活动、控制效果、系统健康；常态概况、用户排障时详细记录，继续讨论后端架构分工 |
| 内存与存储 | VPP 状态、计数和当前流表在内存；配置资产与观测记录分库，Rust 应用侧承担记录消费和历史保存 / 查询 |
| 配置文件与规则管理 | 首版依赖 VPP 在线；VPP 提供规则管理 API、统一读写唯一配置文件，维护规则 / 组实体并编译，前端通过 API 访问。Rust 保留适配、基本校验和观测后台，见第 29.1 节 |
| 保存与应用 | 已确认先基本校验、完整保存，再编译发布；保存失败不编译，编译失败保留已保存的新配置、继续旧快照，并分别报告保存 / 生效结果。重启后编译仍失败则报告恢复失败；作为初版起点，后续按反馈调整，见第 29.3 节 |
| 启动编译与修复 | 编译成功并发布有效快照是启用产品流量接管的前置条件；启动编译失败保留正常的 VPP 管理 API，由用户修复后重新保存 / 应用，不报告保护正在运行。运行中更新失败继续旧快照，见第 31.3 节 |
| 保留 | 观测对象按生命周期、统计贡献按数据年龄管理；初版默认 1 分钟数据留 48 小时、1 小时汇总留 30 天、1 天汇总留 180 天，END 后细节留 24 小时，常态观测存储预算 256 MiB；均可后续调整，见第 21.23 节 |
| 常态历史规则解释 | 近期保留当时规则名称、完整版本 ID、实际动作和计量；长期汇总保留必要辨识信息。完整旧条件复用仍保留的配置历史，缺失时明确说明，不额外保存整套旧规则 / 名单副本，见第 27.8 节 |
| 常态窗口 | Rust 后台根据观测记录增量维护总体流量、应用流量、应用协议分布、规则效果四类预定义视图，UI 等直接查询；不做任意维度交叉，见第 21.16 节 |
| 历史上报 | 创建 / 结束、必要归因变化及增长阈值触发累计快照，并允许低频时间驱动导出待上报变化；不逐包写消息，发总量而非增量，见第 21.20 节 |
| 发送与消息语义 | VPP 非阻塞发送，不等待 Rust 消费或持久化确认；一次消息可同时携带累计增长及 END 等状态变化，Rust 统一处理计量与状态，见第 21.21 节 |
| 记录通道候选 | 普通 / debug 独立有界通道；VPP `svm_msg_q`、Aeron C SPSC ring 均保留，手动实现 ring + eventfd 为最后方案，最终经移动端实验选型，见第 21.29 节 |
| debug 目标与优先级 | 在采集范围内追踪包的完整实际动作链；开启后正确性、证据充分性与故障定位优先于性能，不为沿用常态低开销目标省略排障所需细节，见第 21.31 节 |
| debug 数据生命周期 | 只服务一次调试会话，轨迹与解释资料临时管理；不进入常态长期观测历史，不建立跨会话 debug 档案，见第 21.35 节 |
| 首版常态范围 | 已确认运行 / 策略状态、RX/TX、当前流表、规则计数、丢包 / 异常、资源用量及观测通道状态；复用 VPP CLI / API，不足后续添加。debug 具体模式与交互后置，见第 21.36—21.37 节 |
| 消费复杂度 | 遵守 KISS；Rust 以单一消费流程维护最小实例 / 更新状态，防止重复计量及旧状态覆盖，缺口明确后继续；不引入确认补发、复杂乱序重排或完整历史重放体系，见第 21.24 节 |
| 归因与身份 | 正常 Flow 分方向维护归因；规则变化不重建 Flow 或重置其累计量，规则 ID 不属于观测身份 |
| 前置阻止历史 | 采用五元组等身份的轻量阻止观测，保留累计量与归因；不创建 CT FlowEntry、不做 LPI / 流还原，按空闲超时结束 |
| 两类观测共存 | 正常 Flow 与阻止观测独立身份、互不转换；时间范围可重叠但包不重复计量，共用累计快照与归因语义 |
| 计量与历史完整性 | VPP 基础计量独立于记录成功导出和条目建立；Rust 窗口与历史接受记录级更新延迟并明确表达缺口，消费 / 存储不阻塞包处理 |
| 分类变化 | 当前对象描述与历史统计归属分开；按处理当时可用事实计量、后续变化不默认回填；L7 多个已发布结果全部计入，协议项之间允许重叠，见第 21.26 节 |
| 计量口径 | 共享策略路径的 IP 包 / 字节；实际策略允许、实际策略阻止与运行故障分开；规则命中按最终逻辑赢家计数，缓存和编译片段不改变计量，见第 21.25 节 |
| L7 占比 | 同一贡献在每个不同的已发布协议项中各计一次，应用总量仍只计一次；同范围应用流量作为占比分母，协议占比合计允许超过 100%，不归一化为互斥分布 |
| 统一更新职责 | 归因切换、累计边界、本包计量和导出触发的顺序封装在小而完整的 Interface 后；两类观测保留独立生命周期 |
| Rust 保留与查询 | 同一次消费推进观测概况、必要归因信息和按时间组织的统计贡献；窗口读取已维护汇总，合并消息不等于只保留 Flow 最终总量，见第 21.22 节 |
| 时间归属与压缩默认 | 有依据的归因增量按该增量最后活动时间落入分钟桶，跨桶采用近似；同分类分钟 → 小时 → 日求和，查询不重复叠加不同层；第 21.23 节是用户授权选择的工程起点，不是精确逐包时间重建 |

这里的“两个执行部分”不再意味着：自动放进前置的规则可以额外获得用户未定义的优先级。这个演进是本轮后半段的重要修正，详见第 5 节。

## 3. 输入模型、规则能力与优先级

### 3.1 事实来源不是规则优先级

本轮从三个层次的输入开始讨论：

1. 当前包及已有平台上下文可提供的静态输入，例如 IP、端口、传输协议，以及适用的应用 / 网络信息。
2. Conntrack / FlowRuntime 产生的事实，例如 TCP 当前状态。
3. LPI 产生的应用协议识别事实。

“静态”指不依赖后续 CT / LPI 识别过程，不是说规则配置永远不变，也不是说所有字段在整个 flow 内不变。平台应用 / 网络输入也不应被误称为解析器独自生成的 PacketFacts。

CT 与 LPI 不构成两个各自拥有固定优先地位的规则阶段。通用规则可以使用其中一种事实，也可以组合多种事实及已有静态输入。它们可以共享同一个 owner-local FlowEntry；“来源独立”不要求并行线程，也不要求先完成完整 CT 才能开始协议识别。

例如，在适用输入均已具备时：

- 较低优先级的 CT ESTABLISHED → ALLOW；
- 较高优先级的某应用协议 → DROP；

应该由较高优先级的匹配规则获胜，而不是由事实生成顺序或先访问哪个 Module 决定。

### 3.2 一套逻辑匹配语义

同一个有效规则集按其定义的优先级选择当前获胜者。不能把新出现的每个协议结果分别判一次，再采用“任何历史 DROP 都获胜”之类的另一套算法。

后续讨论已以最终核对的完整排序为起点，继续参考 OVS：

    priority 升序 → explicit order 升序 → stable rule ID 升序

在每个应用的有效规则视图内，编译成紧凑的内部 Rank，数值越小越优先。Rank 只编码原排序，不新增用户优先级层次。前后两个程序保留同一逻辑排名，不能在各自局部重新排序后改变比较含义。

中途探索过“同 priority 时更精确优先”、最长前缀、固定字段比较顺序和精度分数。后续并未把这些作为新的隐藏比较键，而是回到上述完整顺序继续设计。mask 的精细程度、哈希遍历顺序和命中的 OR 分支都不额外决定胜负。精度可用于解释或配置辅助，不代表已批准具体 UI 功能。

`order` 是显式策略顺序；它如何映射到具体界面操作本轮暂不展开。不能把界面临时显示行号、组引用遍历顺序或编译后的物理位置直接当作它。

即使两个匹配方案都返回 ALLOW，若获胜规则不同，也不能直接视为等价：解释、规则计数及缓存归因可能不同。

### 3.3 AND / OR / NOT 与有界执行

已确认支持完整的 AND、OR、NOT，不局限于固定的 AppID 模板。

- AND 要求相应分支都成立。
- OR 只要有足够的已知分支使表达式成立即可，不要求每个分支的全部字段都已经可用。
- 没有可用输入，不能把该条件当成 false，再利用 NOT 把它变成命中。
- 这不意味着“含有任何不可用字段的整条规则一律不参与”；OR 的其他已成立分支仍然有效。

规则本身明确的协议适用前提先于上述表达式求值。用户在第 26 节补充：含 SNI 条件的整条规则仅适用于已识别为 TLS / QUIC 的流，AND / OR / NOT 均不能绕过此前提；协议前提成立后，再按上述可用性与布尔语义处理各条件。不能将普通 DNS 等非 TLS / QUIC 流量当成“确认无 SNI”，再由否定域名条件使规则命中。

例如，CT ESTABLISHED 已成立，而 LPI 暂无结果时：

    CT = ESTABLISHED OR LPI 包含某协议

可以成立。相同两个条件改成 AND，则不能仅凭 CT 分支得出成立。

已确认表达式和资源需要上限。深度、节点数、规则 / 集合大小、编译产物内存和最坏执行工作量的产品总上限仍未确定；第 4.6 节的 32 仅是直接展开的初始预算，不替代这些上限。仅限制深度不足以约束所有成本。

规则编译不是穷举所有输入组合，也不能把任意 AND / OR 全量分配成笛卡尔积。后续已接受适度编译换取匹配性能：简单范围优先编译，小组合可有界展开，大组合保留因子结构。它不撤回 AND / OR / NOT 能力，也不授权任意用户脚本、JIT 或一个通用运行时代码平台。

### 3.4 每个应用的平坦有效规则集

已确认编译前展开全部适用关系：

    应用绑定的规则 / 组 / 集合
        → 展开引用、同源同模式去重
        → 平坦有效规则集与完整 Rank
        → 自动分配整条规则，再生成两个程序

- 组和集合负责组织、复用、溯源；运行时不先在每个组内选赢家，再让组间另做一轮竞争。
- 同一源规则经多条路径适用于同一应用、且有效模式相同，只形成一个逻辑执行项。
- 同一源规则对同一应用同时形成 enforce / observe 模式冲突，拒绝配置，不以隐含模式优先级解决。
- 不同规则 ID 即使条件相同，也保留为不同逻辑规则；重复匹配可警告，不静默合并并丢失顺序与归因。
- 直接绑定的规则不天然压过组引用规则；绑定 / 组的遍历顺序不增加优先权。
- 不同应用分别形成自己的有效视图；共享源规则不等于共享可变 Flow 状态或同一个包级 verdict。

拍平的是组织关系，不是把单条表达式穷举为全量 DNF。因此不再把“混合组”视为一个必须整体后置的编译单位。

### 3.5 联网禁用也是普通规则

已确认：应用联网禁用由界面 / 专用配置入口维护一条最高优先级的普通 DROP 规则，进入同一有效规则集和同一套排序、编译、缓存、归因流程。

普通配置入口不能随意修改它、正常用户配置下其他规则不能绕过它，是配置入口维护最高有效顺序的约束；后端引擎不增加独立 Gate、受保护规则类型或特殊不可覆盖分支。不能把这个入口约束重新解释为独立于规则语义的后端特权，也不新增所谓 FE 领域概念。

这更新了先前把应用联网禁用保留为规则集外硬 Gate 的建议。现行正式文档 / 实现尚未同步这一新方向，见第 13 节。运行时故障、Adapter 完成和传输约束不因此被改造成普通策略规则。

### 3.6 缺省动作

空有效规则集，或完成当前有效规则集查询后没有匹配赢家，默认 ALLOW。

需要白名单 / 默认拒绝时，由一条最低优先级的显式兜底 DROP 表达。不增加每组独立 default policy，也不让前置 NoMatch 直接触发默认 ALLOW 而跳过后置查询。

无匹配是正常匹配结果，不能用来掩盖查询未完成、运行时故障或资源旁路；这些路径保持已有的独立契约。

## 4. 编译、Module 分工与组合快照

### 4.1 独立实现不等于独立产品语义

已经同意 L4 与通用规则的编译 / 匹配 Module 独立实现。它们不必强行共用同一种 AST、索引布局、缓存结构或匹配算法。

同时，用户看到的是一份可解释的策略配置；编译规划、发布和缓存有效性不能分别维护互不一致的规则语义。

自动编排引入了整个有效规则集的分析需求，因此只把两个旧引擎的 ALLOW / DROP 串接起来并不足够。公共规划负责有效规则、完整 Rank、逻辑来源、依赖与安全位置；专用编译器负责本位置内部的编译布局和查询。具体函数、结构体与 ABI 尚未冻结。

概念关系如下；它不是已冻结的函数或 ABI：

    用户规则、规则组及适用关系
        → 有效规则集、逻辑优先级、输入依赖与安全执行规划
            → 独立 L4 编译 / 匹配实现
            → 独立通用规则编译 / 匹配实现
        → 一份一致的组合 Runtime Snapshot

FlowEntry 的可变事实、计数和 owner-local 匹配状态不属于共享不可变规则程序。

### 4.2 Apply 的整体性

快照是一个逻辑上完整的配置版本，不意味着一个巨大内存块或一个超级编译器。

以 L4 程序 A 和通用程序 B 为例：

| 当前 | 本次目标 | 结果 |
| --- | --- | --- |
| A1 + B1 | A2 + B1，且 B1 与新规划仍兼容 | 可以作为一份完整新版本发布 |
| A1 + B1 | A2 + B2，二者都成功 | 一次发布完整新组合 |
| A1 + B1 | A2 + B2，但 B2 失败 | 保留 A1 + B1，不发布半份更新 |

“源规则只改了一侧”不保证另一侧永远无需重编译。自动编排可能让一条规则的修改影响两个程序；是否复用旧产物要服从新计划的正确性，不另做复杂增量编译承诺。

一次包处理使用一致的已绑定快照。旧快照的在途读者可以完成；新快照下的包不能混用未经验证的旧判定。这里不重新选型发布框架，而是衔接已有 S209 约定，见下节。

### 4.3 衔接既有快照发布边界

本节是对已有实现约定的核对，以及新编译计划应遵守的边界；不是新通用编译器已经接入并验收的声明。

- 同一新版本绑定有效应用视图、完整 Rank、前后置计划、两个兼容程序、缓存依赖摘要和逻辑规则归属。
- 必要部分全部编译、校验并满足资源约束后才发布；失败保留旧版，报告原因，不静默截断规则或发布半个组合。
- 一个包从绑定快照到完成本次 owner-local 策略处理都使用同一身份；前置、必要的 Flow 事实处理、后置、缓存检查和赢家归属不能各取一版。
- “更新成功”表示新版成为后续新快照获取的版本，不表示所有旧版在途包已经处理完毕。旧包不在中途重启求值。

例如以下顺序合法：

    包 A 绑定 V1 → 发布 V2 → 包 B 绑定 V2 → 包 A 按 V1 完成

现有 S209 使用带读者保护的双缓冲快照：发布方等待待复用缓冲的旧读者退出，再写入并发布；读者仍在使用的内容不能覆盖。沿用这一有界生命周期，不另外增加 RCU / QSBR、无界退休快照链表或发布时的全 worker 停顿协议。[既有 S209 边界](../testing/SAKAMOTO_209_POLICY_SNAPSHOT.md)

控制面写锁不进入逐包 Flow 可变状态更新；现有快照读者计数等原子同步仍存在，不能把 owner-local 误写成“整个包路径完全没有原子操作”。发布不遍历或修改 worker 的 FlowEntry、池 epoch、CT / LPI 事实和累计计数。后续包由所属 worker 校验快照身份，惰性失效旧策略判定。

### 4.4 同 mask 子表与完整 Rank

已接受以 OVS `lib/classifier` 的匹配组织方式为主要参考，而不是把无优先级的 datapath 缓存表直接当作策略规则引擎。

在每一个匹配器内部：

1. 同一 mask 的匹配项共享哈希子表，不按用户 priority 强制分成互不共享的表。
2. mask 相同表示匹配形状相同，不要求匹配值相同。例如同为 TCP、目标 `/24`、精确目标端口，可具有不同地址、端口值和 priority。
3. 索引命中候选后仍须满足完整条件；高排名候选校验失败，要继续检查其他可能赢家，不能把整个桶直接判为空。
4. 子表用 `bestPossibleRank` 等完整排名上界支持剪枝；同 priority 但 order 更靠前的规则仍可能胜出，不能只比较 priority。
5. 内部条目最终映射回逻辑规则，不能让 mask 片段变成独立用户规则或独立归因对象。

术语明确区分：**候选索引 → 完整校验 → 选择赢家**是同一个匹配器内部的步骤；**进入 Flow 之前的 L4 / 之后的通用引擎**才是实际前置 / 后置执行位置。前者不新增产品执行阶段，也不允许一条规则跨 Flow 两侧续算。

### 4.5 适度编译：小展开，大组合因子化

用户否定了把普通范围普遍留作逐候选剩余扫描的过度保守方向，接受以下中间方案：

- 适合编译的范围先做精确、有界表示。例如 16 位端口 `1024..2047` 可直接表示为 `value=0x0400, mask=0xfc00`，不必为每个端口建立条目，也不必默认保留运行时范围比较。
- 多个 OR 维度的组合较小时，直接生成完整 masked matches。
- 笛卡尔积较大时，保留“每个维度内部 OR，维度之间 AND”的因子结构，通过条件汇总确定完整规则是否成立。
- 真正不适合上述表示的条件，保留有界剩余校验 / 表达式计划；不是所有范围都退回残余扫描，也不是所有布尔表达式都强行套成 conjunction。

例：源端口和目标端口均为 `1000..1999`，各可分成 7 个对齐 mask 片段。直接组合是 `7 × 7 = 49` 个完整匹配；OVS 式因子表示可用 14 个条件项加 1 个完成项表达同一例子。这是表示规模对比，不是查找次数、吞吐倍率或设备基准结果。[OVS 范围与合取说明](https://www.openvswitch.org/support/dist-docs/ovs-fields.7.html)

反过来，两个维度各只有 2 项时，直接组合是 4 项，因子表示可能需要 5 项并增加汇总工作。因此不规定“因子化永远更快”。

因子项只证明条件，不独立执行动作、不成为赢家，也不独立计逻辑规则命中。整条规则的 Rank、动作、模式、归因与实际执行位置保持唯一。OVS conjunction 是局部表示参考，不等于已提供任意 AND / OR / NOT 的完整编译器；本项目也不继承 OVS 同优先级歧义来放弃确定性排序。

### 4.6 编译成本与初始展开预算

已确认方案选择看整个应用的有效编译视图，而不只看一条规则展开了几个片段。采用有界、简单的成本估计，考虑：

- 新增多少 mask 形状，能否复用已有子表。
- 可能产生的候选扇出和完整校验工作。
- 合取条件汇总所需工作。
- 编译产物与查询临时状态的内存。

不引入全局最优搜索、学习型优化器或无界方案枚举。保留完整 Rank 与规则语义，布局只是实现选择。

初始工程默认：**每条逻辑规则最多直接展开 32 个完整匹配条目**。

- 依据：16 位端口的单个连续区间最多需要 30 个对齐前缀片段；32 是覆盖该边界的取整保护预算，不是硬件无关的理论性能最优点。
- 这是直接展开预算，不是用户规则数、子表数、全程序内存或所有布尔表达式的总上限。
- 预算内仍可因整体索引成本选择因子化；成本相近时先偏向直接匹配，减少合取汇总。
- 先做有界组合规模计算，超过预算立即停止继续枚举并选择合法的因子 / 剩余计划；不能先生成巨大笛卡尔积再放弃，也不能截断条件。
- 若所有合法计划仍超过产品总资源上限，应明确拒绝该配置并保留旧版，而不是改写规则语义。

性能测量按用户要求暂缓，实践中不足再调整默认。这里没有吞吐、功耗、延迟或最坏探测次数已经验收的声明。

### 4.7 半命中、完整匹配与提前停止

内部可区分完整匹配和条件命中：

- 完整匹配可以参与 `bestRank` 比较。
- 条件命中只更新该逻辑规则本次查询的条件状态；合取完整且剩余条件通过后才可参与赢家比较。
- 同一个 OR 维度可有多个备选项同时命中，只能算该维度成立一次。因此使用幂等的条件位 / 等价状态，不把原始命中次数累加成“已满足维度数”。

提前结束必须同时覆盖尚未查询的子表，以及已经收集但尚未完成校验的候选 / 合取工作。只有两者都不能产生更好的完整匹配，才可返回。例如已有 Rank 20 完整匹配，但 Rank 5 仍待验证，不能只看剩余普通子表较低就宣告 20 获胜。

这里的“待验证”只属于当前输入的同一次查询，不是等待未来包、未来 LPI 结果或额外放行探测流量。正向条件位也不是任意 NOT / 输入不可用语义的替代品；完整表达式仍遵守第 3、6 节。

### 4.8 worker-local 查询临时状态

在已确认的 worker-per-core / owner-local 约束下，采用预分配的单次查询临时空间，不把半命中挂到 FlowEntry 跨包累计，也不增加跨 worker 的共享可变合取表或逐包协调。

例如同一双向连接的两个包是 `40000 → 443` 与 `443 → 40000`。规则要求当前包 `源端口=443 AND 目标端口=443` 时，两包都不匹配，不能把两个包各自满足的一半拼成命中。

查询代号懒初始化可避免每包清空全部状态槽：本次首次触及才重置，代号回绕时清空。具体位宽和布局留给实现，但不能串用不同查询 / 程序的半命中状态。共享编译程序保持不可变；临时状态、决策缓存和 Flow 可变事实各有清楚的生命周期。

这不禁止 CT / LPI 事实持续维护，也不禁止在满足有效性契约时跨包复用完整匹配结果。

## 5. 自动前置 / 后置编排：本轮最新确认的方向

### 5.1 从 UI 位置选择转为编译职责

中途讨论过让用户选择前置 L4 或后置规则。用户随后提出：能否根据整个规则组，由编译器自动决定执行位置。该方向已被接受，同时明确要求特别小心、采用保守策略。

用户定义条件、动作和优先级；编译器选择安全执行计划。不能因为一条规则只使用 IP / 端口，就无条件前移。

这里的分析范围已确定为第 3.4 节中每个应用拍平后的有效规则集，不是一个孤立小组。先消除组织边界，再比较完整 Rank、条件重叠与事实依赖。

分配粒度已明确：**暂不允许一条逻辑规则同时出现在前置和后置，不做跨位置的半条规则续算。** 曾讨论的残余续算、按包决定一条规则两侧分工等方案不是首版方向；用户接受整条分配损失部分前移机会，以控制复杂度。

### 5.2 相同输入必须得到相同结果

用户特别澄清：关注的是匹配条件没有变化的情况，不是后来识别出新协议导致结果变化。

本轮确认的不变量是：

    对同一有效规则集：
    规则版本相同 + 匹配输入相同 + 输入可用性相同
        ⇒ 前后置编译计划与平坦规则集的获胜规则、动作相同。

“前段还没读取某个已有字段”不是输入发生变化，也不能据此把更高优先级规则当成永远不匹配。

自动前置不能额外赋予规则最高优先地位。正确关系是：先证明能够保持用户规则的逻辑结果，才允许提前执行，而不是先搬到前面再用阶段顺序改变结果。

这修正了早先将全部前置 L4 视为天然高于全部后置规则的解释。应用联网禁用也已确定作为普通最高优先级规则参与，而不另留后端 Gate 特权；运行时故障、传输和 Adapter 约束仍不属于该规则优先级空间。

### 5.3 已接受的整条分配算法

按完整优先顺序处理（Rank 数值从小到大），传播必须后置的约束：

1. 先标记必须后置的规则：需要 CT / LPI / SNI 等后置事实、不被前置完整执行能力支持，或违反已经明确成立的事实维护约束。不得自行增加第 5.6 节已撤回的全轨迹要求。
2. 依序处理每条规则 R。若 R 本来必须后置，保持后置。
3. 否则，若 R 可能与任何更高排名、已经后置的规则 H 同时匹配，R 也后置。
4. 只有排除了上述竞争和其他前置约束，才将 R 放到前置；无法证明安全就保守后置。

第 3 步必须包含因传播而后置的静态规则，不能只查直接依赖 CT / LPI 的初始集合。即使两条规则动作相同，也不能忽略它们的竞争，因为赢家及归因必须保持一致。

### 5.4 后置约束传播示例

以下暂只看匹配和完整排名；数字越小越优先：

| Rank | 条件 | 动作 | 分配 |
| --- | --- | --- | --- |
| 1 | TCP，目标端口 443，且识别为 SSL | ALLOW | 依赖 LPI，必须后置 |
| 2 | TCP，目标端口为 22 或 443 | ALLOW | 与更高排名的后置规则 1 重叠，后置 |
| 3 | TCP，目标端口为 22 或 80 | DROP | 与已经后置的规则 2 重叠，后置 |
| 4 | UDP，目标端口 53 | DROP | 无上述 TCP 重叠；满足其他事实维护约束时可前置 |

规则 3 与规则 1 不直接重叠，仍必须受到规则 2 的约束。否则 TCP 22 会被前置规则 3 抢先 DROP，而平坦规则集本应由规则 2 ALLOW。规则 3 并非整条冗余，它还可能在端口 80 获胜。

用户明确接受这类保守传播的代价：不为把规则 3 的端口 80 部分移到前置，就把同一逻辑规则拆到两个位置。

在固定输入下，若前置赢家 P 还可能被更高排名的后置 H 击败，则 H 与 P 在该输入上同时匹配；这本应触发传播，让 P 后置。因此满足上述条件的前置命中可以是整个有效规则集的赢家。该推理解决匹配 / 排名；事实维护约束的适用边界以第 5.6 节最新澄清为准。

### 5.5 运行时结果与保守分析边界

前后置之间不传递半条规则续算。前置完成查询后只需区分：

| 前置结果 | 后续行为 |
| --- | --- |
| NoMatch | 继续必要的 Flow / 事实处理，再查询后置；后置也无匹配才使用默认 ALLOW |
| Match，实际 DROP | 立即终结；不查询、创建或更新 FlowEntry |
| Match，实际 ALLOW | 保留完整赢家并锁定该有效规则集的决定；继续必要处理，但同组低排名后置规则不能推翻 |

这里的实际动作按既有有效执行模式解释；匹配结果仍保留声明动作、模式和规则来源。不能让 observe 的声明 DROP 绕过已有模式解释直接丢包。

前置 ALLOW 不能退化成丢失赢家信息的旧式 PASS_NEXT。例如更高排名静态 ALLOW 已成为整组赢家时，低排名 LPI DROP 不能另起一轮裁决将其覆盖。“该有效规则集已定案”也不意味着跳过必要统计、识别维护、传输和 Adapter 完成。

所有 mask 展开片段、因子条件、合取完成节点与剩余校验都继承整条规则的唯一位置。第 4 节的内部索引 / 校验优化不能重新引入跨 Flow 两侧的规则拆分。

重叠分析可使用协议互斥、地址 / 端口不相交、保守静态范围等简单证据；不能证明不相交就按可能重叠处理。证明预算用完则放弃相关前移，不要求完整 SAT、全量布尔展开或全局最优切分。规则 / 编译产物超过硬资源上限与“不能证明某个优化”是两种情况，前者按明确配置错误处理，后者保持合法保守计划。

### 5.6 事实维护约束的边界（2026-09-15 修正）

当前正式执行约定中，前置 DROP 不进入 FlowRuntime；后置 DROP 不回滚已经进行的 CT 观察。把一个晚阶段 DROP 前移，可能改变之后包所看到的事实轨迹。

这并不把“所有包都先进入 Flow 时的完整 CT 历史”定义为自动编排必须复制的参考轨迹。中途曾据此要求方向互斥的静态规则也后置，随后又提出应用级观察范围；用户明确拒绝这一路径。不能以未被接受的额外观察要求推翻既定的整条分配算法。

用户已再次确认：真正前置的 DROP 就立即结束，即使对应 Flow 已经存在，也不补做 CT / LPI，不在 DROP 后偷偷进入 Flow。不能用“先前置 DROP，再补必要状态”绕开这个边界。

正确性不变量仍是第 5.2 节的相同规则版本、相同输入和可用性下，逻辑赢家及动作一致。真实提前 DROP 造成后来观察事实不同，本身不构成禁止前置的额外理由。已经明确成立的生产者契约仍需遵守；缓存命中也不能跳过正常路径要求维护的状态。

后续如有具体生产者确实要求某种输入维护，应明确该要求及适用条件，而不是预设“存在 CT / LPI 就必须观察整个应用的全部双向流量”。本轮没有承诺任意时间序列均等价，也没有新增应用级 watch scope。方向示例及保守分析方法见第 15 节。

## 6. 输入可用性与 LPI 结果语义

### 6.1 不用额外 UI 状态替代规则输入模型

讨论中曾尝试用三种 UI 识别状态直接决定规则语义，用户认为不自然、可能过度设计；该方案没有被接受。

当前共识是区分输入是否可用，以及可用时的结果值。它不强制新增一套面向用户的三状态配置模型。

| 当前输入 | 协议比较的含义 |
| --- | --- |
| 尚无可用识别结果 | 缺少比较输入；不能利用 NOT 变成命中 |
| 已发布具体协议结果，识别仍在继续 | 结果立即参与规则，无须等全过程结束 |
| 明确的最终 Unknown / 未识别结果 | 是有效结果，可以正常比较 |

“明确的 Unknown 结果”不是“我们不知道有没有结果”。如何将未启用、执行故障、未映射结果、预算结束等底层原因归一化，仍需定义；不能把它们全部机械地视为同一种可用 Unknown。

SNI 的确定缺失与输入不可用已在第 26 节进一步明确：含 SNI 条件的整条规则先要求流已识别为 TLS / QUIC；此前提下，正常解析确认无 SNI 是可参与匹配的结果，尚未得到确定结果时不能利用域名条件的 NOT 命中。第 25 节的预算停止继续保留未取得事实的不可用性，不自动发布确定缺失。

### 6.2 NOT 针对当前已发布结果

以下行为已经明确接受：

| 情况 | NOT（结果包含 SSL） |
| --- | --- |
| 尚无可用结果 | 不能凭此命中 |
| 当前已发布结果为 SMTP，仍继续识别 | 成立 |
| 后续累计结果变为 SMTP、SSL | 不再成立；相关缓存需失效或重新验证 |
| 已明确得到最终 Unknown | 按正常结果比较，可成立 |

已识别到一个协议但后面还能识别到更多协议，不要求否定条件额外等待整个检测结束。这里采用的是当前结果语义，不承诺未来不会再出现新的结果。

如果用户配置 NOT SSL → DROP，可能在 SSL 出现前阻止必要交互，从而使识别无法继续。用户接受该后果；系统不隐式放行、不改写规则来替用户兜底，但必须能解释实际丢包原因。

### 6.3 LPI 过程的源码核对结论

这些是参考事实，不是当前产品已经完成 LPI 集成的声明：

- 上游 libprotoident 接收有限的双向特征并执行一次猜测，没有替调用者定义整个 flow 的识别完成 / 继续生命周期。
- 一次调用返回 Unknown，只说明当前输入未匹配，不是“永久识别失败”或停止命令；库给出一次已知猜测，也没有不可改变的终态保证。
- 参考 fork 的包装层逐包更新当前方向的特征，执行基础猜测和扩展识别，再映射为受支持的 AppID。
- fork 把新的映射结果按首次出现顺序去重追加；后续某包没有新结果，不清除先前累计结果。
- 普通映射结果可停止检测；隧道、NAT、部分邮件升级等情形允许继续。这些停止 / 继续策略来自包装层，不应归为上游库原生生命周期保证。
- fork 默认最多检测 20 个带 payload 的包，最多保存 8 项去重结果。这是参考参数，不是本轮验证通过的产品常量。
- 继续识别不代表可以自动解封装或解密任意内层流量，也不意味着已经具备完整流重组 / 深层协议解析。

上游原生输入更新与 fork 包装层也不相同：上游围绕每方向的初始 payload 特征取样，fork 的当前方向特征会随检测包更新。不能把 fork 的连续识别行为直接归因于上游默认调用方式。

需要保留的一项例子修正：此前用过 SOCKS → Telegram 来说明累计结果与优先级。检查的 fork 虽包含 Telegram 检测器，但 AppID 映射没有接入对应名称；这个例子只能视为规则语义假设，不能当作已验证识别能力。

## 7. 识别时机、动作与包处理边界

已确认：

- 当前共享策略动作是包级 ALLOW / DROP；不能因为 fork 有会话终止或注入能力，就为本项目增加“终止连接”承诺。
- NFQUEUE 的包级 DROP 不等于主动断开 TCP、发送 RST 或销毁整个 flow。
- 为取得识别结果，某些必要早期包可能已经按当时规则通过；不支持追溯修改已经完成的 verdict。
- 正常处理当前包时同步取得、且在 Adapter completion 前可用的事实，可以影响当前包。
- completion 后才到达的事实，只能影响后续包。
- 不缓存或扣留包来等待未来识别结果；“后置”不等于等待未来包。
- 不存在无条件放行首包或前 N 包的例外。若当时规则已经足以决定 DROP，仍按规则执行。

前一个包 ALLOW，之后因实际输入变化而 DROP，可以成立；固定规则及固定输入，仅仅拆成前后两个执行位置，就得到不同最终结果，不可以成立。

## 8. 编译、匹配与缓存必须统一设计

### 8.1 快速路径是有条件复用，不是永久授权

结果缓存是需要的能力。缓存可以省去重复匹配，但不能把一次 ALLOW 冻结成整个 flow 永久放行，也不能绕过必要的事实更新。

缓存有效性必须覆盖该结果实际依赖的输入、输入可用性、策略身份及必要上下文。相关输入变化后，原结果不能继续未经验证地复用。

依赖范围不能只取当前获胜规则用到的字段，还需要考虑能够改变获胜者的更高优先级竞争规则。例如，当前 CT 规则 ALLOW，不代表可以忽略后来可能命中更高优先级规则的 LPI 结果。

“新规则编译”与“新事实出现”是两种不同变化：

- 规则变化：生成 / 发布新的执行计划，并处理旧判定缓存。
- 事实变化：更新 owner-local 输入及相关缓存有效性，不因此重新编译用户规则。

### 8.2 两类 mask 不应混淆

编译后按规则形状组织索引的 mask，与结果缓存描述“哪些输入变化会改变本次选择”的依赖 mask，不是同一个概念。

不能只复制获胜规则的匹配 mask 作为缓存有效性证明。保守地依赖更多字段会降低命中率；漏掉必要依赖则可能错误复用。

后续已将首版基线收敛为 worker 私有、固定容量的结果缓存，使用编译器生成的保守输入依赖摘要。具体容量、替换策略和容器布局仍是工程细节，不为此增加跨 worker 可变共享状态或复杂多级缓存框架。

### 8.3 跨 flow 复用的边界

跨 flow 复用的例子已被理解和认可，但不要求首版所有事实类型都能跨 flow 命中。

它只表示多个独立 flow 在相关匹配输入及上下文相同时，可以复用纯匹配结果。不意味着：

- 同一应用的所有连接共享同一 verdict；
- 第二条 flow 可以继承第一条 flow 的 LPI 识别结果；
- CT 状态、计数、生命周期被合并；
- 跨 flow 必须变成跨 worker 的共享可变缓存。

所需事实仍必须分别取得；是否可复用取决于有效输入约束，不取决于“都是同一个应用”这种过粗判断。

### 8.4 缓存保存完整查询结果

统一的逻辑结果是：

    Match { 逻辑规则引用、完整 Rank、声明动作、有效模式、来源归属 }
    或 NoMatch

这是逻辑契约，不冻结 C 结构体或具体 ABI。缓存不能只存一个 ALLOW / DROP 位，否则无法保留赢家、执行模式及正确归因。

直接完整匹配、合取完成和缓存命中最终走同一条结果处理路径。缓存命中仍为当前包更新正确的计数和归因，不因跳过匹配就漏记，也不因多个片段命中重复计一条逻辑规则。NoMatch 不伪造规则命中。

只有已完成的正常查询结果才能缓存为 NoMatch。“已完成”指当前可用性语义下查询已经得出结论，不要求所有可能事实都存在；基础设施错误、执行中断、资源旁路或只扫描了一半不能冒充 NoMatch。缓存满、碰撞后守卫不符或失效时回到正常查询，不改变策略含义。

### 8.5 编译器同时产出保守依赖摘要

首版覆盖当前适用规则程序可能使用的逻辑输入，不追求每次查询单独推导最小条件集合，也不直接使用赢家索引 mask 作为依赖摘要。

缓存有效性至少关联：

1. 当前适用的应用 / subject 策略视图及其绑定上下文。
2. 规则程序所属的完整快照身份。
3. 相关输入值及其可用性，或足以等价保护这些输入的事实版本。

同一个通用匹配器中：

    Rank 1：LPI 结果包含 SSL → DROP
    Rank 2：目标属于某网段 → ALLOW

最初 LPI 没有可用结果时可由规则 2 获胜。之后发布了 SSL，即使 IP / 端口不变，也必须失效并重新匹配，因为规则 1 可以成为新赢家。守卫要覆盖竞争者，不只是当前赢家。

CT / LPI 事实版本只能在绑定了正确 Flow 实例和生命周期的前提下代替值比较；不同 flow 的相同版本号、五元组复用后的新实例，都不能据此共享旧结果。应用归属 / 可用性改变也可能更换有效视图，不能因为 Flow 身份没变就继续使用旧应用的判定。

按当前包源 / 目标字段匹配时，去程和回程的输入可不同，不能只凭双向 Flow Key 相同就复用。与规则无关的字节计数、last-seen 等统计更新不作为策略事实变化；多包含必要之外的事实依赖可以接受，漏掉影响赢家的依赖不可以。

### 8.6 位置、状态与缓存不能互相偷换

前置缓存只使用当时合法可得的输入，不为获取 cache key 而查询或创建 Flow。后置使用既有必要 Flow / 事实处理提供的输入；命中缓存也不跳过必要维护。

共享的是不可变规则程序与依赖摘要；查询临时状态、缓存读写与 Flow 可变状态仍归当前 owner。32 条展开预算、因子化与剩余校验只是不同编译布局，不形成另一套失效或归因语义。

## 9. 策略变化后的缓存处理

用户最初提出结合编译结果变化及现有缓存判断影响范围，随后明确接受保守策略：即使多失效一些缓存，下次判断也可以重新匹配并补回，不宜为了最小失效集合过度设计。

当前原则：

1. 发布新的一致快照，不在 Apply 时主动遍历、清空或终止所有 flow。
2. 新版本下的包不能直接使用未经验证的旧判定。
3. 首版按完整快照身份不符使旧结果惰性失效，按新计划重新匹配；不以跨版本精确重验证作为必需快速路径。
4. 不要求精确语义 diff、最小失效集合、长期保留所有历史版本或一个布尔等价求解器。
5. 失效的是策略派生结果，不因此清除 CT / LPI 已得事实、Flow 身份和累计计数。
6. 即使动作没变，获胜规则或来源改变时，也要更新归因和相应引用。
7. 缓存不得靠保留旧编译程序的裸引用而绕过快照生命周期管理。

策略更新与事实变化使用互补的守卫：新快照身份阻止旧版判定混入，相关输入 / 可用性变化阻止同版旧事实判定复用。沿用既有 generation、revision、snapshot hash 等完整身份约定；不能只比较可能重复的 revision，同 revision 而 hash 不同也必须失效。

这不要求把每条缓存立刻物理删除，更不要求跨 worker 扫描、清空 FlowEntry 或改变池生命周期。旧包可在已绑定的旧快照内完成，但下一个绑定新版的包必须检查新身份；连接不是终身固定旧策略。

精确语义 diff、跨版本部分重验证和最小失效集合不作为首版要求。允许保守失效也不是“规则更新的性能影响已经测得很小”的证据。

OVS 提供了依据当前规则重新验证缓存的参考，但不能把它概括成“直接比较两份编译产物”，也不能照搬它允许的异步重验证时间窗口来放宽本项目的新快照一致性要求。

## 10. UI：已排除的路径与接受的方向

本轮专门讨论了用户是否应选择 L4 的前置 / 后置位置。

以下方案没有被接受，不能复活为默认设计：

- 两个固定、并列的规则区，要求普通创建流程先选 L4 或通用规则。
- 普通新规则全部默认进入通用引擎，把独立 L4 降为只有高级用户才主动启用的特殊能力。

另外，讨论指出了“最高优先级”这一标签的解释风险：单靠它无法说明 L4 的 ALLOW 是否还会继续后续检查。具体文案未定，不将这一提醒记成已批准的界面。

当前接受的方向是：用户定义规则及优先级，组 / 集合用于组织复用，编译器对应用拍平后的有效规则集自动安排整条规则的安全位置。不是根据单条规则的字段类型进行隐藏分类，也不是把前置 / 后置变成必填配置。

中途曾在“独立 L4 固定优先”和“统一逻辑排序”之间反复澄清；最新结论是：保留物理前置与真实提前 DROP 能力，但位置不另赋优先权，整条分配必须保持平坦有效规则集的赢家。应用联网禁用已进一步确定为最高优先级普通 DROP，不再沿用先前保留独立硬 Gate 的建议。

联网禁用规则的最高顺序与专用修改入口由界面 / 配置层维护，不要求后端引擎添加特权。除此以外，具体编辑器和解释呈现仍未冻结。

具体编辑器布局、优先级数字或拖拽、规则组展示、编译位置是否提供只读解释、修改规则后的提示方式，仍未决定。不能把“自动编排被接受”扩大为某张界面线框已经批准。

外部产品研究只提供对照：

- Little Snitch 的常见创建路径围绕应用、目标和允许 / 拒绝，不要求先选执行阶段。
- LuLu 将普通规则与覆盖普通规则的特殊名单分开呈现，但其 Allow List 是豁免语义，不能套用成本项目的 L4 ALLOW。
- Cloudflare Gateway 显式分层，并允许 Network 层通过后被 HTTP 层阻止；其企业产品界面不构成本项目必须分区的理由。

没有从这些资料得出唯一“最佳实践 UI”。也不能为了隐藏层次，让用户看到的优先级与实际结果不一致。

## 11. 可观测性要求：目标与最新方向入口

用户接受规则可能造成最坏连接结果，但明确要求后续解决：

- 在哪个处理位置丢包；
- 因为哪条规则；
- 丢了多少；
- 什么时间发生。

自动编排、缓存命中和匹配器内部候选都不能让这些解释失真。尤其不能将前置 NoMatch 或内部半命中记作整组最终 ALLOW，再把同一包重复解释为两次相互矛盾的终局判定。

已收敛的最低实现约束是：直接匹配、因子化匹配和缓存命中最终保留同一逻辑赢家与来源，走统一的结果 / 计数处理；内部片段不是独立命中规则。它不等于完整可观测性方案已经设计完毕。

后续讨论已确定个人设备定位、四类常态视图、配置 / 观测分库、有界保留，以及 Flow 与轻量阻止观测的累计快照和分方向归因。最新口径集中在第 21.4—21.26 节；固定窗口由 Rust 后台增量维护，VPP 非阻塞导出且不等消费确认，增长阈值之外允许低频时间驱动；Rust 同次消费推进观测状态与时间统计，并以 KISS 保持消费简单。时间精度、保留与压缩已有第 21.23 节的初始默认，第 21.25—21.26 节明确计量口径与 L7 多标签。常态轻量统计事实不能与 debug 的完整逐包路径混淆。

尚需落实的是计量路径的具体接入、事实可用性与分类细节、归因消息合同、简单缺口处理、条目键、其余资源数值、传输和数据库实现。第 21.13 节保留交接时的议题地图，第 21.14—21.26 节记录其后收敛、提案与修正，须按各节的确认状态阅读；时间精度、保留与压缩按已给工程默认推进，初版后可调整。

## 15. 2026-09-15 续记：方向与简单保守重叠分析

### 15.1 当前包方向与 Flow 方向分开

已确认：`src_ip / dst_ip / src_port / dst_port` 始终是当前包的源 / 目标，不随 in / out 自动交换，也不隐含客户端 / 服务端端点。

- `in / out` 相对当前设备，描述入站 / 出站。
- `ORIG / REPLY` 相对 Flow 首次观察方向，是 CT / Flow 事实。首次观察不保证就是客户端发起，不能从端口号推断。
- 不为一条规则隐式添加反向匹配。用户表达双向条件时仍须明确其逻辑。

例如，高排名 H 为 `out AND TCP AND dst_port=443 AND 某 CT 条件`，必须后置：

| 较低排名静态规则 R | 分析结果 |
| --- | --- |
| `in AND TCP AND src_port=443` | 与 H 的设备方向互斥；没有其他已成立的限制时，可以前置 |
| `out AND TCP AND src_port=443` | 可能与 H 同时匹配：源、目标端口可以都是 443；按后置传播处理 |

不能因为第一条规则“看起来是回复包”就交换其端口条件；也不能为了保留假定的全量 CT 历史，重新把它强制后置。第 5.6 节记录了这次修正。

### 15.2 采用静态包络证明不相交

用户接受先用简单、保守、便于实现的分析，不继续为极少数前移机会建立完整逻辑求解器。

1. 为整条规则提取设备方向、地址族、传输协议、src / dst IP 与端口等静态范围。
2. AND 合并可确定的约束；OR 为各对应字段取覆盖所有分支的并集 / 范围，允许丢失字段间关联。
3. 难以处理的 NOT，以及 CT / LPI / SNI 等动态部分，在该分析中视为不限制；外层其他已知的静态约束仍保留。
4. 任一对应字段能证明不相交，即可证明两条规则不重叠；否则按可能重叠处理，并套用第 5.3 节的完整 Rank 传播。

包络只能扩大候选范围，不能漏掉真实匹配输入。损失的是前移机会，不能改变最终匹配语义。实际执行仍准确处理 AND / OR / NOT，不把包络当成完整规则执行。

不做全量 DNF、完整 SAT 或全局最优切分。更精确的关联证明可作为后续有证据支持的优化，本轮不继续展开。

DNS 与 VPP 可以共享名称定义、名单、规范化与匹配能力，但不同消费者只能执行其具备条件的规则。

用户明确纠正了以下错误转换：

这条规则仍只在目标端口 443 等条件完整成立时生效，不能提取其中的域名，变成全端口拒绝或 DNS 查询拒绝。DNS 查询一般不知道后续连接的目标端口；名单复用不赋予删掉条件的权限。

## 17. 本版 SNI 与 TCP 流数据缓存

### 17.1 本版范围

已明确本版需要 SNI 提取和 VPP 域名谓词，与 LPI 一起提供匹配事实。SNI 覆盖 TLS 与 QUIC；暂不解析隧道内流量，有实际需求后再讨论。

此结论不自动扩展为 HTTP Host、DTLS、任意 STARTTLS 或所有协议升级形态的完整支持。升级路径的具体覆盖尚未冻结。JA3 / JA4 等握手指纹是以后可能的消费者，本版不实现。

### 17.2 fork 的数据路径是调查证据

只读检查的外部 fork 位于 `/home/js/backup/backup/Git/vpp`，以下描述针对检查时工作树，未作为本产品运行或验收：

- TCP 路径中，session 的 TCP 流还原先提供顺序数据；LPI 读取当前提供的 payload，TLS decoder 在 LPI 产生相应协议标签后工作。不是“先识别 TLS 才有任何 TCP 流还原”。
- `session_manager/session_manager_feature_order.c` 显示 LPI、协议 decoder、scanner、enforcer 的顺序；UDP 路径中 QUIC / DTLS decoder 位于 LPI 与 scanner 之间。
- TLS decoder 要求 TCP segment 与 TLS 标签，处理 TLS record 及握手分段，再调用 `tls_message_parser_parse_client_hello` 取出 SNI。
- QUIC 路径处理 Initial 保护和 CRYPTO 数据组装，复用 TLS ClientHello 解析；scanner 发布 TLS_SNI / QUIC_SNI 及 session 目标名称等结果。
- fork 的有序 TCP 数据存在借用路径，乱序数据需要复制；TLS trunk 还会 realloc / 复制。TLS / QUIC decoder 在部分握手阶段也会 detain 原包，不能把它描述为只有一份字节缓存、完全不扣包。

这些是路径与所有权观察，不是对整个 fork 内存上界、性能或回收完整性的验证。该 fork 面向网关，其资源方案不直接成为个人终端方案，也不直接导入源码。

### 17.3 最新决定：不因等待 SNI 扣住原包

讨论中曾短暂接受有界的 fork 式原包暂存，随后用户根据个人设备资源和现有处理方式明确修正：

**仅复制后续解析所需的流字节，原包仍根据当前已可用事实执行规则并正常完成，不等待未来 SNI。**

- 若处理当前包时已经取得 SNI，可用于当前包随后的规则判定；若尚未取得，只影响以后具备该事实的包。
- 不增加“前 N 包自动放行”。现有 CT / LPI / 静态规则仍按当前输入和完整 Rank 执行。
- 等待解析数据与 Adapter 持有原包是两种资源。不能从需要流还原推导出必须扣住原包。
- 当前 C 主线没有本轮设计的 SNI 等待路径。测试 hold CLI 和 IP 分片重组不是这项产品能力，也不能用于证明已有 SNI 持包行为。

先前提出的 `96 KiB / flow`、`16 包`、`1 秒`、`32 个活跃 SNI 解析`、`4 MiB 总额`及每 lane 持包槽位，只是已被后续方案替换的中途建议，不作为默认配置。没有接受新的数值替代它们。

### 17.4 一份缓存及其资源边界

用户要求遵守 KISS，同时为以后真正需要的消费者保留扩展空间：

1. TCP 流还原 Module 拥有一份有界数据拷贝，按序号处理乱序与重复，向 TLS / SNI 暴露可用的连续字节。
2. TLS / SNI 引用这些数据并保留少量解析状态，不再保存第二份完整 ClientHello。最终小型域名结果可以复制保存。
3. 上限按**当前缓存的字节长度**衡量，不按累计包数 / 重传次数衡量。同一范围重传不形成另一份逻辑数据副本。乱序索引、窗口跨度和元数据同样要有界。
4. 不另设 32 个活跃 SNI 解析名额；需要解析的 TCP 数量随实际流量和既有 Flow 容量约束。仍需测量整个设备上的资源峰值，不能把取消独立名额理解成无界分配。
5. 两个 TCP 方向各有序号空间，但属于同一 Flow 的资源核算。讨论中的每 TCP 共 8 / 16 KiB 仅是量级示例，未冻结为产品常量。
6. 超时清理有必要；预算耗尽 / 超时行为已在第 25 节确认，具体时长与容量留实施和实验。QUIC 使用自己的握手数据组装，不套用 TCP 序号重组。

当确认协议不再需要本版任何后续消费者，或 SNI 解析 / 尝试已经结束时，停止相关流还原并释放缓存，保留 Flow、CT 及已经发布的结果。暂时 Unknown 不能误当成确定不需要解析；LPI 继续识别或协议升级的可能性需要结合真实生产者契约处理。

未来 JA3 / JA4 可以复用同一 TLS 解析输入，但本版不预建多消费者订阅总线、复杂引用框架，也不为尚未实现的功能长期保留字节。个人设备应节省内存和复制，同时不按极端嵌入式约束反复增加独立配额。

## 18. 域名匹配语义及暂定候选

### 18.1 必需语义与优先目标

用户明确要求区分：

| 模式 | `example.com` | `a.example.com` | `badexample.com` |
| --- | --- | --- | --- |
| 精确名称 `example.com` | 命中 | 不命中 | 不命中 |
| `example.com` 自身及子域名 | 命中 | 命中 | 不命中 |

域名匹配必须按标签边界，不是任意字符串后缀。个人终端尤其移动设备优先查询效率和内存。用户随后在第 23 节确认初版只支持上述两种模式，复杂 glob / regex 后置，并确认基本规范化与导入原则；具体导入兼容清单和校验实现仍待落实。名单来源已有此前调查，本轮不再重复来源选择。

匹配 Module 返回相关名称条件 / 名单归属，由通用引擎结合其他条件及完整 Rank 决定动作。一个名称命中多个祖先、多个名单时，必须保留可能参与规则竞争的结果；不能暗加“最长名称优先”“白名单总覆盖”或“最小 ruleId 单独获胜”。

名称存储可以去重，但不能丢掉精确 / 子域模式、名单身份与逻辑来源。字典共享不可变存储，worker 保持自己的查询临时状态；不为每个 worker 复制整份大名单。快照、缓存守卫和统一归因继续遵守前文契约。

### 18.2 已完成调查，尚未选定依赖

历史核对发现 iodé 及本项目旧版本的大名单主要使用哈希表和逐父域查询，小型自定义规则另走正则。生产用途证明其有参考价值，不证明它在当前个人设备要求下最快或最省内存，更不能沿用其隐藏的白名单 / 精度优先语义。

进一步调查得到以下暂定比较范围：

| 候选 | 当前定位 | 需要实测 / 适配的事项 |
| --- | --- | --- |
| libdatrie | 首轮完整 C 库候选 | 公开增量游标可收集祖先；尾串分配、运行内存和更新峰值需测 |
| 维护中的 Valkey rax | 首轮 C 源码复用候选 | allocator / assertion 支持层及祖先查询适配；不能当成旧独立 rax 的相同版本 |
| VPP 字符串 hash | 比较基线 | 名称与名单 payload、逐父域查询成本，以及未来独立 DNS 的依赖安排 |
| Knot QP trie | 保留的生产代码备选 | 小支持层提取、祖先查询临时状态和真实总内存 |

BIND QP 的原生祖先能力有参考价值，但配套运行时较重；libart、CMPH、MARISA 等的接入取舍及证据限制保存在调查报告中，不继续凭抽象复杂度决定胜者。序列化文件大小、只计索引的 bits/key、桌面微基准均不能替代完整手机运行内存与延迟。

## 21. 宏观定位与旧设计参考（2026-09-18 续记）

### 21.1 已确认的定位与本轮讨论层次

用户同意可观测性覆盖三个方面：**网络活动、控制效果、系统健康**。产品面向个人设备，不以网关优化为目标；平时关心概况，不常驻记录最详细信息，排障时才由用户开启详细记录。

用户随后两次澄清讨论层次：先讨论支撑 UI 的底层能力及架构归属，不先进入 UI 使用流程，也不先冻结字段、计数器、时间窗口和日志参数。领域概念由哪层拥有、编译和执行怎样分工、观测与存储由谁维护，仍有需要梳理的架构选择。

用户明确的当前倾向是：后端作为完整的引擎，支持规则集、规则组，并承担编译和执行；前端负责编辑。第 3—5 节的拍平和统一排序是后端执行语义，不要求前端先丢掉规则组织关系再提交配置。这里没有决定编译在后端内部的具体进程 / 语言分布。

用户提出的观测能力包括状态 / 计数、通过 CLI 或 API 获取当前流表及统计，以及详细模式下追踪包怎样判别、经过哪些规则。用户随后明确更正：`status` 文件是口误，指的是内存中的状态与计数，不是实际文件。常态详细逐包日志的体量不可接受，不能把“具备详细诊断能力”变成默认全量记录。

用户希望个人设备产品把观测保存等能力集成在一起，并进一步以 VPP 的内存状态 / CLI 与向外导出的 records 为类比，明确这里“前端”指 Rust 应用侧整体。它包含记录消费与存储职责，不能只理解成纯 UI。具体进程数及是否同进程尚未确认；数据库分离与保留方向见第 21.4 节。旧 fork 的外部存储链路不能直接成为个人设备的部署要求。

### 21.2 旧非 VPP 设计中值得作为起点的内容

本轮用户要求回看已经尝试建设的旧体系，梳理可参考内容。定向结论追加到[旧版调查第 8 节](2026-09-15_OBSERVABILITY_LEGACY_RESEARCH.md)；以下是架构讨论入口，不是导入旧实现或冻结新模块清单。

| 旧设计内容 | 可参考的职责 / 语义 | 当前需要重新处理的边界 |
| --- | --- | --- |
| Metrics、规则计数、运行状态 | 以低成本查询回答当前状态及累计效果，与日志记录分开 | 接口、应用、规则等统计覆盖；VPP 中的计量点及更新 / 读取归属 |
| Traffic Windows | 日常概况不应依赖完整 Flow 记录或重诊断；在线统计与历史查询分开 | 属于后期收口设计，不能当成旧版完整实装；窗口、排行算法及所在层待重估 |
| Flow / Fact Records | 保存发生过的事实，支持上层历史与聚合；不以详细逐包 explain 作为常态输入 | 当前无 Flow 的提前 DROP 覆盖；本机 consumer / store 与数据面分工 |
| Packet Diagnostics / Explain | 显式排障时提供实际判定、跳过原因和规则归因；具有独立采集生命周期 | 当前统一 Rank、自动前后置、缓存及 CT / LPI / SNI 事实；不沿用固定旧 stage |
| PerfMetrics 与通道健康 | 区分系统自身成本、业务效果及观测通道丢失；观测开销本身需要管理 | 从旧 NFQUEUE callback 边界重新映射到当前 VPP / Adapter；旧采样层级及数值不直接继承 |
| Authoring 与来源回溯 | 后端保存规则、组及绑定；运行时给出稳定归因引用，后端据源配置还原来源关系 | 旧检查点数量、保存流程、阶段和排序表述不自动成为当前方案；历史版本保留范围待讨论 |

主要原始设计依据：[SNORT-10 §1、§2、§9、§10](SNORT_10_DISCUSSION_NOTES.md)、[Flow Telemetry §1—3](../decisions/FLOW_TELEMETRY_WORKING_DECISIONS.md)。需结合调查报告区分早期真实 producer 与后期设计约定。

### 21.3 不宜直接继承的旧选择

- 不恢复旧 C++ 模块、shared-memory ABI、vNext 命令、线程 / 锁结构和固定容量。当前产品实现边界仍为 VPP-native C。
- 不把全部观测都建立在 Flow 上，也不为保留旧观测覆盖而让前置 DROP 重新进入 CT。
- 不沿用持久 `tracked` 导致没有诊断 consumer 仍构造重解释的行为；保留的是按需诊断这一职责。
- 不把旧文“前端负责持久化 / 聚合”直接解释为 UI 持有权威数据库。consumer 是功能职责，其在当前完整本机后端中的归属需要明确。
- 不用最近一条记录、累计快照或一个 dropped 总数推导完整历史；旧设计暴露的覆盖、归因和丢失边界应作为新设计的检查依据。

当前只确定参考材料及宏观方向。各类能力是否为独立模块、常态记录保留范围、流表读取方式、导出通道和存储实现，仍留在后续架构讨论中。

### 21.4 内存状态、两类数据库与保留方向（后续确认）

用户明确区分两类数据库 / 独立存储：

| 存储 | 内容与方向 |
| --- | --- |
| 配置资产库 | 规则、规则组 / 集合、域名黑白名单及相关配置等长期资产 |
| 观测记录库 | 支撑常态查询和历史汇总的轻量观测数据，采用有界保留。此前包含 debug 详细记录的表述由第 21.35 节修正：debug 仅为一次调试会话的临时数据，不进入常态长期观测历史 |

这修正了助手先前提出的单一物理 Product Store 起点；本轮按配置资产和观测记录分库继续讨论。具体数据库引擎、schema、进程和文件布局尚未选择，也未修改正式产品计划。

VPP 的运行状态、计数和当前流表仍属于内存状态及实时读取能力；需要历史查询的记录 / 汇总才涉及观测存储。Rust 应用侧是记录消费、保存和查询的讨论位置；不因此把旧 shared-memory queue 或 fork 的导出协议直接确定为新传输方式。

用户进一步确认：近期记录应在有限时间内保留；更久的明细默认不应占用大量空间，用户可通过设置扩大保留范围。更长期倾向只保存总结后的计数等信息。因此观测存储需要区分**近期明细、较长期汇总、用户主动扩大的保留范围**，而不是把全部 session / 包级细节长期累积。

用户随后接受同时以**保留时间与总空间上限**约束观测数据，避免有限时间内的大流量仍产生过量存储。近期明细淘汰后，已经形成的较长期汇总独立保留；必要时可降低长期统计的时间粒度，不能据此声称仍可还原逐次通信。用户可通过设置调整保留范围与预算。

本节形成时，具体保留期、容量预算、汇总维度和时间粒度、跨重启恢复及容量不足时的取舍尚未冻结；常态后续默认见第 21.23 节。详细诊断的数据生命周期以后续第 21.35 节为准，只服务一次调试会话。具体数据库与淘汰实现仍未选择。

### 21.5 常态历史统计与 debug 深度的中途澄清

后续用户又要求核对旧版“轻量 Flow 统计记录导出、应用侧计算”的方案，见第 21.6 节。不能仅凭记录名称含 Flow / session，就把所有此类统计载荷一概归入 debug；下述当时表述须结合后续澄清阅读。

用户明确纠正：常态不需要采集 session records 或规则命中的详细执行路径，这些在 debug 模式才记录。此前助手提出以常态 session / 活动明细支撑复杂统计的方向，由本节修正；第 21.4 节的近期记录保留原则不能解释成常态必须产生 session 明细。

常态需要提供的能力明显多于一组实时 state 累计数，包括按给定时间段查询：

- 各应用的流量大小与占比。
- 某应用的 L4 / L7 协议流量统计。
- 规则命中统计，以及各规则对应的流量。

这些是有时间和分类维度的聚合统计需求，不要求保存每个包穿过 VPP 的完整路径、逐条规则的判定过程或单会话明细。仅区分“简单 counters”和“详细 records”两类不足以承接上述需求；常态历史统计需要单独明确其数据职责。

用户要求继续讨论明确准则：哪些统计常态采集、哪些解释与明细仅在 debug 采集。支持的维度交叉、时间精度、VPP 与 Rust 的具体聚合分工、L7 归类口径和资源上限尚未冻结。本节记录需求修正，不直接选择统计库、数据结构或传输协议。

### 21.6 回到旧版 Flow 统计导出与应用侧聚合方案核对（后续澄清）

用户指出其记忆中的旧非 VPP 设计：引擎保留必要固定计数，常态按流量增长、阈值或间隔输出较轻的记录；应用侧接收并保存，由应用侧计算时间范围、应用、协议、规则等统计；debug 才输出更详细的判定过程。用户要求先核对原设计，而不是直接决定由 VPP 常驻维护全部多维时间统计。

因此，助手上一条提出的“VPP 按时间与维度维护统计分组，再导出聚合块”仅是未接受的建议，不作为本轮既定架构。还需区分**轻量 Flow 统计快照、完整会话记录、逐包执行路径**的内容和成本，避免名称造成误判。

经定向核对旧原始设计与 producer，确认：

- 早期 Flow Telemetry 将常态高维查询 / 历史聚合交给应用侧 consumer；引擎输出原始观测事实及必要结果元数据，另保留固定 metrics。
- 常态 `FLOW` 为 `BEGIN / UPDATE / END` 累计快照。包 / 字节增长相对上次成功导出达到阈值、执行 / CT 状态变化、包到达时达到最大导出间隔等触发更新；应用侧按同一流的前后累计值计算增量。不是每个包都导出一条，也不是无包时每个流都有独立周期上报。
- 查到的增长阈值以 Flow 包 / 字节为单位；本次未找到独立的“规则命中累计达到阈值就导出一条 rule record”机制。规则归因随 Flow 执行结果及变化记录提供，实际覆盖仍须核对。
- 普通常态载荷写共享内存 ring；旧 tracked debug 事件经进程内队列输出 JSON / netstring socket 载荷。它们均可由应用侧消费，但不等于同一共享内存消息载荷。控制握手 socket 的使用也不能与 record 数据载荷混同；本次未证明两类记录在旧应用中最终保存到同一物理数据库。
- 后期 SNORT-10 的 Traffic Windows 是另一次设计调整，不能与早期实际 Flow producer 拼成一个从未存在过的完整实现。旧 producer 及导出渠道也不因此成为当前产品实现模板。
- 旧快照输出 Flow 累计量及当前 rule / decision；源码在变化前没有先导出旧规则段的边界量，不能把相邻快照差值直接全部归给新规则。旧 `proto` 也是 IP protocol，载荷没有本轮的 L7 / SNI 事实。这些限制不否定应用侧聚合方向，但说明旧字段不能直接保证当前全部统计需求。

详细源码核对见[旧版调查第 9 节](2026-09-15_OBSERVABILITY_LEGACY_RESEARCH.md)，原始原则见 [Flow Telemetry §0—3、§6—7](../decisions/FLOW_TELEMETRY_WORKING_DECISIONS.md)。当前继续以事实导出与应用侧聚合的旧方案为讨论输入；新传输是否统一、哪些统计必须在数据面维护、记录格式及归因完整性仍待后续讨论。

### 21.7 固定窗口由 VPP 常态维护（后续确认）

续记导航：本节保留当时已确认方向；用户在第 21.15 节重新澄清目的，随后接受第 21.16 节的 Rust 后台增量维护方向。本节 VPP 窗口归属不再作为当前决定。

用户说明旧固定窗口的动机：应用需要反复查看若干固定时间范围内的汇总，不希望每次重新计算。随后明确指出 Android 手机的续航约束，并确认**期望 VPP 维护一些固定窗口统计**。

### 21.9 常态历史以 Flow 累计快照推进；Flow 与规则分开（2026-09-23）

用户明确希望讨论的常态历史模型是：Flow 创建和删除等关键节点产生消息；流量增长超过阈值，或新包到达时距上次上报超过间隔，再产生累计快照。发送的是**总量，不是增量**；应用侧可按相同 Flow 实例的前后快照求差。该模型当时与 VPP 固定窗口并存，窗口归属后来由第 21.16 节改为 Rust 后台；累计快照模型保持，不要求窗口维护单位与历史记录单位相同。

这取代了助手提出的“常态历史以不重叠统计时间片为主要单位”的倾向；时间片不是当前已选的导出模型。具体消息格式、触发阈值与传输实现仍待讨论。

用户进一步确认：

1. **Flow 身份由生命周期确定。** 旧 FlowEntry 已被删除后，即使相同五元组再次出现，也属于新 Flow 实例，不接续旧累计量。
2. **规则变化不改变 Flow 身份。** 同一个 Flow 的包可以先后命中不同规则；不能因为赢家或策略变化就重建 Flow、重置 Flow 累计量，或把整个 Flow 归属于最后一条规则。规则与 Flow 是不同统计对象。
3. **当时上报间隔仅采用包驱动检查。** 有新包到达时检查是否应上报，不额外安排这项周期更新。用户后来在第 21.20 节明确补入低频时间驱动，将尚未上报的变化导出，不再要求等待下一包；Flow 过期 / 回收与观测更新继续分开。

Flow 快照的规则引用至多解释相应观察时的执行结果，不能把 Flow 总量或跨越多个规则的快照差值直接当成某条规则的贡献。常态已有独立的规则效果视图；历史规则统计如何导出仍需单独确定，不能依靠改变 Flow 身份规避归因问题。

### 21.10 归因变化边界与分方向维护（后续讨论）

用户提出：Flow 实际命中的规则发生变化时发送状态变化消息，此后区间中的包 / 字节增长归给新的规则；Flow 身份保持不变。助手将其分析为“稳定 Flow 身份 + 归因变化的累计边界 + 阈值更新”，而不是重新创建 Flow。

用户明确接受**分方向归因**：双向 Flow 的两个方向分别维护当前归因与对应方向的累计量，避免请求和回复采用不同规则时，单个全流 current-rule 在两个方向之间反复切换。它不改变既有 Flow 方向与设备方向分开的语义。

助手指出的正确性要求包括：变化边界位于新规则首包的贡献之前；周期阈值不能吞掉必要的归因变化；累计量能补回流量总量但不能凭空补齐丢失的规则归属区间；规则自身的整体计数继续独立存在。具体消息字段、缺口处理、同方向频繁切换的资源策略尚未冻结。

用户随后要求专门讨论前置 DROP 的观测，因为它没有 Flow。当前既定约束继续成立：不为记录前置 DROP 创建或更新 Flow，也不因此伪造 Flow 生命周期。

### 21.11 前置 DROP 的轻量阻止观测与超时生命周期（后续讨论）

助手先提出按应用 / 规则导出专属阻止汇总，用户认为不妥，要求重新比较。随后讨论转向按五元组等身份维护轻量阻止观测条目，以保留目标级历史并按累计量 / 阈值导出；应用 / 规则等固定统计仍作为独立的概况来源。该条目属于观测状态，不是 CT FlowEntry，不运行协议状态机、流还原或 LPI。

用户强调个人设备的工作负载，接受五元组变化频繁时形成不同观测条目、合并效果下降的取舍；不能为了合并而默认忽略端口或改变已有身份含义。

用户明确：**被阻止的通信不能期望存在正常结束信号，阻止观测超时结束即可。** 本轮据此以最后一次观察到被阻止包的时间计算空闲超时；后续被阻止包刷新最后观察时间，不能依赖 FIN / RST 或推断 TCP 正常关闭来结束条目。超时结束表示观测条目退役，不表示真实网络连接已经关闭。

该方向沿用创建、阈值更新、退役时最终累计快照的观测模型；发送总量，不在发送后清零。条目已退役后，同一五元组再次出现属于新的观测实例。上报间隔当时采用包驱动检查，后来由第 21.20 节补入低频时间驱动；空闲超时回收与尚未上报变化的导出仍是不同职责。

具体条目键中应用 / 网络身份的处理、超时数值、容量及回收机制、规则变化归因与记录格式尚未冻结。候选方案需要有界资源，但不将此前讨论的网关规模或旧容量参数当作个人设备默认值。

### 21.12 正常 Flow 与阻止观测的共存关系（后续确认）

用户接受“独立生命周期，共用观测语义”：正常 Flow 由既有 FlowRuntime 管理；前置阻止观测有自己的观测实例身份，以空闲超时结束。二者均可采用创建 / 更新 / 结束、记录顺序、累计量及归因变化边界，但不因此要求相同字段布局或已选定传输协议。

同一观测对象先被前置阻止、后来允许、再被前置阻止时：

- 初次阻止建立阻止观测 B1。
- 允许通过后，正常查找或建立 Flow F1，不将 B1 升级或转换为 F1。
- 再次阻止时，若 B1 尚未超时则继续累计 B1，否则建立新的阻止观测实例。
- B1 与 F1 的时间范围可以重叠，但承接不同的包。B1 表示其保留期内的阻止累计，不表示整个时间段都持续阻止，也不能用其首末观察时间伪造连接状态。

正常 Flow 的两个方向分别维护归因；前置阻止观测使用已有的设备包方向，不伪造真实 Flow 的 ORIG / REPLY。规则 ID 不作为观测对象身份的一部分；实际规则变化更新归因及累计边界，不重新创建该观测对象。

Rust 侧可以通过统一的观测存储逻辑消费两类记录，同时保留来源类型及语义区别。基础应用 / 规则计数在实际判定时更新一次，生成观测记录不再额外增加一次。完整条目键、归因消息形状、超时数值和容量策略仍待后续收敛。

### 21.14 计量独立性、分类变化与统一更新职责（交接后确认）

用户接受助手提出的第 1、2、3 项建议；第 4 项时间精度尚未收敛，用户随后转向窗口维护位置，见第 21.15 节。

1. **基础计量独立于历史导出。** 实际处理时维护的应用 / 规则计数不依赖记录是否成功导出，也不依赖 Flow 或阻止观测条目是否成功建立。Rust 消费中断或存储落后可以造成明确的历史缺口，但不能阻塞包处理；常态历史不以每条记录持久化确认为包处理前提。原建议同时包含 VPP 固定窗口独立于 consumer 的性质；如果改由 Rust 从 records 派生窗口，需要另行说明窗口对导出覆盖与时效的依赖，不能默称性质完全相同。
2. **当前对象描述与历史统计归属分开。** 接受以处理当时可用的应用、网络、协议事实计量、后续变化影响后续计量而不默认回填历史的起点；当前对象描述可以更新为最新已知事实。该原则不改变正常 Flow 的生命周期身份。原建议保留的 L7 问题仍需细化：早期未识别流量是否最终归入已识别协议、多协议结果如何分配，不能默认照搬规则归因的全部语义。阻止观测的完整身份键仍未冻结。
3. **封装统一更新职责。** 归因切换、旧归因累计边界、本包计入新归因及导出触发的正确顺序由小而完整的 Interface 承接，避免直接匹配、缓存、前置及后置路径分别拼装。FlowRuntime 继续拥有正常 Flow 生命周期；阻止观测保有独立生命周期；共用计量原则不要求继承体系、通用事件框架或冻结具体 C 布局。

这些是讨论共识，尚未更新正式领域文档或实现，也不意味着容量、计量点、消息字段、可靠性机制或分类细节均已确定。

### 21.15 固定窗口的产品目的与 Rust 后台维护可能性（重新讨论）

用户澄清：原先让 VPP 维护固定窗口，本意是让 UI 等调用方能直接查询结果，避免总是自行计算；并提出这是否也能由“前端”常态地根据 records 维护。这里仍按既有用语将“前端”理解为 Rust 应用侧整体，包含后台消费与存储，不限于 UI。

本次重新比较的是窗口维护位置，而非撤销四类预定义视图或 Flow / 阻止观测累计快照模型。持续维护可查询结果与由哪层维护是两个选择：Rust 后台可以随有效记录到达增量维护汇总，UI 读取已有结果；它不必等 UI 打开后全量扫描历史，也不要求 UI 自己聚合。

待比较的性质包括：VPP 在包处理时直接计量与 Rust 在记录到达后派生的时效、覆盖和时间精度；consumer 中断或记录缺口的影响；记录批次、唤醒、窗口过期与存储成本。累计快照求差不能凭空恢复区间内的包时间分布或丢失的分类边界；没有后续快照时也不能保证补回末尾累计量。只改变维护位置不自动解决这些问题。

本节比较时尚未决定更换维护位置；后续接受的方向见第 21.16 节。不能仅凭 UI 需要直接查询就推导维护层，也不能未经测量宣称任一方案更省电。第 21.14 节基础计量独立于导出的原则继续成立；派生窗口是否需要同等独立性是本次讨论的实质取舍。

### 21.16 常态窗口由 Rust 后台增量维护（后续确认）

用户接受上述建议，当前按 **Rust 后台根据观测记录增量维护常态窗口，UI 等直接查询已有结果** 的方向继续设计。这修正第 21.7 节的 VPP 窗口归属；四类预定义视图、累计快照导出、两类观测独立生命周期及配置 / 观测分库保持。

- **VPP 职责**：在实际处理时维护基础计数、观测累计量与归因，并按既定触发原则导出。基础计数不依赖观测记录成功导出，也不依赖每个包均有可用的 Flow 或阻止观测条目；消费 / 存储不得阻塞包处理。
- **Rust 职责**：后台消费两类观测记录，结合实例身份、累计差值和归因边界增量维护四类视图，并处理窗口随时间推进的过期贡献；与近期保存、长期汇总协调。后台职责不以 UI 打开为前提，不要求每次查询扫描完整历史。
- **调用方职责**：UI、CLI 等查询已经维护的结果；当前状态与基础计数仍可通过对应的实时读取能力获取，不把记录派生结果当成 VPP 全覆盖实时计数的替代品。
- **接受的取舍**：常态窗口受上报和消费节奏影响，接受记录级更新延迟，明确表达覆盖缺口。consumer 暂停时不承诺窗口继续实时完整推进；后续快照可以补回有依据的累计差值，不能凭空恢复区间内的时间分布、缺失归因或没有末尾快照的尾部量。
- **尚待细化**：时间分辨率、跨窗口边界分配、消息顺序 / 去重 / 缺口合同、消费批次与唤醒节奏、过期方式、容量及存储实现。接受归属和取舍不等于接受任意延迟、无界资源或具体参数，也不构成已测得的省电结论。

当前不要求 VPP 另维护同一套四类查询窗口。若后续出现明确需要独立于 consumer 的窗口能力，再按具体需求单独讨论，不预建两套等价窗口体系。这里仍是临时讨论共识，未实施或修改正式规格。

### 21.17 旧非 VPP 时间窗口设计的定向核对

用户接着询问旧版在累计快照与时间窗口方面如何设计。核对记录补入[旧版调查第 9.6 节](2026-09-15_OBSERVABILITY_LEGACY_RESEARCH.md#96-累计快照如何归入时间窗口旧契约的确定项与空白2026-09-23)。

早期 Flow Telemetry 规定 producer 输出累计快照、consumer 求差和承担聚合，但核对的契约未选择累计差值跨时间窗口时的具体分配方法，且前端持久化 / 查询库不在其 MVP 内。后期 SNORT-10 的 `60s` minute buckets 则由 daemon 直接按包更新，查询时合并为 trailing windows，不以 Flow records 为输入；这是另一次设计收口，不能当作旧 consumer 已实现的分桶算法。

第 21.16 节的 Rust 后台窗口方向继续有效。本次只补历史证据，没有选择当前的桶长、窗口时长、均摊 / 插值 / 落桶规则，也没有因旧资料重新改回 VPP 窗口。

用户进一步补充：Traffic Windows 当时应是因为前端每次计算太卡而设计。按这一回忆，当前必须保留的目的是持续预聚合与查询复用，避免每次页面刷新或时间范围切换都重新处理大量原始记录。现存旧文能够核实分钟桶和查询时合并的机制；本次没有找到该次卡顿的直接测量，具体瓶颈不作推定。

第 21.16 节的 Rust 后台方向包含增量维护，不能降格为把全量 records 计算移到 Rust / 后台线程后仍逐次重算。常用窗口应消费已经维护的汇总；查询时允许必要的有界桶合并或排行，但具体缓存、分桶和刷新算法尚未选择。用户这次补充没有重新指定窗口回到 VPP，也没有改变已接受的记录延迟与缺口语义。

### 21.18 常态统计与目标级历史的数据依赖复审（讨论中）

助手随后建议一次消费统一求差和归因、分别保留近期记录与汇总、按活动时间统计，以及消费进度与汇总一致恢复；其中提出将跨桶新增贡献计入区间最后活动时间所在桶。用户仅表示直觉上方向对，但感觉有坑，要求从更高层审视；不能将这组建议尤其是落桶算法记成已接受决定。

本次复审识别的核心问题是：**Rust 负责维护可查询结果，与全部常态统计只能由 Flow / 阻止观测累计记录重建，是两个不同的架构选择。** 后者已经作为第 21.16 节的讨论方向接受，但需要结合产品约束重新审视其依赖；接受延迟与明确缺口不自动等于已经确定可接受的误差范围。

- **覆盖与完整性**：基础计数独立于观测条目建立与导出，故 records 派生统计可能与同口径基础计数不一致。没有正常 Flow 或观测条目、整实例记录缺失、末尾快照缺失都不能仅靠相邻快照求差补全。总量差异不能直接按比例分配给应用 / 协议 / 规则。
- **时间信息与新鲜度**：当时仅包驱动上报不构成无包时的固定延迟上界，已有贡献可能要等后续包或生命周期结束才导出；用户后续在第 21.20 节补入时间驱动以处理这一空档。累计快照仍不包含区间内全部时间分布，不能据此精确恢复各桶。助手此前的末次活动时间落桶仅是未接受候选，不能将简单归桶当作问题已解决。
- **总体成本**：Rust 预聚合能避免 UI 反复全量扫描，但常态统计若依赖目标级记录完整消费，其生产、传输、实例状态、归因变化和存储成本仍然存在。为了窗口新鲜度增加导出、唤醒与持久化，可能逐步扩大手机常态开销；不能把查询不卡等同整条链路成本合适。
- **恢复范围**：消费进度与汇总一致只能解决本地重复 / 漏提交问题，不能恢复数据源从未导出或已丢失的事实。近期记录淘汰后，长期汇总也不天然支持重新归因或全量重建。

助手的复审建议是：保留 Rust 后台预聚合和直接查询的方向，重新判断四类常态视图是否需要独立于目标级记录完整性的统计输入；目标级历史仍保留已经接受的 Flow / 阻止观测累计模型。若需要基础计数或必要统计摘要作为独立输入，应共用实际计量语义，明确额外状态、导出和对照成本，不能把两路数值相加或宣称自动获得精确时间分布。

这不是已决定增加新记录类型、恢复 VPP 全套窗口或用粗汇总替代阻止观测。下一步应先明确常态统计与目标级历史各自的覆盖、新鲜度和完整性承诺，再选输入与时间归属；数据库、传输、桶长和容量保持未定。

用户随后仍表示感觉不自然，并未接受上述新增统计输入建议。助手再次检查推导后指出：本轮已经接受记录级延迟和明确缺口，不能仅因 records 派生统计不完全等同于 VPP 基础计数，就把独立统计链提升为必要架构。第 21.18 节揭示的信息限制仍成立，但尚不足以证明增加第二路统计输入的收益；该建议不再作为当前优先推荐，第 21.16 节继续作为讨论基线。

后续应分别讨论三种性质：计量正确性（已消费的贡献不重复、归因有依据）、覆盖完整性（已经接受可见缺口）、时间精度（仍未定义）。不能用完整性不足推定已有数据必然计错，也不能用接受缺口来默许任意时间分配。当前不再追加模块或通道，先明确四类视图的时间含义，再判断输入信息是否足够；末次活动时间落桶仍未接受。这里是助手对建议的修正，不声称已经确定用户感到不自然的具体原因。

### 21.19 导出消息、消费状态与保留形态（讨论中）

用户同意先讨论一次观测更新消费后哪些信息需要继续存在。助手提出按保留目的区分：消费中的观测状态（求差和归因所需基线）、近期观测概况（目标级近期查询）、统计汇总（四类常态视图及长期查询）。这些是职责分类，不要求独立数据库或新增进程。

助手建议普通累计 UPDATE 用于推进同一对象状态和统计，不逐条永久保存；近期保留观测概况及必要的轻量归因段，同一归因段内只更新累计贡献。仍在使用的求差基线不能随近期明细保留期一同删除；近期观测淘汰后，已形成汇总独立保留；持久化后的消费进度和汇总需要一致恢复。用户后续在第 21.21 节确认消息合并与状态推进，并补充 END 后延后完全压缩的要求；完整归因段存储形状、落桶规则、恢复算法或每条消息同步落盘仍未冻结。

用户随后针对仅包驱动上报的前提作出修正，见下一节。

### 21.20 增长阈值与低频时间驱动上报并存（用户明确补充）

用户明确：除了包驱动，可以有不激进的时间驱动，融入当前框架，类似 session 删除时内部“假包”的调度思路。常态不能每包都写一条消息；达到次数 / 增长阈值，或距上次上报经过一定时间，才上报累计更新。这修正第 21.9 节仅在新包到达时检查上报间隔的限制。

当前方向是包处理维护计量，增长条件与时间条件共同决定何时导出累计快照。时间驱动让已有未上报变化在没有下一包时也能被处理，不必等待 Flow 生命周期结束。累计总量继续保留，不在导出后清零；创建 / 结束及归因变化的必要语义继续存在。时间阈值、批次预算、物理消息合并与队列策略未定。

本次只读核对当前 C 主线，确认已有接入基础：

- [Expiry driver](../../src/product/vpp/product_flow_expiry.c) 使用每 owner 的 one-shot timerfd，经既有 worker file polling 唤醒内部节点，再在 owner 上有界处理到期工作；到期清理不依赖下一包。
- [FlowEnd 契约](../decisions/VPP_PACKET_METADATA_OWNERSHIP.md#flowend-overlay--2026-09-12)及 [flow consumer](../../src/product/vpp/product_packet_graph.c) 使用零 payload 内部 END buffer 进入共享 consumer，跳过真实包的 parser、policy 和网络发送；END 还承担 entry 结束与最终回收职责。

助手据此建议沿用 owner 调度方式：由当前 owner 批量处理到期的待上报观测，优先复用现有唤醒 / 图调度基础；不因此为每个观测增加线程或系统 timer。是否需要独立内部更新信号、如何组合不同 deadline，留在具体设计中。

观测更新与 FlowEnd 必须区分：更新不 unlink、不回收 Flow、不推进 CT、不刷新真实活动时间，也不修改协议过期时间。阻止观测同样可以按这一上报原则设计，但仍有独立身份及超时生命周期，不能为了时间驱动创建 CT FlowEntry。

助手建议只对尚有未上报计数或归因变化的对象安排更新；没有新增变化时不重复发送相同累计值。普通增长可合并，必要归因边界需在变化时保存，物理发送可以合批，不能仅以最后一个归因覆盖尚未导出的前段。这里没有选择缓存结构或承诺无限保留边界。

本次仅更新临时讨论记录；现有 Expiry / FlowEnd 的实现不等于观测时间驱动已经实现或验收。时间驱动可以缩短尾部增量的等待，但不自动确定窗口精度、消除记录缺口或保证任意负载下严格准点。

### 21.21 非阻塞发送、复合状态更新与 END 后近期保留（用户明确修正）

用户对上一轮四点作出明确回应：

1. **VPP 只负责非阻塞发送。** 不等待 Rust 确认读取、消费或落盘，不因消息传递或 consumer 状态阻塞 VPP。此前“成功导出”仅能指本地提交语义，不能扩展成端到端确认或可靠重传协议；通道失败 / 丢失按既有有界观测原则处理。
2. **一条消息可以同时表达多种变化。** END 可以携带尚未上报的包数、字节增长及相关状态，合在一次消息中发送；不能要求先发 UPDATE 再发独立 END，也不能因为标为 END 就忽略其新增计量。这不冻结消息布局，也不要求每种变化对应一个顶层消息类型。
3. **Rust 的合并不能绕过状态更新。** 一次有效观测更新要同时处理相对既有状态的计量贡献、必要归因和生命周期变化。普通增长可以折叠进同一近期概况，但不能只相加数值而丢失状态。消息没有新增流量时仍可能有有效状态变化，END 也不能提前删除求差所需状态而漏掉尾部贡献。
4. **FlowEnd 不立即触发有损的完全合并 / 压缩。** END 后可以先合并整理，但因仍涉及近期窗口，已结束流的信息应继续保留一段时间，再完全汇总或压缩。结束表示 VPP 运行对象退役，不表示 Rust 已不需要其近期时间与归因信息，也不要求 VPP 为 Rust 保留运行对象。

助手据此建议区分两种处理：同一观测、同一统计粒度下不丢信息的折叠可以及时进行；会降低时间粒度或丢弃对象 / 归因细节的压缩，等待近期保留条件满足后再做。窗口在消息消费时就增量推进，延后的是细节淘汰与降粒度，而非推迟统计更新；压缩也不能再次把已计入的贡献加入窗口。

相应的 Rust 保留过程可表述为“活跃观测 → 已结束但近期保留 → 较长期汇总 / 压缩”。具体保留多久、从哪个时间基准计龄、近期窗口与空间上限怎样协调、细粒度贡献以何种结构保存、迟到 / 重复更新及重启恢复如何处理，仍待后续设计。这里没有承诺任意时间查询都能精确重建，也没有选择数据库、格式或容量常量。

### 21.22 观测生命周期与统计数据年龄分开管理（当前采纳方向）

用户同意先按本节方向继续。它是当前设计起点，不冻结具体数据结构、时间参数或压缩算法。

**观测对象按生命周期管理，统计贡献按数据年龄管理，由同一次消息消费共同推进。** Rust 需要保留的内容按用途区分为观测概况、必要归因信息，以及按时间组织的统计贡献；这些可以共用存储结构，不意味着新增统计输入链、独立数据库或进程。

- 窗口继续查询已维护的汇总。END 后保留观测信息，不使查询退回遍历大量 Flow 或原始消息后全量重算。
- 合并普通消息可以去掉重复快照，但不能只剩 Flow 的最终总量，从而过早丢弃已获得的时间区别；在选定的统计精度下，贡献可以及时合并入应用、协议、规则等时间汇总。
- 长时间活跃的 Flow 不必拖住全部早期细节：较早的统计贡献可以按保留策略逐步转为粗粒度汇总，后续求差、归因和状态推进所需的小份活跃状态保持。
- 刚结束的 Flow，其近期贡献仍留在细粒度保留范围内；观测概况与必要归因信息继续保留，满足近期保留条件后再完全合并、压缩或淘汰。已形成的较长期汇总独立存在。
- 普通增长可以折叠，影响解释的应用、协议、规则变化及结束状态必须参与相应处理；不因消息合并或记录没有新增流量就跳过状态更新。

这里保留的是来源实际提供、当前统计口径能够表达的信息，不凭累计快照推导不存在的逐包时间分布。本节确认时尚未选择具体时间分配和压缩默认；用户随后在第 21.23 节授权先取一组默认，因此以该节作为初版起点。迟到 / 重复 / 重启处理与具体存储实现仍需落实。

### 21.23 时间精度、保留与汇总的初版默认（用户授权选择）

用户明确要求这些细节先取一组默认，初版之后再调整。以下为据此选择的工程起点，不是测得的最优值、永久产品硬上限或新的实施授权；不再为选择这些初始数值反复请求确认。

| 项目 | 初版默认 |
| --- | --- |
| 近期统计 | 1 分钟粒度，保留最近 48 小时 |
| 中期统计 | 1 小时粒度，保留到数据年龄 30 天 |
| 长期统计 | 1 天粒度，保留到数据年龄 180 天 |
| 已结束观测概况及必要归因细节 | Rust 首次处理 END 后保留 24 小时；重复 END 不延长保留期 |
| 常态观测持久化空间预算 | 256 MiB；时间与空间任一先到即触发保留处理，可由后续设置调整 |

**时间归属默认：** 先依据有效累计边界和归因信息确定新增贡献，再按该贡献最后活动时间归入分钟桶。END 的发送 / 接收时间不能代替最后活动时间；一条消息中若有不同归因段，应分别处理。跨桶差值初版不做时间均摊或插值，因此属于近似时间统计：保留有依据的总量与归因，不宣称恢复逐包时间分布，时间偏差也不保证仅一个桶。此前未选定的末次活动时间归桶，在本节明确转为用户授权下的可调整默认；已知归因缺口仍按缺口表达，不将无法归属的全部差值硬记给最新规则。

时间桶先按 UTC 整分、整点及整日对齐；日桶为 24 小时，时区只影响显示，不改变已存统计。VPP 增长 / 时间上报与协议超时继续使用单调时间；将源活动时间映射到历史时间轴及处理时钟变化属于后续具体合同，不改变以上初版精度选择。

**汇总算法默认：** 相同既定分类内，将完整分钟桶的包数 / 字节数求和为小时桶，再将完整小时桶求和为日桶；方向、应用、协议、规则等各视图的分类语义保持。比例与排行根据合并后的计数派生，不平均已有百分比。后台分批推进，查询使用已维护结果；同一贡献在一次查询中只取一个时间层，归并不重复增加业务计量。分钟 / 小时 / 日层的保留期限均以数据年龄计算，不是每次压缩后重新获得完整保留期。

降粒度时先形成可用的上层汇总，再淘汰对应下层贡献；END 后的对象概况淘汰不撤销已经形成的统计。活跃对象可压缩早期贡献，但后续求差与状态推进所需基线继续保留。

**空间处理默认：** 先清理过期数据；仍不足时优先淘汰最旧的已结束对象细节，再提前归并最旧的细粒度统计，最后缩短最旧汇总的保留范围。实际覆盖范围随之明确缩短，不伪称仍有完整的默认保留期。不能通过删除活跃求差基线后把下次累计量重新从零计入来节省空间。256 MiB 为常态观测的持久化预算，需将索引及维护日志计入实现预算并预留整理空间；不是 VPP 内存池或配置资产库额度，按需 debug 的预算另属其采集设计。

具体编码、数据库、整理批次、崩溃一致性与迟到记录处理在实施设计中落实；不为了这些默认值另建压缩框架或重做记录通道。本轮只将默认值写入讨论记录，尚未修改正式规格或产品实现。

### 21.24 KISS 与简单消费原则（用户再次明确）

在助手提出观测身份、消息顺序、缺口及重启语义后，用户明确要求遵守 KISS，不能阻塞 VPP，Rust 消费侧保持简单，按当前原则继续。不能由“恢复 / 顺序需要正确”扩展出复杂可靠消息体系。

- **VPP**：只做有界、非阻塞的观测导出；通道不可写按既有丢失 / 健康语义处理，不等待 Rust 读取或落盘，不引入确认、补发握手或因消费侧状态重做包处理。
- **Rust**：初版采用单一、明确的消费流程，根据最小观测身份与更新状态，统一推进累计差值、归因、生命周期和汇总；END 同时处理尾部贡献，然后进入近期保留。不预建多消费者协调框架。
- **必要正确性**：保留防止实例混淆、重复计量、累计量倒退及旧 UPDATE 使已结束实例复活的最小状态；这些是消费逻辑，不是端到端确认协议。缺口明确后继续处理有依据的信息，不猜补未知规则贡献。
- **异常范围**：消费中断或运行截断保留已知信息，并作必要的不完整标记；不为追求完整历史建立复杂乱序重排、事件重放或跨层对账恢复体系。Rust 本地状态与汇总的一致推进仍需保证，但不向 VPP 施加等待。

本节收敛复杂度原则，不冻结字段位宽、传输设施、具体线程布局或数据库事务形状。工程细节按这些简单职责继续落实，不将每个低层选择重新提交用户讨论；仍不构成本轮开始产品实现的授权。

### 21.25 统一计量口径（用户确认）

用户接受以下常态计量方向，作为四类视图共用的语义：

- **单位与覆盖**：按共享策略路径看到的 IP 包计量，字节采用 IP 层报文长度，包含 IP 头；重传再次经过计量点时再次计入。不将它解释为运营商计费或应用去重后的有效载荷。内部 handoff、数据拷贝、定时信号和 FlowEnd 不增加业务流量；重组后的策略计量与 Adapter 原始分片接收计数分开。
- **结果分类**：最终 Policy ALLOW 计入允许量，最终 Policy DROP 计入阻止量。解析、容量、转发等运行故障保留对应健康信息，不伪装成规则阻止。策略允许不证明送达；阻止字节表示被阻止包的大小，不直接称为节省的流量。
- **规则命中**：按当前包的最终逻辑赢家增加一次命中及对应字节；直接匹配、缓存命中、前置与后置执行共用口径。内部候选、OR 多条件或因子化片段不额外计命中。无规则赢家的默认 ALLOW 不伪造规则命中。
- **observe 模式**：按既有有效模式解释实际结果。声明 DROP 但以 observe 模式生效的赢家仍可增加该规则命中与对应流量，而实际策略为 ALLOW 时增加允许量、不增加阻止量。
- **观测对象与计量分开**：正常 Flow 也可以包含后置 DROP，前置 DROP 由独立阻止观测承接；两类对象承接不同包，共用计量原则。计量在真实包处理时更新，导出、消费、压缩不再产生一次业务命中。

本节不把当前源代码中的已有累计字段认定为已经完成上述全路径接入，也不改变前置 DROP 不进入 CT 的约束。

### 21.26 L7 多个识别结果全部计入（用户确认及示例）

具体协议目录映射、结果可用性及消息编码另按既有识别合同落实；本次只收敛统计语义，没有增加重新识别、重跑策略或回填历史机制。

### 21.27 按需 debug 与常态记录的通道关系（讨论中）

助手建议 debug 显式、短时、按应用 / UID 聚焦，记录实际判定过程，不重新运行规则，不改变缓存路径，不为前置 DROP 创建 CT，也不通过 debug 记录再次增加业务计量。VPP 输出结构化事实和执行时的规则引用；Rust 消费、解释及保留诊断信息。停止、超时或消费会话结束后释放重诊断状态。上述是讨论建议，不直接继承旧固定 stages、tracked 持久开关、JSON 格式或命令面。

用户指出旧非 VPP debug 使用另一条通道，询问当前建议。已有[旧版调查 §9.3](2026-09-15_OBSERVABILITY_LEGACY_RESEARCH.md#93-普通与-debug-不共用-payload-通道不能据此断言必须两个-socket-或已共用数据库)确认：普通 records 走共享内存 ring，旧 tracked debug 经进程内队列生成 JSON / netstring socket 载荷；控制设施共用不代表普通与 debug 共用 payload 通道。

**助手建议保留两条独立、有界的数据通道，同时复用传输实现与 Rust 后台。** “复用基础设施”指共用接入、编解码和消费框架，不把 debug 大量详细记录混入普通累计快照的同一 FIFO 容量中。

- 常态通道承担 Flow / 阻止观测累计更新及状态变化，有自己的容量与处理份额。
- debug 通道按诊断会话启停，有独立缓冲额度、消费 / 写入预算与丢失计数。debug 拥塞时在自身预算内丢弃并标记缺口，不占用常态通道的保留容量，不让 VPP 等待。
- Rust 由同一个后台统筹消费，两路按类型处理；不因此默认增加进程、独立服务或复杂消息代理。初期曾建议优先保障常态处理份额，用户后来在第 21.31 节明确开启 debug 后正确性与故障定位优先，具体资源安排应保障诊断证据充分性，不以常态性能目标压缩必要细节。通道容量隔离不等于 CPU / 存储完全隔离，详细解码及写入仍需有界批次。
- 诊断开关沿现有控制职责接入，控制命令与大量诊断 payload 分开。按第 21.35 节修正后的职责，普通记录进入观测记录库，debug 数据由本次调试会话临时管理；共用 Rust 后台不要求两路都长期持久化，配置资产库职责不变。
- 低层可以复用同一种有界记录传输实现；不要求重建旧版“一套共享内存 ABI 加一套 vNext JSON stream”的组合。独立通道不必机械等同于两个 OS socket，具体 buffer / socket / ring 接线尚未选定。

本节没有实现或选定新协议，也未将单应用诊断、具体会话时长或通道容量记为已确认产品常量。

### 21.30 通道讨论收口，转入详细诊断的内容（讨论中）

### 21.31 debug 追踪包的完整动作链，正确性与故障定位优先（用户确认）

后续范围说明：第 21.36 节将 debug 具体设计后置，并提出未来模拟 / 预览也是可能用途。本节描述实际路径追踪的目标，不等于 debug 只能有这一种模式。

用户接受前述详细诊断方向，并明确：debug 要能追踪对包执行的每个动作。开启 debug 的原因是已经发生故障，此时解决故障最优先；正确性优先，性能不再是首要目标。

据此，debug 的目标是**在采集范围内还原包从进入到退出本产品处理范围的完整实际动作链**。覆盖实际经过的处理动作、输入与状态变化、选择依据、结果及失败原因，不能只保留最终策略摘要。开启后可以接受更高的 CPU、内存、记录量与处理开销；优化必须先保住所需的诊断信息，不默认以抽样、只留赢家或省略中间动作换取常态级性能。

助手据此归纳需要覆盖的动作类别，作为后续设计检查范围，而非固定 stage 或已实现能力：

- 接收、解析及必要的包转换 / 修改；相关输入值与不可用原因。
- owner 分流 / handoff、Flow 查找 / 创建及相关状态变化，含无 Flow 的提前阻止路径。
- 识别事实的生成、变化或失败，缓存查找、命中 / 失效及当次实际使用的决策依据。
- 实际执行的规则检查、条件结果、短路 / 跳过与逻辑赢家；能关联编译结构与来源规则。
- 允许、阻止、旁路、转发 / 提交及实际可观察的完成或失败，不把策略允许解释为远端送达。

完整动作追踪要求能按同一个包串联记录；跨 owner、跨模块或异步动作，以及实际发生的分片 / 重组 / 派生，应保留解释所需的关联，避免只产生无法对应的散点日志。关联方式与消息布局由后续设计落实，不在这里冻结追踪 ID 或一包一消息。

正确性包括忠实于实际执行：未执行的条件不能标成 false，缓存复用不能伪装成重新求值；不把另行重跑的结果冒充该包当时的经历。采集范围生效前的动作没有证据时应明确不可回溯。规则版本与运行上下文应支持解释当时的行为，不以最新配置覆盖历史含义。

已有通道约束继续有效：普通 / debug 独立有界，VPP 不等待 Rust 消费或落盘。性能退居其次允许为诊断增加资源和处理开销，不等于取消记录真实性或隐瞒容量不足；若确有溢出、截断或丢失，应明确标出轨迹不完整。正常情况下的设计目标是完整采集所选范围内的动作，不将缺口当成主动省性能的默认手段。

本节收敛 debug 的产品目标和取舍优先级，未开始采集实现或实验，也未冻结采集范围选择、字段、预算或规则历史保留结构。

## 26. SNI 规则的协议适用前提与确定缺失（2026-09-24 用户明确）

用户先明确区分：暂时没有解析完成、拿不到 SNI 时，依赖该 SNI 输入的条件不能据此成立；取得确定解析结果，包括确认没有 SNI 后，相关条件才可以正常参与匹配。确认无 SNI 是一个可用结果，不等同于尚未取得结果。

随后用户进一步明确：**含 SNI 条件的整条规则，必须在流已识别为 TLS / QUIC 后才执行匹配。** 这是整条规则的协议适用前提，不只约束某个 SNI 子条件；条件使用 AND、OR 或 NOT 都不能绕过它。协议尚未识别或只识别为普通 DNS 等其他协议时，该规则不参与匹配，不能把未适用 SNI 解析当成“确认无 SNI”。已发布的协议结果包含 TLS 或 QUIC 即可，不要求完整识别过程结束。

例如 `NOT（SNI 域名属于 example.com）→ DROP` 的语义是先满足 TLS / QUIC 适用前提，再计算该否定条件；不能将协议前提放入 NOT 内，把其他协议也算成命中。用户不必为每条 SNI 规则手动补写此前提；具体配置展示和编码尚未选择。

在上述协议前提成立后，以本版 SNI 域名条件 `域名属于 example.com` 及其 NOT 为例，结合既有布尔语义，结果如下：

| 当前事实 | 域名属于 example.com | NOT（域名属于 example.com） | 确认无 SNI |
| --- | --- | --- | --- |
| 尚未得到确定解析结果 | 不可用，不能据此命中 | 不可用，不能利用 NOT 命中 | 不可用，不能据此命中 |
| 已取得有效 SNI，且属于指定域名范围 | true | false | false |
| 已取得有效 SNI，但不属于指定域名范围 | false | true | false |
| 正常解析完成并确认没有 SNI | false | true | true |

因此，对此前讨论的 `NOT（域名属于 example.com）→ DROP`，尚无确定结果时不能凭该条件命中；确认无 SNI 后该否定条件成立。整条规则是否获胜及实际动作仍遵守完整表达式、Rank 和有效模式，不因确认无 SNI 自动新增全流 ALLOW / DROP。

用户随后同意直接支持“确认无 SNI”作为普通规则条件，例如 `确认无 SNI → DROP`。该条件同样要求流已识别为 TLS / QUIC；在取得有效名称时为 false，仅正常解析确认缺失时为 true。它与“域名不属于某名单”不同：一个存在但未列入名单的名称不会满足“确认无 SNI”。条件继续参与既定布尔组合、完整排序和有效模式，不新增特殊动作路径；具体操作符拼写、字段编码和 UI 控件留工程 / 交互设计。

这里的“确认没有”必须来自有效的解析结论。解析失败、未执行、数据不足、超时或预算耗尽本身都不能替代这一结论；未取得的事实继续按第 25 节保持不可用，已有可用事实保留。取得有效 SNI 后即可按既有流程发布，不要求等待全部 LPI 过程结束。

第 3.3 节的布尔组合语义在规则协议适用前提成立后继续有效；此前“OR 的其他分支可以成立”的表述不能被用于让非 TLS / QUIC 流量匹配含 SNI 条件的规则。本节不要求扣包等待识别或解析，当前不适用的规则不妨碍其他适用规则按既定 Rank 竞争。

编译规划、缓存依赖及测试参考求值均须包含该协议适用前提。从未识别到已发布 TLS / QUIC，以及 SNI 从不可用变为有效名称或确认无 SNI，都属于影响匹配的事实变化，须由第 8 节既定缓存守卫覆盖；不能仅因前后都没有名称字节而复用旧结果。

本节确认匹配行为及直接表达确定缺失的能力，不冻结字段编码或新的 UI 状态配置。本轮仅更新临时讨论记录，未修改正式规格、产品实现或执行测试。

## 27. 同一逻辑规则的不同版本与历史解释（身份与常态历史解释已收口）

本节保留方案比较过程；第 27.6 节是用户接受的标识工程起点，第 27.8 节是已确认的常态历史解释范围。第 27.1—27.5 节中的双 UUID、24 字节、32:32 和快照短引用提案不作为已采纳设计。

SNI 行为收口后，助手继续询问常态历史是否需要始终保留当时完整规则条件及引用名单内容。用户提出一种身份方案：规则修改后唯一标识变化，但标识的前一部分保持不变，类似 IP 地址前缀；用户仍看到同一条规则，本地可区分其变化前后的版本，并询问这是否过度设计。初次提出时尚未确认具体编码或历史保留方案；后续身份选择见第 27.6 节，历史解释范围见第 27.8 节。

助手建议将该思路表述为“稳定的逻辑规则身份 + 具体版本身份”。例如展示为 `R42@v1`、`R42@v2`：`R42` 关联同一用户规则，各版本对应各自内容。两部分可以是两个字段或组合标识；当前需求无需定义 IP 式前缀长度、掩码或层级分配协议。版本化本身可以保持简单，具体是否需要独立的逐规则版本号还需结合现有完整策略快照身份决定。

身份设计与历史保存分别解决两件事：版本引用说明“当时用了哪一版”，只有对应内容仍被保留时才能还原“那一版是什么”。区分版本不自动意味着保留所有旧定义、名单或完整配置；同一逻辑规则在 UI 中如何展示跨版本统计也没有在此冻结。

落实时需保持已有边界：

- 本轮完整 Rank 的稳定规则身份不因内容版本变化而改变；不能直接用变化后的整段版本标识替换排序中的稳定 `ruleId`，造成编辑引发额外顺序变化。
- 观测继续关联实际使用的完整策略快照；引用名单、组 / 绑定及有效模式也可能改变执行含义，单条规则文本的版本不能独自代替这些上下文。
- 现行 CONTEXT 中历史 `ruleId` 定义不保证跨所有 Apply 稳定；当前 typed bundle 则已有规则引用和整份策略快照身份。新身份职责须在正式整理时映射清楚，不能声称现有代码已经具备逐规则不可变版本与完整历史查询。

以上保留初次分析过程；用途核对和比较后，标识格式按第 27.6 节工程默认推进，常态历史解释按第 27.8 节范围落实，具体版本形成时机与存储接入留工程设计。继续保持讨论状态，不修改正式模型或开始实现。

### 27.1 标准唯一标识建议（资料已核对，双 UUID 方案未采纳）

后续修正：用户在第 27.2 节表示不倾向两个独立标识。本节双 UUID 方案未被采纳，保留标准与库资料供后续选择。

用户进一步要求采用更明确的唯一标识，并询问成熟选择。助手核对 RFC 9562 与 Rust `uuid` 库文档后，建议两个身份均采用独立生成的 UUIDv7：

| 身份 | 建议职责 |
| --- | --- |
| `RuleId` | 一条逻辑规则的稳定 UUID，修改同一规则时保持不变 |
| `RuleVersionId` | 一个具体规则版本的 UUID，形成新版本时生成，并关联所属 `RuleId` |

UUIDv7 是 RFC 9562 定义的 128 位格式，包含毫秒时间戳及随机 / 可选单调性部分，适合按字节排序与数据库索引。UUIDv4 也是标准选择，采用随机生成而不带时间排序；本项目倾向 v7 属于助手建议，不是本地性能验证结果。[RFC 9562 §5.4](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.4)、[§5.7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7)、[§6.11](https://www.rfc-editor.org/rfc/rfc9562.html#section-6.11)

两字段表达“固定规则身份 + 可变版本身份”；需要组合引用时可写成 `RuleId/RuleVersionId`，不截取、固定或重写 UUID 内部位段来编码父子关系。UUIDv7 的时间前缀不是业务规则前缀，UUID 格式版本号 7 也不是规则修订号。UUID 的大小不决定实际生效版本，仍以已发布策略快照为准。[RFC 9562 §6.12](https://www.rfc-editor.org/rfc/rfc9562.html#section-6.12)

Rust `uuid` 库已有 `Uuid::now_v7()`，可在控制侧复用；持久化时保留唯一性约束。当前仓库 Cargo 清单 / 锁文件核对未发现该依赖，本轮未添加依赖或验证目标端接入。[库文档](https://docs.rs/uuid/latest/uuid/struct.Uuid.html#method.now_v7)

这仍是待确认的身份方案，不决定版本形成时机、旧定义 / 名单保留范围或 VPP 热路径字段布局；已有完整策略快照身份继续用于实际执行上下文。

### 27.2 VPP 标识支持与单一复合标识（上游用途已核对，长度未定）

用户询问 UUIDv7 在 VPP 中能否顺畅使用，并明确不太想使用独立的 `RuleId` 与 `RuleVersionId`。助手据此修正双 UUID 建议，转向单一复合标识。用户随后比较 24 字节、64 位与 16 字节的区别，先表示可以采用 24 字节并询问 VPP 的实际用途，随后明确要求“先确认核对 VPP 中这种键的实际用途再决定”。以最新要求为准：固定 UUIDv7 前缀（16 字节）加无符号修订号（8 字节）仍为候选，不记为已确认选择。

源码核对：VPP `bihash_16_8` 的键为两个 `u64`，提供 16 字节哈希与完整键比较；`bihash_24_8` 的键为三个 `u64`，提供对应的 24 字节操作。控制侧生成 UUID 后，VPP 可将其作为固定长二进制数据处理，不要求逐包生成 UUID 或转换文本。此处说明基础数据结构可承载，不代表本产品已接入 UUID 或测得性能无影响。[VPP 16 字节键](https://raw.githubusercontent.com/FDio/vpp/master/src/vppinfra/bihash_16_8.h)、[24 字节键](https://raw.githubusercontent.com/FDio/vpp/master/src/vppinfra/bihash_24_8.h)

本项目当前 [L4 规则源结构](../../src/product/vpp/product_l4_policy.h:80)、[typed API](../../src/product/vpp/product_core.api:260) 及 C / Rust ABI 的规则引用仍为 `u64`。采用更宽身份需要一致更新接口或设计明确的运行时映射，不能直接把 UUID 截断塞入现有字段；本轮不选映射布局、不修改接口或运行实验。

当前候选是一个完整的 `RuleIdentity`，内部由 **固定 UUIDv7 前缀（16 字节）+ 无符号修订号（8 字节）** 组成，总长 24 字节。规则创建时生成前缀；同一规则形成新内容版本时使用未用过的修订号。整体比较标识具体版本，固定前缀关联同一逻辑规则；这是一个结构化标识，不需要第二个独立生成的 UUID。若采用，修订号分配须持久化且不复用，不以截断、回绕或恢复旧内容为理由让相同完整标识对应不同内容。

完整 24 字节值是产品复合标识，只有其中固定的 16 字节部分是标准 UUIDv7。UUIDv7 内部的时间字段不能改作规则家族前缀并仍宣称沿用标准生成语义。若要求整个复合标识限制为 128 位，需要另行权衡编码和唯一性；此处不提前选择自定义 UUIDv8。UUIDv8 允许自定义格式，但唯一性由具体设计负责，不因为使用版本号 8 就成为现成的版本化规则身份标准。[RFC 9562 §5.7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7)、[§5.8](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.8)

该候选保留固定前缀不影响排序、完整策略快照解释实际执行上下文、历史内容按独立保留决策管理的边界。长度与组成仍待用户在用途核对后选择；版本分配时机、二进制序列化与具体接入也未冻结。VPP 自带相应键类型不意味着本产品必须新增一张身份哈希表。

按用户要求进一步核对该能力在 VPP 内的实际用途。核对上游现行源码可见，`bihash_24_8` 是 **24 字节键 → 8 字节值** 的通用哈希表变体，键结构为 `u64 key[3]`，值为 `u64 value`；名称中的 `8` 表示查表结果长度，不是键内部的修订号。它提供按完整键的查找、增删和比较，不负责 UUID 生成、业务版本分配或历史保留。

| VPP 使用处 | 24 字节键的组成 | 查找结果 |
| --- | --- | --- |
| IPv6 FIB 转发表 | 掩码后的 IPv6 前缀（16 字节）+ FIB 索引 / 前缀长度（组合为 8 字节） | 转发对象索引 |
| 传输层本地端点表 | IP 地址（16 字节）+ FIB 索引 / 端口 / 协议（组合为 8 字节） | 端点索引 |

依据：[IPv6 FIB 更新](https://raw.githubusercontent.com/FDio/vpp/master/src/vnet/fib/ip6_fib.c)、[传输端点查询](https://raw.githubusercontent.com/FDio/vpp/master/src/vnet/session/transport.c)。本地参考 fork 的对应端点键尚不含 FIB 索引，表中按核对的上游实现描述，不能混称所有版本布局完全相同。

本产品当前提案是 24 字节规则版本身份；VPP 已有的是能承载这种长度的查表基础设施。若后续确需按身份查规则元数据，可据实际接入复用；这不将身份索引等同于按 IP / 端口 / 协议等条件匹配数据包的规则索引，也不构成当前产品性能或端到端接入证据。

### 27.3 消息体积与本地 64 位标识候选（用户认为 32:32 仍过大，未采纳）

用户指出 24 字节太长，每次写消息都会重复占用空间；产品定位为个人设备，规则规模达不到十万、百万量级。助手据此撤回将保留完整 UUID 作为长度选择的优先理由，改为先考虑实际唯一性范围与导出成本。VPP 存在 24 字节哈希键，不构成产品必须采用该长度的理由；原方案未被确认。

消息数量与规则数量分开核算：同一规则身份会被多次导出。从每份完整引用 24 字节降到 8 字节，每份少 16 字节；一百万份引用相差 16,000,000 字节，约 15.26 MiB。这里只计算标识字段的原始差值，不是现有产品实测消息数量、传输开销或存储压缩率。

助手的新建议以“同一配置库内唯一”为前提：使用一个 64 位复合值，高 32 位为稳定逻辑规则编号，低 32 位为修订号。稳定编号由控制侧持久化递增分配，不采用 32 位随机数或截断 UUID；形成新内容版本时递增修订号，已使用的完整值不再对应不同内容。两部分都保持有界且不回绕，实际分配与恢复合同待后续落实。

该候选保留用户要求的固定部分与变化部分，并且没有第二个独立 UUID。32 位稳定编号的编号空间远大于当前预期规则规模，但须管理累计分配与历史引用，不能仅凭活跃规则少就复用旧编号。它是本地复合标识，不称作 UUID，也不自动保证跨独立配置库或跨设备全局唯一；是否需要这种全局身份保持，尚待用户明确。

VPP 也提供 `bihash_8_8`，键和值各为一个 `u64`，可复用已有的 8 字节键操作。当前产品接口本来使用 `u64`，但新的内部位段语义、排序中的稳定部分及历史引用仍需接入，不将宽度相同当成新方案已经实现。[VPP 8 字节键](https://raw.githubusercontent.com/FDio/vpp/master/src/vppinfra/bihash_8_8.h)

本节仅记录约束与待讨论候选，未采纳 64 位布局，也未改变跨设备导入 / 恢复语义；下一项需明确唯一性应覆盖单一配置库还是独立设备 / 配置库。旧版本内容保留仍是另一项未决问题。

### 27.4 较短标识、文本形式与生成方式（继续讨论，未确认）

后续澄清见第 27.5 节：用户允许内部递增修订，主要关注外部身份在全量导入时不能冲突；不能继续将该需求仅解释为字母数字显示偏好。

用户进一步认为 32:32 仍然过大，指出不太可能一次修改很多版本，并表示标识最好不是数字，要求继续讨论。该反馈不等于已经选择新的位数，也尚未回答跨库 / 跨设备唯一性的范围。

助手建议先分清文本形式与内部生成方式：可在配置展示、日志等位置使用字母数字短码，而 VPP 与普通消息保留紧凑二进制；Base32 等成熟编码负责二进制到文本的表示，不单独提供唯一性或规则版本语义。[RFC 4648 §6](https://www.rfc-editor.org/rfc/rfc4648.html#section-6)

“不是数字”仍需明确是避免纯十进制流水号的外观，还是连内部版本生成也不希望使用递增序号、倾向随机标识。两者会影响不同的设计选择；当前不把用户表述直接解释为要求 VPP 传递文本字符串，也不提前选择随机短后缀、内容哈希或新的位段分配。

版本位宽后续还应区分累计修改次数与同时保留的版本数量；需要被历史引用的标识不能指向另一个内容。该正确性边界不预设很大的版本容量，实际长度继续按本项目需求收敛。

### 27.5 全量导入身份与消息引用的分工（需求澄清，短引用提案未采纳）

用户澄清：内部版本号的形式可以灵活选择，只需能看出递增顺序；外部规则身份若只使用单调递增编号，担心全量导入不同版本时 `rule-id` 重复，同时需要兼顾 msg 效率。这使讨论重点从文本外观转为导入身份的唯一性与消息表示成本，不能仅用 Base32 编码解决，也不能继续默认本机自增编号足以满足导入需求。

沿用此前同一逻辑规则固定部分不变、内容版本变化后完整标识变化的意图，助手建议配置侧保留足以识别来源和版本的完整身份；不假定各次导入从 1 编号就能直接合并。具体全局标识格式、同一份内容重复导入的处理、不同来源冲突及旧内容保留范围尚未定案。

为控制高频消息成本，助手提出可在发布后的策略快照内为规则版本分配短引用，消息通过“对应快照上下文 + 短引用”指向完整身份；例如不同快照中的索引 17 可以映射到同一规则的不同修订。短引用是当前快照内的运行表示，不是新增一个独立持久规则身份。若采用，配置发布过程提供相应映射，旧消息必须使用对应旧映射解释，不能取最新表猜测；映射的有界保留和消息消费衔接须与既有快照 / 观测合同一起落实。

这一建议尚未确认。短引用可以按实际容量采用紧凑整数，具体位宽不在此冻结；其总成本仍须包含必要的快照上下文与映射，不能把“索引可为 4 字节”说成整条消息只需 4 字节，也不能假定尚未设计的新观测消息已经拥有可直接复用的全部字段。

当前源码具有编译后规则数组、32 位 `winner_rank` 和独立 64 位 `rule_id`，并已有策略快照身份，但这些不等同于已实现上述观测短引用。`winner_rank` 不能未经视图范围 / 唯一性证明直接充当全局规则身份。本轮只核对设计接入基础，未新增索引表或修改产品代码。[当前 L4 查询结果](../../src/product/vpp/product_l4_policy.h:151)、[匹配返回](../../src/product/vpp/product_l4_policy.c:333)

### 27.6 回到简单标识：单一 64 位值（用户接受的初版工程起点）

用户指出标识讨论已陷入复杂设计，认为直接指定一个方式即可。助手据此停止继续增加身份层次、快照映射或逐位选择问题，直接选取以下可调整的初版工程默认。用户随后表示“差不多这样就得了”，接受该简单方案，标识议题在此收口；具体数值保留为可调整的工程起点，不构成性能实验结论或产品实现授权。

- **内部与消息表示：** 一个 `u64`，共 8 字节；高 48 位为固定规则身份，低 16 位为修订号。消息直接携带完整值，不为该 ID 新增快照内短引用及其导出映射协议。
- **固定部分：** 创建规则时由控制侧随机生成非零 48 位值，并检查本地已有 / 保留规则身份，冲突则重新生成。同一逻辑规则保留该固定部分；不将不同导入批次从 1 开始的编号直接当成外部规则身份。

- **导入校验：** 校验完整 ID 与所指规则内容；同一完整 ID 对应不同内容时报告冲突，不静默覆盖。具体导入去重 / 合并流程仍按后续配置设计落实，随机生成不被宣称为数学上绝无碰撞的全局唯一性保证。

该默认保留一个整体标识、同一规则的固定部分、可见的版本顺序及紧凑消息表示。已有完整策略快照仍解释实际生效上下文，既有编译索引继续属于匹配器内部实现；这里撤回的是为压缩该 ID 额外设计的消息短引用方案，不改变快照一致性或正常编译索引职责。

旧版本的完整规则 / 名单内容保留不由 ID 选择自动决定，后续已按第 27.8 节收口。此处只保存工程起点，未修改正式 CONTEXT / ADR、产品代码或执行测试；后续有实际问题再调整，不继续为预想规模追加身份框架。

## 28. 配置校验与 VPP 编译的职责（用户修正，接入分工继续细化）

在 SNI、规则标识和常态历史解释收口后，用户要求继续讨论。助手转入第 12 节第 6 项的 Interface 接入设计，先核对当前实现，避免把已有执行分工重新列成开放问题。

当前主线的相关过程为：

- Java `AuthoringPolicyCompiler` 将当前支持的 Gate / L4 authoring 配置按 subject 组织，形成 Apply payload 与完整 native bundle；遇到协议规则仍明确拒绝。这是现有转换职责，不是本轮通用表达式、组引用拍平和自动编排已经实现。[编译入口](../../app/android-runtime/src/main/java/com/sakamoto/snort/androidruntime/AuthoringPolicyCompiler.java:16)、[Apply 调用](../../app/android-runtime/src/main/java/com/sakamoto/snort/androidruntime/ProductPolicyTransactions.java:212)
- Rust Product Core 校验 typed bundle，维护保存与 native Apply 的处理流程；底层通过 native/VAPI 提交给 VPP。[Rust Apply](../../crates/product-core/src/session.rs:551)、[保存处理](../../crates/product-core/src/policy.rs:1240)
- VPP C 将配置转换为本地规则表示，调用 `product_l4_policy_compile` 构建查询视图，并经现有快照发布过程使 worker 使用新配置。[VPP Apply](../../src/product/vpp/product_core_plugin.c:724)、[查询视图与发布](../../src/product/vpp/product_packet_graph.c:3474)

助手最初建议将有效规则拍平、Rank 和自动前后置规划集中到 Rust。用户随后指出：Rust 的规划应限定为输入格式、内容等校验，而自动分配前后置应在 VPP 内，属于编译的一环，并要求说明考虑。助手核对依赖后赞同该划分，撤回将自动编排放在 Rust 的建议。

修订后的职责建议如下；具体输入对象和配置展开接线尚未冻结：

| 位置 | 职责建议 |
| --- | --- |
| Rust 控制侧 | 校验格式、类型、取值范围、规则 / 名单引用、标识及配置内容的一致性，完成必要规范化与配置提交；不决定规则物理前后置位置或运行索引布局 |
| VPP-native C 编译路径 | 根据合法输入形成运行所需的有效规则视图和完整 Rank，分析事实依赖与规则重叠，自动分配整条规则的前后置位置；结合能力与预算完成展开 / 因子化、两个程序的查询结构及缓存依赖，所有必需产物就绪后一次发布完整快照 |
| VPP worker | 使用已发布程序执行匹配，维护 owner-local 事实、计量与归因；不逐包重新做前后置规划 |

助手此前偏向 Rust，是希望集中配置语义并让各平台共用；这并不要求把执行优化也放在 Rust。自动分配依赖实际前置匹配器能完整执行哪些条件、CT / LPI / SNI 事实何时可得、保守重叠证明及编译预算。将该工作放在 VPP C 编译路径，可让这些知识与实际匹配实现共同维护，避免 Rust 与 VPP 同时拥有需要同步的执行能力 / 优化判断。

因此建议用“配置校验与准备”描述 Rust 的职责，用“执行规划与编译”描述 VPP 的职责，避免“公共规划”同时指配置处理和执行优化。第 4.1 节公共规划与专用编译器的逻辑分工仍可在 VPP 编译路径内部保留，不需要额外进程或服务。

VPP 编译发生在配置提交 / 发布前的路径，不进入逐包 worker 热路径。Rust 预校验通过不等于编译一定成功：VPP 仍验证必要入参、支持能力和实际产物预算，失败按已有合同报告并保留旧快照。已有 L4 编译也在 C 侧完成校验、排序与 Rank 生成，可作为职责事实的核对依据，不表示新通用编译器已经实现。[当前 C 编译](../../src/product/vpp/product_l4_policy.c:116)

现有 Java authoring 转换与 Rust 配置准备的接入、源规则到有效视图的具体输入形态、AST / typed 传输、错误字段和迁移顺序留后续落实；这里不据此新增通用 IR 框架、预览引擎或冻结全部 ABI。

本轮只记录源码事实和待确认建议，未修改正式 CONTEXT / ADR、产品代码或开始构建 / 实验。

### 28.1 规则组引用展开的位置：围绕轻量应用侧的双向评估（讨论过程，后续已收口）

本节保留建议过程；后续第 28.2、29.1 节已收敛为 VPP 维护规则 / 组实体并完成展开和编译，Rust 保留适配与基本校验，不再把引用展开归属当作未决选择。

用户要求继续后，助手曾建议 Rust 将组 / 绑定展开为每应用适用的逻辑规则，再交给 VPP 编译；该操作只展开引用、按既定原则去重，不做表达式 DNF 或自动前后置分配。用户说明更希望该职责位于 VPP，让前端保持轻量，并要求同时考察赞同与批评理由。这里沿用此前用语，“前端”包含 Rust 应用侧，不限于 Java 界面。

**支持 VPP 侧展开的理由：** 从规则 / 组 / 应用绑定到有效规则视图、同源去重、完整 Rank、前后置分配及索引，可以由同一编译 Module 承接；Rust 不需要继续跟随执行语义维护一段规则展开逻辑。输入保留共享定义和引用关系，也可能减少按应用展开后的重复提交，但实际消息规模取决于编码，不预先宣称性能优势。编译后的 worker 路径仍使用平坦执行程序，引用展开不会变成逐包组遍历。

**代价与批评：** VPP 的输入面会从直接适用规则扩大到规则、组和应用绑定等逻辑关系；C 编译器需要处理缺失引用、循环 / 深度限制、同源模式冲突、展开预算和可回溯的错误。Rust 的配置库、导入格式解析及基本校验仍存在，移动展开过程主要减轻职责，并不自动降低同一设备的总 CPU 或内存；配置侧检查不能代替 VPP 对输入与资源的必要验证。

**执行路径事实：** 当前 `product_core_policy_bundle_apply` 是主线程 API handler，在初始化时被 `vl_api_set_msg_thread_safe(..., 1)` 标记，因此不因普通 API 分发机制自动取得全 worker barrier；它构建查询视图并沿既有受保护快照发布。不能据此声称编译零影响：更大的展开仍会占用主线程时间及临时内存，可能延迟该线程其他工作，需要在实际规模下验证；本轮不预先增加专用编译线程或新调度系统。[handler](../../src/product/vpp/product_core_plugin.c:724)、[thread-safe 注册](../../src/product/vpp/product_core_plugin.c:1104)、[视图构建与发布](../../src/product/vpp/product_packet_graph.c:3474)

综合当前用户目标，助手更倾向将规则组引用展开、同源去重及其后的执行编译放在 VPP 内，作为一次编译调用的内部过程。此前偏向 Rust 的理由是让 VPP 收到更简单的输入；在本轮原本就需要扩展通用规则编译输入的前提下，集中规则执行语义、减轻 Rust 职责的收益更符合当前目标。该判断不表示 C 比 Rust 更快，也不把已有 VPP 支持当作新编译器的验收证据。

建议保留的简洁接入范围：Rust 负责配置资产、外部导入格式、IDNA / 名称等必要规范化、输入基本校验及提交；VPP 接收有界、明确类型的规则 / 组 / 绑定数据并完成展开和编译，不直接访问配置数据库或处理任意外部文件格式。编译错误返回规则 / 组引用及原因，成功后一次发布，失败保留旧版。具体二进制格式、对象布局与预算按已有约束工程落实，不增加配置服务、长期规则关系同步或新 IR 框架。

本节记录当时应用户要求进行的双向评估与助手建议；引用展开的职责后续按第 28.2、29.1 节收口，具体接线留实施，未修改正式文档或实现。

### 28.2 VPP 常驻规则实体、主线程编译与 worker 快照（持久化比较过程，后续文件方向见第 29.1 节）

后续范围修正：用户在第 29 节要求回到已有文件合同核对，随后在第 29.1 节认可文件与 API 方向。本节“Rust 管理配置资产库”是助手当时的职责建议，不作为当前已经选择的数据库引擎、文件写入方或双端配置管理方式；单一持久配置来源继续作为讨论原则。

用户进一步说明期望：规则编译由 VPP 主线程运行，再替换 worker 所用的快照；日常规则、规则组等由 VPP 内的实体维护，UI / Rust 应用侧更多执行查询与数据窗口计算。助手赞同将运行中的规则 / 组模型与编译职责集中在 VPP，并建议明确运行实体、不可变执行产物与长期配置保存的不同生命周期。

用户随后明确修正：UI 如何决定留待后面，现在不做假设。助手此前据此推导 UI 主要查询、编辑方式、状态展示或防护停止时的界面能力，均不能作为已接受设计；下文仅描述 VPP 与 Rust 后台，不推定实际 UI 的职责或交互。

| 位置 | 当前建议 |
| --- | --- |
| VPP 主线程 | 常驻维护已装载的规则、规则组及应用绑定模型，提供运行模型查询与控制入口；构建候选编译产物，完成引用展开、去重、Rank、前后置分配与索引生成，并一致发布 |
| VPP worker | 获取并读取已发布的不可变执行快照，继续维护自身 Flow、事实、缓存与计量；不直接读写主线程正在修改的规则 / 组实体 |
| Rust 应用侧 | 管理唯一的持久配置资产库，完成保存 / 恢复、输入基本校验、外部格式处理、提交及重启装载；查询 VPP 当前生效状态；消费观测并维护既定窗口、压缩与历史库 |

“替换 worker 快照”沿用第 4.3 节 S209 的含义：发布新的不可变版本，之后的包绑定新版；已经绑定旧版的包可完成，旧读者退出后才能复用其存储。主线程源实体不成为 worker 的可变共享配置表，也不要求给每个 worker 单独复制一套规则 / 组关系。

持久化建议仍放 Rust：VPP Runtime 的停止、重启或 Root / VPN 切换会结束其内存状态，规则资产需要独立持久保存以支持恢复。启动时由保存的配置重新装载 VPP 实体并编译发布；“实体在 VPP 维护”不必同时意味着让 VPP 接管数据库、外部导入格式和历史统计。Rust 保存源配置与 VPP 持有运行模型可以同时成立，不要求 Rust 再维护一套执行规划；这不决定运行停止时 UI 提供哪些能力。

用户随后追问配置持久化留 Rust 是否意味着保留两份。明确澄清：**配置只持久化一份，由 Rust 管理配置资产库；VPP 不另存独立配置数据库或长期配置文件。** VPP 中的规则 / 组实体是加载后的内存模型，worker 快照是该模型的编译产物，不是另一份可独立编辑的配置。Rust 不必常驻维护第二套运行实体图，加载、校验或保存所需的临时表示按需存在；这不承诺序列化过程零复制。

配置修改通过同一控制提交流程协调，不让 Rust 和 VPP 各自改一套配置再后台双向合并。已定观测记录库仍独立存在，但按第 27.8 节只保存基本历史归因与汇总，不成为第二套完整配置库。具体持久化与发布时序沿既有控制合同继续落实，本次仅明确单一持久配置来源。

提交与生效状态仍须保持既有区别：已提交源配置不等于 worker 已采用的新版本；候选编译失败保留旧运行快照，控制结果如实报告失败和生效身份。该后端事实不冻结 UI 文案或展示。Rust 持久化和 VPP 发布沿现有控制处理继续接入，不新增两侧各自改写规则的后台同步协议，也不在本节选择每字段 CRUD 或新的事务框架。

源码核对支持当前发布机制与恢复职责：现有 VPP 已在发布函数中编译后写入受保护 bank，再切换可见版本；Rust 的 `apply_policy_bundle` 负责 staged 保存与 native Apply，`reconcile_policy` 从持久配置恢复 / 核对运行状态。当前还没有用户所述的完整规则组常驻模型，不能将职责提案描述为已经交付。[当前发布](../../src/product/vpp/product_packet_graph.c:3474)、[Rust 提交与恢复](../../crates/product-core/src/session.rs:551)

本节记录用户方向及助手建议；配置持久化是否继续按该分工、运行模型管理与查询接口仍待进一步确认，UI 相关决定明确后置。未修改正式 ADR / CONTEXT、产品代码或运行实验。

### 29.1 单一配置文件与在线规则 API（用户接受的首版方向）

用户认可上述文件方式，表示这正是期望的形态，并明确 UI 等前端通过 API 读取；同时认为 VPP 不运行时编辑和查看规则意义不大。该补充只收敛规则管理的后端可用性方向，不扩大为具体 UI 布局、控件或交互决策。

助手建议首版按在线规则管理推进，不为离线查看 / 编辑另建 Rust 规则实体管理器。顺着该职责，建议 VPP 提供规则、规则组及绑定的管理 API，并成为那份配置文件的唯一写入方；它加载文件形成内存实体、完成编译与快照发布，并按明确的保存入口更新文件。Rust 保留输入基本校验、请求适配、外部格式处理及已定观测消费 / 保存 / 窗口职责，不拥有另一套可独立修改的完整规则配置。

该决定保持单一持久配置来源和主线程编译 / worker 只读快照的已定方向；文件保存与运行生效的具体处理沿既有完整发布要求落实。具体编码、API 与保存时机尚未冻结，UI 交互继续后置。未修改正式 ADR / CONTEXT、产品实现或运行实验。

### 29.2 修改请求何时算成功（初始建议，后续修正见第 29.3 节）

后续用户明确倾向先全部保存完毕，再应用 / 编译。以下“一次提交成功”的提案尚未被整体接受，尤其“编译拒绝保留原持久配置”不能与第 29.3 节的新顺序混用。

核对第 12 节后，剩余大部分是已定范围下的接口、布局、容量与实验事项，不逐项请求用户选择。与新职责直接相关、仍影响行为的一项是：是否保留“保存配置但暂不应用”的独立后端状态。

现有 [CONTEXT 的 Draft / Commit / Apply 术语](../../CONTEXT.md:934) 将可编辑草稿、已保存配置与生效快照分开，Commit 本身不改变数据路径。这是现有文档中的设计，不等于当前代码已完整实现三层管理；当前 [Rust apply_policy_bundle](../../crates/product-core/src/session.rs:551) 实际执行 staged 文件 → native Apply → 成功后提交文件，并处理结果不明等情况。两者不能混称为本轮已确认的接口。

助手建议首版对外收敛为一个提交入口：一次请求可以包含一条或一批关联修改，按修改后的完整配置校验、编译并整体发布；只有该配置已经保存且已生效，才返回成功。例如创建规则并将其加入组可放在同一次请求，不要求把中间配置分别发布。首版暂不增加可长期保留的“只保存、稍后应用”后端配置状态；这不决定 UI 编辑、草稿或按钮如何设计，也不要求每次输入操作都调用提交。

校验或编译拒绝保留原配置与原运行快照；保存失败或结果不明不能冒充成功。保存与发布仍是两个物理时点，上述成功语义不宣称磁盘与内存具有天然跨介质原子性；具体顺序和失败恢复需要在工程接入时闭合，并遵守既有完整快照与如实报告生效身份的要求。本节只提出接口行为建议，尚未得到用户确认，也未设计额外事务框架。

### 29.3 先完整保存，再编译应用（用户确认的初版起点）

用户表示保存没有问题，但倾向于一定全部保存完毕后再应用 / 编译，并询问助手建议。助手赞同这一顺序：本次修改涉及的规则、组及绑定先形成完整的一版配置，完成基本格式 / 引用一致性校验并可靠保存，再以该确定版本编译；编译成功后发布完整快照。编译过程中不得混入后续修改，也不将一批关联变更的中间状态逐条发布。

理由是配置文件明确保存用户已提交的配置，编译明确负责把这一版配置变为执行产物，保存和运行切换的先后容易解释。基本校验在保存前完成，不表示编译不再可能因实际能力或产物预算拒绝。这一顺序仍可由一次请求顺序完成，也可由明确的保存 / 应用入口驱动；用户本次没有据此冻结 API 拆分、手动应用按钮或其他 UI 行为。

初版失败处理为：保存失败则不启动编译，继续使用旧配置和旧快照；保存成功但编译失败时，保留已保存的新配置供后续修改，worker 继续旧快照，报告“已保存、未生效”及具体原因。与第 29.2 节相比，这撤回了编译失败必然回退持久配置的建议，也承认保存版本与生效版本可以不同；两者是同一配置的不同阶段，不是两套可独立编辑的规则库。API 应分别说明保存与生效结果，不能只报告含糊的成功或失败。

这一方案的实际代价是：重启后旧内存快照已经消失，若最新保存配置仍编译失败，无法仅靠该文件恢复上一次成功运行的内容。此时明确报告恢复失败，不能把空规则或默认放行伪装成成功恢复。第 31.3 节进一步确认此时保留 VPP 管理 API 供用户修复，编译成功前不启用产品流量接管；具体进程 / Adapter 接线沿运行生命周期落实，不据此自动新增长期旧配置档案或备份体系。

用户随后明确表示“当然，我们先这样做初始版本吧，后面通过用户反馈来进行修改”，接受上述流程、失败处理和分别报告结果作为初版起点。本议题在此收口，不为预想边角继续扩展保存框架；文件格式、API 拆分和结果字段等留工程落实，实际使用反馈可以驱动后续调整。这是设计讨论中的初版共识，未修改正式规格或产品实现。

建议第一步用当前 C 主线已有的静态 L4 执行能力，打通新的规则管理链路：API 提交规则 / 组 / 绑定 → VPP 管理源实体并校验 → 完整保存文件 → 展开有效规则、生成完整 Rank 并编译 → 发布一致快照 → 查询保存 / 生效结果及实际规则计数。规则身份使用第 27.6 节起点；静态规则仍遵守本轮统一排序、普通规则式联网禁用和缺省动作，不将旧 Gate 特权或阶段语义固化为新接口。这里只复用当前允许的 C 主线基础，不以已移除的 C++ 或 POC 源码实现。

这条链路先覆盖成功更新、保存失败、编译失败保留旧快照、重启装载及失败报告等已定行为。具体格式和 Interface 应能自然容纳后续表达式与事实类型，但不预建尚无消费者的框架，也不把中间验收称为完整规则引擎交付。

随后接入完整 AND / OR / NOT 与 CT 等动态事实、前后置自动分配和保守缓存守卫，再接 LPI、TLS / QUIC SNI 及域名条件，沿第 24 节的方法对照动作、逻辑赢家和归因。索引 / 因子化等实现按有界语义逐步接入，参考求值器保持测试用途；最终布局和库选择仍取决于工程验证与移动端实验。

常态观测沿每一步接入实际动作与计量，逐步补齐累计消息、Rust 窗口及持久化，不等全部匹配能力完成后才检查归因；既定传输候选仍需实验选择。这是同一初版内部的建议顺序，TLS / QUIC SNI、域名谓词和已确认常态观测范围没有移出本版，也不提前设计 UI / debug。

上述顺序保留为实施参考，不作为当前未决设计问题；本节不创建实施工单、不修改正式规格、不开始产品实现或实验。

### 31.2 复核发现的行为缺口：启动编译失败后的修复入口（后续确认见第 31.3 节）

按已确认方案构造如下完整场景：

1. V1 正在运行；新配置 V2 已保存，但因为编译产物超预算等原因无法应用，worker 正确继续 V1。
2. VPP 重启，V1 内存快照消失；加载 V2 后编译仍失败，按第 29.3 节报告恢复失败。
3. 规则只能通过在线 VPP 管理 API 修改。若恢复失败同时停止 VPP，用户便无法经正常 API 修复 V2；再次启动还会遇到同一问题。

这不是文件编码或参数问题，而是已选保存语义、在线管理与启动生命周期之间缺少修复路径。当前 [RuntimeService 启动恢复](../../app/android-runtime/src/main/java/com/sakamoto/snort/androidruntime/RuntimeService.java:1235)在策略恢复失败时调用 [failProductCoreGeneration](../../app/android-runtime/src/main/java/com/sakamoto/snort/androidruntime/RuntimeService.java:4834)，该函数关闭控制会话并终止 VPP 进程 / owner；因此不能把当前路径当作新方案已经具备修复能力的证明。本轮是静态核对，没有运行失败实验。

助手推荐：可归因于规则配置的启动加载 / 编译失败，不直接结束整个 VPP 规则管理入口；在进程与控制基础正常的前提下，保持管理 API 可用，报告策略恢复失败，允许查询错误、修正 / 替换配置并重试保存与应用。没有成功策略时不启用产品流量接管，也不报告保护正在运行；修复并成功编译发布后，才按正常运行生命周期启动保护。具体 Root / VPN 资源的延后建立或清理接线留实现，并不声称当前代码已支持。

这保留 VPP 单一规则管理者，不增加 Rust 离线规则库，也不要求引入最后成功版本档案。推荐针对配置失败；VPP 自身崩溃、权限不足或控制基础不可用时，仍不能承诺 API 存活。它不重新决定 OS / 外部 always-on VPN 等机制的联网策略，也不设计 UI 展示。

复核当时的结论为：核心规则设计及常态观测的主链已收敛，完整启动 / 修复闭环还差这一处行为选择；助手此前笼统表示可以结束设计，未充分核对这一交叉路径。用户随后的确认见第 31.3 节，此处不再是未决问题。此次其余已查范围未发现新的阻塞矛盾，不将此结论扩大为实现或性能已通过验收。

### 31.3 编译成功是流量接管前置条件，失败由用户修复（用户确认）

用户认可上述修复方式，并明确“规则编译这个相当于一个前置条件，规则变了，但是编译失败，这是用户必须处理的情况”。据此收口为：

- **启动 / 重启时没有有效快照：** VPP 进程和控制基础正常时，保留规则管理 API，报告配置错误；只有编译成功并发布有效快照，才具备启用产品流量接管的策略前置条件。修复前不报告保护正在运行。
- **运行中修改配置：** 新配置仍先完整保存；编译失败时保留修改与错误，worker 继续已有旧快照，明确区分保存版本和生效版本。这不因本次启动前置条件的确认而改成停止已有保护。
- **用户处理：** 用户通过同一 VPP 管理入口修正 / 替换配置，再保存、编译和应用；系统提供可定位的错误，不通过自动删除、忽略失败规则或回退已保存配置来伪造本次应用成功。

成功编译是必要前提，不代替权限、Adapter、平台生命周期等已有就绪条件。具体 API 返回、修复后的启动接线和 UI 交互在各自阶段落实；不为此增加第二套配置管理者或复杂自动恢复框架。

补齐该路径后，本轮已讨论的规则后端与常态观测设计达到可指导实现的闭环，未发现仍需用户先决定的阻塞语义。剩余工作是同步正式文档、细化实施合同、实现与实验验证；UI 和具体 debug 设计保持既定后置范围。此次只更新临时讨论记录，没有将设计确认写成已经实现或通过验收，也没有开始产品实现。
