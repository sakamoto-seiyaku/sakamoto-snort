## 四項具體發現

1. **缺少整 frame buffer pointer 準備及有界預取。** Admit、policy、consumer、terminal 每次迴圈才 `vlib_get_buffer`，沒有為後續包提前載入 header／需要的 packet data。Pinned `ip4_input` 則先 `vlib_get_buffers`，再以 x4/x2 與較遠的 header、較近的 data 預取重疊記憶體延遲；其 API 也提供批量 index-to-pointer 轉換。可先建立固定容量 pointer scratch 和短 lookahead：admit 預取 parser 要讀的 L3 起點，consumer/terminal 只預取 metadata，保留短 frame 的 scalar 路徑。這是後續流水線的基礎，單獨換 API 不代表已有收益。預取只能指向仍持有的合法 buffer；成功 handoff/free 後不再解引用；END 與 fragment 仍走原分支。[產品 admit:1254](../../../src/product/vpp/product_packet_graph.c#L1254)、[policy:1596](../../../src/product/vpp/product_packet_graph.c#L1596)、[consumer:1751](../../../src/product/vpp/product_packet_graph.c#L1751)、[terminal:1964](../../../src/product/vpp/product_packet_graph.c#L1964)、[上游 ip4_input:119–138](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/vnet/ip/ip4_input.c#L119)、[buffer API:186–231](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/vlib/buffer_funcs.h#L186)。

2. **Admission 的純準備工作仍一包到底。** 現行 `admit` 封裝 parse→canonicalize→FNV hash→distribution，每包 hash 又有逐 byte 相依鏈；呼叫方完成整包後才開始下一包。Pinned ACL 以四包準備 tuple/hash、提前讀取後續 header/data，然後才進入 stateful loop。適合設計產品自身的 x2/x4 短準備窗口，交錯獨立 packet 的解析／hash 工作，再按原 frame 順序執行 metadata、credit 與 publication。保留目前 typed key、seed、hash 值及 owner mapping，避免把換 hash 演算法和流水線混成一項變更。IPv6 extension、錯誤包及已準備的重組包保持原判定；沒有 public parse-only API 可直接套用，`parse_ingress` 目前是 private helper。[產品呼叫:1299–1318](../../../src/product/vpp/product_packet_graph.c#L1299)、[hash:110–127](../../../src/product/vpp/product_packet.c#L110)、[private parser/admit:330–402](../../../src/product/vpp/product_packet.c#L330)、[上游 ACL x4 準備:219–299](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/plugins/acl/dataplane_node.c#L219)。

3. **Policy cache/index 查找沒有跨包分階段接口。** 每包先投影 facts、建立 cache guard/hash，再立即讀 cache；miss 時又逐 subtable 建 masked key、hash、走 entry chain。即使單 key 已被編譯器向量化，後續查找仍沒有 lookahead。Pinned classify 將 hash/bucket 預取與 entry 查找分離，並在保留 scalar consume loop 時預取後方 entry。可由 policy 模組封裝短窗口的靜態投影、guard/key/hash 和 prefetch，保持原 winner rank、完整 residual 判定與 cache guard。PRE 準備不能提前使用尚未產生的 CT/LPI/SNI；POST query 必須等當包 Flow update 後才形成。每個 prepared query 必須持有自己的既有 snapshot claim；把 snapshot 改成整 frame 一份會改變 publication 生效粒度，需要另行決定，不能順手改掉。[產品 projection/cache:3037–3056](../../../src/product/vpp/product_packet_graph.c#L3037)、[index:953–979](../../../src/product/vpp/product_l4_policy.c#L953)、[cache:1088–1117](../../../src/product/vpp/product_l4_policy.c#L1088)、[上游 classify hash/bucket:76–159](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/vnet/classify/ip_classify.c#L76)、[entry lookahead:175–201](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/vnet/classify/ip_classify.c#L175)。

4. **FlowRuntime 欠缺安全的查表預取 seam；保序更新則應保留。** Runtime 的 linked bucket lookup 與 observe/update 綁在單 assignment 呼叫中；VPN UID 路徑還會先查 incarnation，再由 enrichment 查表，之後 observe 再查。適合先增加 owner-local、無狀態變更的 bucket/候選 cache-line prefetch，由 runtime 私有實作索引，不讓 node 取得 table/slot ownership。不要先保存全 frame 的 miss 或 entry pointer：同 flow 前包可能建立 entry、UID 衝突退休舊 flow、邏輯 expiry 或 TCP replacement；後包必須看到這些變化。官方 ACL 的 bucket/data/session 三段 lookahead 仍逐包更新，且在 create/delete 後明確修正相同 tuple 的下一包預測。產品若日後加入 lookup ticket，也須重新驗證 generation/incarnation/link/expiry；最小第一步只做 prefetch，可免除 authoritative 預測失效問題。[產品 lookup:72–117](../../../src/product/vpp/product_flow_entry.c#L72)、[observe/expiry/replacement:494–561](../../../src/product/vpp/product_flow_entry.c#L494)、[UID 路徑:1665–1680](../../../src/product/vpp/product_packet_graph.c#L1665)、[opaque runtime 契約:237–268](../../../src/product/vpp/product_flow_entry.h#L237)、[上游 ACL 三段流水線:352–400](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/plugins/acl/dataplane_node.c#L352)、[delete 修正:441–449](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/plugins/acl/dataplane_node.c#L441)、[create 修正:527–533](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/plugins/acl/dataplane_node.c#L527)。

## 優先三項建議

- external submit 現在產生真 singleton frame，單獨加 admit `get_buffers`／x2/x4 不會取得 batch；應協調入口 frame 形成與下游準備，再加入短 header/data lookahead、獨立解析/hash 準備。保留立即處理小 frame，不為湊 batch 等待。
- 再由 policy 與 FlowRuntime 各自提供 prepare/prefetch seam，從無 mutation 的預取起步；CT、UID、expiry、識別、cache 更新及完成提交仍按原包序進行。
- 將 same-flow-in-frame、replacement/expiry、PRE/POST、END/fragment、部分 publication 與 snapshot lifetime 列為設計驗證条件，再獨立量測收益；此次靜態審查不能排序實際 CPU 瓶頸或推導加速比例。

固定 owner、parse-once、metadata lifetime 與 exactly-once completion 是上述變更的邊界。獨立 owner-guard node 只在 host-evidence 編譯，shipping 接收端使用既有 assignment，沒有可「刪掉」的二次 selector；也不應引入 corrective dispatch、跨 owner CT、擴大 opaque 或全 frame PacketLease 常駐 scratch。這些限制不阻止短準備窗口，但限定可以並行的工作。[host-only guard:1454–1579](../../../src/product/vpp/product_packet_graph.c#L1454)、[shipping receiver:1635–1689](../../../src/product/vpp/product_packet_graph.c#L1635)、[唯一 assignment/owner 契約:96–100](../../decisions/PER_WORKER_FLOW_OWNERSHIP.md#L96)、[metadata 邊界:69–83](../../decisions/VPP_PACKET_METADATA_OWNERSHIP.md#L69)。
