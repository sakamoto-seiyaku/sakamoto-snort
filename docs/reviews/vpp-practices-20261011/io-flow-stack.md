# VPP I/O 與 owner-local Flow Stack 審查（2026-10-11）

基準為 Product HEAD `54f2566f26cbbd2ae2cdfd3a1796e4e0f19041e6`，VPP pinned `9258530f3804a152578ce11cc7c8a1e9eab88ed0`。本次只讀程式與既有證據，沒有修改 Native/tests、執行 benchmark 或操作裝置。上游程式以 `build-output/pinned-vpp-clean` 的 `git show 9258530:<path>` 核對；Android patches 另行辨識。FD.io 的「26.02」網站目前頁面自述 development revision，以下具體 API 行為以 pinned blob 為準。[FD.io graph 說明](https://docs.fd.io/vpp/26.02/aboutvpp/extensible.html)。

優先順序是 **P1 admission/drain 耦合 → P2 native ingress frame 生產 → P3 HEV 呼叫邊界攤銷**。這是待驗證的投資順序，不是已證明的性能修復。

1. **underused，P1：入口與 owner drain 的預算須一起設計。** VPN egress 逐包 `input_copy` 後只設 input-node interrupt；真正 drain 在另一個 node 的 `step(8,200)`。上游 main loop 先 dispatch input interrupts，再一路處理 pending graph frames；因此 graph 中新設的 interrupt 不會在當下每次 admission 後自動執行。這提供「一輪入流累積比 drain 快」的機制假設，尚不能判定是主要瓶頸。[egress](../../../src/product/vpp/product_packet_graph.c#L1790)、[driver](../../../src/product/vpp/product_vpn_flow_stack.c#L295)、[pinned loop](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/vlib/main.c#L1548)。

   四個歷史 30 秒 VPN 窗口接受 `299533/223862/238975/218371`，拒絕 `849991/742015/759559/752609`；raw before/after 的新增 failure 全為 `PACKET_CREDIT`，CPU 約 `56.54–56.69` CPU 秒。這是 HEV 的 live `PBUF_POOL` admission predicate，與 VPP primary handoff credit／`primary_rejected` 是不同階段，亦不是 VPN return credit。[HEV guard](../../../third_party/hev/product/hev-owner.c#L380)、[VPP primary credit](../../../src/product/vpp/product_packet_graph.c#L1193)。這支持審查容量與 drain 邊界；兩次 batch 窗口沒有證明提高端點交付效率，也沒有證明加容量或改排程有效。[comparison](../../evidence/2026-10-11-vpp-admit-owner-long/run-warmed/comparison.json)、[raw CLI 證據](../../evidence/2026-10-11-vpp-admit-owner-long/raw.tar.gz)。最小下一步證據是各 owner admission burst、兩次 step 間隔、credit occupancy、成功 send 和 socket `EAGAIN` 的同時序資料，區分 graph backlog、runnable transport 與 underlay 阻塞；再考慮分段 admission/有限 drain，保留總時間上限與其他 flow 的公平進度。

2. **underused，P2：readiness burst 尚未成為 native ingress vector。** NFQ/TUN callback 各最多讀 64 次，卻逐包呼叫 external submit；HEV return 也走同一入口。其 `get_frame_to_node → n_vectors=1 → put_frame_to_node` 每次配置並加入獨立 pending frame，上游 API 沒有自動合併。AF_PACKET 上游示範集中配置 buffers、填滿 next frame 再 publish；可學其 frame 生產形狀，不能移植它的 RX ring。[NFQ](../../../src/product/vpp/product_root_nfqueue_adapter.c#L1027)、[TUN](../../../src/product/vpp/product_vpn_tun_adapter.c#L317)、[external submit](../../../src/product/vpp/product_packet_graph.c#L4089)、[pinned allocator/publish](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/vlib/main.c#L99)、[AF_PACKET](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/plugins/af_packet/node.c#L298)。

   機會是把同一 bounded receive turn 已接受的 buffer indexes 成批發布，低流量時立即 flush；每包仍有自己的 platform facts、obligation 和拒絕 settlement。Root 已有 receive pool，無須為 batching 重建配置器；TUN 的 `vlib_buffer_alloc(...,1)` 可另外評估小批配置，但不得留住未用 buffers。最小證據須同時顯示 vectors/frame、physical publications、credit rejection 與真正政策覆蓋的交付；只降低 node calls 不足以接受方案。歷史 batch code 不作產品實作範本。

3. **underused，P3：HEV 的單包外部邊界尚未攤銷。** 每包 `enter/leave` 都執行 owner/thread 檢查、scheduler TLS 與 lwIP context 切換、`pbuf_alloc/pbuf_take/ip_input`；VPP 已有一個 egress frame，卻仍逐包進出此邊界。可研究 owner-local、小批量且逐包回報結果的介面，把 context 切換攤銷；batch 仍須有數量/時間上限，並與 P1 的 drain 協調。[owner scope](../../../third_party/hev/product/hev-owner.c#L77)、[input copy](../../../third_party/hev/product/hev-owner.c#L799)。

   活跃 UDP task 每輪循環最多 send/receive 各一個 datagram，再 yield；quanta 是 task 調度次數，不能換算成 packet 數。Direct patch 的 `sendmsg` iov 是同一 datagram 的 pbuf spans，不是多包 batch。先量測 context、yield、reactor poll 的成本，才評估同一受保護 session fd 的有限 drain；不能把不同 flow fd 放入同一 `sendmmsg`。拒絕目前可能發生在 full copy 後，但 generic 提前拒絕會跳過 UID/incarnation conflict-close 等副作用，須保留逐包語義；兩次所有權 copy 繼續存在。[UDP task](../../../third_party/hev/product/hev-owner.c#L312)、[credit guard](../../../third_party/hev/product/hev-owner.c#L355)、[Direct patch](../../../third_party/hev/patches/0004-direct-udp-session.patch)。

4. **alreadyused：owner locality、非阻塞與事件進度已落地。** 固定 shard registry、worker-local mutable callbacks、broker fd/transport reactor/timerfd subscription、interrupt input node 和 runnable 自我 reschedule 都存在；TCP timer 無新包也由 step 推進。HEV scheduler patch 以零 timeout poll reactor、每次最多 32 readiness events，並限制 quanta/時間；這不是全域 HEV funnel，也不需要新增共享 TX 或 busy-poll。200 μs 是合作式 yield 處的預算檢查，並非任意 callback 的硬性 preemption；timer、session scan 等 work 亦須納入成本觀察。[driver subscriptions](../../../src/product/vpp/product_vpn_flow_stack.c#L74)、[reschedule](../../../src/product/vpp/product_vpn_flow_stack.c#L370)、[owner step](../../../third_party/hev/product/hev-owner.c#L920)、[scheduler patch](../../../third_party/hev/patches/0001-bounded-owner-scheduler.patch)。Android 的 pending-frame pre-wait 檢查與有序 notification latch 也已有產品 patch，不能誤報成「缺少喚醒」。[notification patch](../../../src/product/vpp/android/patches/0019-vpp-worker-notification-latch.patch)。

5. **missing：缺的是 admission/drain 因果證據，不是總量 counters。** snapshot 已有 steps/quanta、input peak、pbuf/PCB/socket 與 fault counters；CLI barrier 時看到 occupancy 為零不代表負載期間沒有峰值。當前資料不足以把 PACKET_CREDIT 分成短 burst、driver 調度延遲、broker 等待或 socket 送不動。適合補 bounded owner counters/直方圖與 sampled 時序，避免常態逐包 stderr；滿 CPU 或 accepted 數量均不能代替 delivered goodput、尾延遲、idle CPU 和公平性。[snapshot](../../../third_party/hev/product/hev-owner.c#L978)、[現有證據限制](../../evidence/2026-10-11-vpp-admit-owner-long/run-warmed/comparison.json)。

6. **platformconstrained：一個 TUN lane 與 origin verdict confinement 是邊界。** Android `establish()` 回傳 packet fd、預設 nonblocking；Linux multiqueue 則需用 `IFF_MULTI_QUEUE` 對同一 device 建立多個 queue fd。不能由前者推論 Android 公有 API 已提供 RSS/multiqueue；現有單 fd 接收不妨礙之後兩個 canonical owners 各自運行 HEV。[Android API](https://developer.android.com/reference/android/net/VpnService.Builder#establish())、[Linux TUN multiqueue](https://docs.kernel.org/networking/tuntap.html#multiqueue-tuntap-interface)、[現有 owner 配置](../../../src/product/vpp/product_vpn_flow_stack.c#L239)。NFQ verdict 留在 origin lane；return credit 每 owner 隔離、buffer free 後才釋放；output callback 只複製並 native schedule，不能遞迴跑 graph 或等 TUN write。上述均按 [ADR-0006](../../adr/0006-vpp-native-packet-io-adapters.md)、[ADR-0007](../../adr/0007-owner-local-lwip-direct-egress.md) 保留。容量增大、跨 owner 借位、shared-TX、另建 payload queue 和零 copy 均非本審查的默認解法。
