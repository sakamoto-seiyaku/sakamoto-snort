# 全设备网络可见性：竞品交互研究（2026-09-29）

状态：设计研究输入，不是竞品实测、产品规格或功能验收。2026-09-29 查阅六款产品的第一方帮助、官网、更新记录及公开界面说明；没有安装或运行它们。官网概述只能证明厂商如何描述产品；下文只有标明「帮助/操作说明」的内容才作为具体点击路径依据。「推论」是对 Sakamoto 的设计判断，不是竞品可用性测试。Portmaster 的具体交互材料有 2021–2023 年版本背景，不能据此断言 2026 年 v2 的每处界面仍相同。

研究问题：当用户只觉得设备联网「有点不对」，尚不知道该怀疑哪个应用时，界面如何从**全设备变化**带他找到**应用、时间、目标、处理原因**；找到后又如何做决定、返回并核对？同时，不能把 DNS 请求数、连接数和传输字节混成一个「流量」数字。Sakamoto 的目标平台是 Android 手机/平板与 Linux PC；本研究借用不同平台的交互经验，不借用它们的数据能力限制。

## 六款产品的实际入口与可借鉴边界

### Little Snitch：时间图和应用树相互缩小范围

**帮助/操作说明。** [Little Snitch 6 Network Monitor 概览](https://help.obdev.at/littlesnitch6/lsm-overview)的默认列表先展示进程/应用组，展开后是域名、服务器；同屏有流量图、地图和详情。用户没有嫌疑应用时，可在[流量图上选择一段时间](https://help.obdev.at/littlesnitch6/lsm-traffic-chart)：列表随之只留下该段有相关事件的连接，并暂按传输量排序，地图也聚焦同一范围。选中列表项时，图和详情反过来只表达该选择。[Little Snitch for Linux 帮助](https://help.obdev.at/littlesnitch-linux/connections)也描述「应用→域名→主机/IP」的展开顺序和时间图选区过滤列表；点连接可建规则，随后到规则视图细化。这证明「应用优先」与「先看全设备哪段变化」可以是同一个连续交互，而非互斥首页。

**精确性与代价。** [规则管理帮助](https://help.obdev.at/littlesnitch6/lsm-managing-rules)说明列表一行可能是一组连接，按该行建规则会覆盖这组连接，按钮颜色还区分完全覆盖与部分影响；查看对应规则和最近使用规则是两个不同动作。若省掉这种范围提示，用户容易把「点一行」理解成只改一次连接（这是我们的推论）。[Linux 帮助](https://help.obdev.at/littlesnitch-linux/connections)主动说明 DNS→IP 命名只是启发式，一 IP 可对应多域名，缓存和加密 DNS 也可能遮住证据；因此名称应带来源与确定性，不能把推测写成该应用确实访问的域名。[地图帮助](https://help.obdev.at/littlesnitch6/lsm-map)把没有地理信息的服务器放在明确的占位位置，避免伪造真实位置。

### GlassWire：图上找到变化，再认出应用；提醒照顾离开后的用户

**帮助/操作说明。** [Windows 用户指南](https://www.glasswire.com/userguide/)的 Traffic Monitor 从全设备图开始，点击峰值时图会暂停，随后可查看应用及所联系的主机；时间滑块用于回看。Usage Table 和地图是同一观察领域的其他视图，Protect 则是独立的应用防火墙入口。指南还列出「首次联网」和「离开电脑期间」的提醒，以及可暂时静音通知。[Android 帮助](https://www.glasswire.com/android-help/)描述图下按用量排列的应用，点击图上的时段看由哪些应用造成，再点应用看它自己的用量；防火墙另有应用列表。

**精确性与代价。** 用户指南明说图的刻度可能随着用量变化，且选择峰值后会暂停图。这使「哪段时间、什么单位、现在是否还在更新」成为图本身必须回答的问题；否则形状变化可能被误读为网络行为变化（推论）。观察和阻止分在两个区域，给了各自任务空间，也可能使从某个峰值到具体控制的上下文跳转变长；资料没有证明实际用户是否觉得困难。提醒可以帮助没有嫌疑应用的用户回来后开始，但不能让每次普通连接都成为必须处理的警报。

### Portmaster：厂商自己发现原始监视器不足以当起点

**第一方版本记录与当前概述。** Safing 在[2021 年进度记录](https://safing.io/blog/2021/11/05/progress-update-october/)中说，旧监视器的点看起来可点击、实际却不能点，并把改版目标定为一眼看到各应用允许/阻止的连接数。[2022 年 v0.9 记录](https://safing.io/blog/2022/08/18/portmaster-0.9-new-network-monitor/)引入全设备监视、搜索/筛选/分组及允许和阻止连接随时间的图。[2023 年 v1.4 记录](https://safing.io/blog/2023/08/21/portmaster-v1.4/)明确说网络监视器对新用户不是好入口，因而增加首页概览；[v1.5 记录](https://safing.io/blog/2023/10/18/Portmaster-v1.5/)把发送/接收图分别放到单连接、应用和全设备层。[当前官网 v2 概述](https://safing.io/)仍描述全设备实时监视与应用级规则，但未给出足以核对 v2 每一步点击行为的帮助；上述交互事实按原发布日期理解。

**推论。** 一个强大的全设备监视器仍可能要求用户先懂筛选和分组，概览应给出可进入的具体异常或变化，而不是只摆「功能已开启」开关。Safing 对误导性点击外观的自述也提醒：Sakamoto 图、统计行、地图点若看似能钻取，就应真的将用户带到造成变化的应用和记录。

### LuLu：一次新连接的决定很直接，全网观察是另一扇门

**官方操作说明。** [LuLu 产品帮助](https://objective-see.org/products/lulu.html)展示新连接警报先给进程和目标，用户可 Allow/Block；默认决定作用于整个进程，展开 Details and Options 后才可选远端目标范围和持续时间。Rules 窗口区分用户、默认和最近规则。要看当前全设备活动，状态栏菜单的 Network Monitor 会打开随附的 [Netiquette](https://objective-see.org/products/netiquette.html)；后者按进程列出当前连接/套接字及地址、端口、状态和传输量，可搜索，默认数秒自动刷新。

**推论。** 警报擅长回答「刚出现的这个连接怎么办」，不等于回答「刚才设备整体发生了什么」。默认整进程范围若藏在展开项后，可能比用户以为的「只对这一目标」更宽；Sakamoto 从记录给操作时，作用应用、目标和以后适用的范围必须就在按钮附近。Netiquette 的自动刷新适合看当前状态；阅读历史和固定一条记录需要另有稳定路径，不能由「当前连接」页推断已有完整历史。

### RethinkDNS：DNS 与连接各有记录；跨两类事实的归属最容易断

**官方文档与更新记录。** [Firewall 文档](https://docs.rethinkdns.com/firewall/)描述可搜索的逐连接网络日志，以及应用被阻止和连接去向；配置 DNS 后还有实时 DNS 请求分析与应用报告。[2026-09-20 v057 更新记录](https://www.rethinkdns.com/download)写明新增按应用和时间分组的允许/阻止域名与 IP 统计、名单统计和国家地图。较早的同一更新记录写明应用内的 Network 与 DNS 日志视图，点 DNS 记录可看名单原因，Network Log 的操作片可针对应用或 IP。它们是版本记录，不能单靠文字判定现在所有视图怎样并排。

**可溯源的用户问题。** 项目[2025 年用户请求与维护者回复](https://github.com/celzero/rethink-app/issues/1872)记录了一个具体困难：被拦的 DNS 名称若无法看出请求它的应用，就难以做应用例外；维护者后来指向更新的 DNS 日志界面。这是一个个案和改进线索，不是当前版本仍缺应用归属的证明。设计启发是：DNS 查询和连接必须分别计量，但若用户从其中一类记录不能到达同一应用及处理来源，分开就会变成断裂。

### PCAPdroid：未知应用时先扫连接；噪声和记录缺口必须可见

**用户指南。** [快速入门](https://emanuele-f.github.io/PCAPdroid/quick_start.html)描述 Connections 每行显示应用图标/名称（未知时问号）、目标名称或 IP、状态、最后时间及传输量；Apps 视图给应用总量，从应用可进入其连接。用户可以按应用、主机、协议等搜索，也可从一条连接长按建立筛选，持久隐藏背景噪声。文档同时说明内存记录达到上限会淘汰旧项，并显示丢弃数。[防火墙指南](https://emanuele-f.github.io/PCAPdroid/paid_features#51-firewall)描述长按连接后可阻止应用、IP 或主机，并用过滤器查看被阻止的记录。

**推论。** 应用图标和目标同一行，让没有嫌疑对象的用户可先扫全设备，再顺势收窄到应用；长按承载主要动作也可能不易被第一次使用者发现。隐藏噪声是有用的工具，但不能把「已隐藏」「已淘汰」「没有记录」都显示成空白。PCAPdroid 明示丢弃数的做法比静默缺失更可取；它的捕获范围与 Sakamoto 目标能力不同，不能直接照搬数据覆盖承诺。

## 跨产品模式与我们不应照搬的地方

1. **无嫌疑对象时，变化是入口；找到后，应用成为主角。** Little Snitch 和 GlassWire 都把一段时间里的变化连到应用列表，Portmaster 的演进说明纯监视器对新用户可能太陡。Sakamoto 不必在「全局仪表盘」与「应用首页」之间二选一：从全设备图选一个时段，下一屏应直接出现该时段有活动的真实应用，随后沿应用进入记录与决定。
2. **图、列表、地图和规则需要共享选择，但不能共享错误口径。** Little Snitch 的图表选择过滤连接列表；GlassWire 点击峰值暂停以便阅读。Sakamoto 可借用这种稳定的选区关系；DNS 查询次数、连接次数、发送/接收字节仍分别标名和计量。地图只表达有地理依据的连接去向，不把 DNS 请求的名称推成实际连接地点。
3. **可观察性和控制是两次不同的确认。** 看到阻止原因后可直接进入适用规则，如 Little Snitch 的对应/最近使用规则；创建或修改规则后，需要分别反馈保存与生效，等新活动出现才谈观察效果。LuLu 的进程默认范围提醒我们避免把「阻止此目标」暗中放大成「阻止整应用」。
4. **空白和漂亮图形都不是结论。** GlassWire 指出图的尺度会变化；PCAPdroid 明示记录淘汰；Little Snitch Linux 对 DNS 名称的推断作出界定。Sakamoto 应清楚显示所选时间、单位、覆盖与未知事实。图像使人好奇，不能代替「这些数字到底来自哪些活动」的可追溯性。

## 对当前 app-first 原型的可证伪启发

以下是待原型走查的设计假设，不是从竞品直接推出的唯一答案；按手机、平板和 Linux 可变窗口分别验证。

| 假设 | 在原型中检验的动作与失败信号 |
| --- | --- |
| **给不知嫌疑应用的用户一条全设备入口。** 保留应用作为熟悉的主入口，同时把全设备传输变化与阻止/新活动做成可进入的同一时间视图。 | 不先告知应用名，让评审者点一段变化；若只能看到无来源的总字节或必须逐个打开应用才能找到贡献者，就失败。当前手机首页图位于应用列表之后，应特别检查 393×852 首屏是否发现它。 |
| **全设备选区应立即收窄到应用，而非跳入原始日志。** 图上所选时段必须带到应用排序、连接/DNS 记录和返回路径。 | 从图点时段→认出应用→看一条具体结果→返回；若时间丢失、回到全部记录、或实时刷新使选中行跳走，就失败。当前 `graph('all')` 进入活动后应检查是否先帮助用户认出贡献应用。 |
| **全局观察仍保留 DNS 与连接的两条口径。** 同一范围可看到传输量、连接数与 DNS 查询数，但不能相加。 | 选一段有 DNS 阻止而无对应连接的时段；若界面把 DNS 阻止计成「连接被阻止」，或从拦截 DNS 推断所有连接都未建立，就失败。记录要能追到应用、名单/规则来源。 |
| **变化、故障和数据缺口不是同一种空白。** 运行暂停后历史仍可查，覆盖不完整时图与列表应同时标记。 | 返回应用一小时后，分别模拟正常无新记录、运行暂停和记录被淘汰；若三者都只显示「0」或空图，或图的量尺/时间范围不明，就失败。 |
| **从全设备发现到决定后仍回得去。** 观察选区、应用、记录、规则来源与结果形成一条可返回的线。 | 从全设备峰值找应用并调整规则，再返回原时段；若只见保存成功却找不到那条历史记录，或把新规则已生效画成历史访问已改变，就失败。 |

本研究不为六款产品排「赢家」。它们分别在异常提醒、时间图、应用列表、规则控制和记录细节上作取舍；Sakamoto 需要用同一条用户任务检验取舍是否连贯。所有外部事实以上述第一方链接为依据，页面访问日期均为 2026-09-29。
