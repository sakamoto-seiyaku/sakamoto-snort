## 3. 按优先级排列的问题

以下顺序表达本次评审认为应先解决的设计问题，不是执行队列。

| 优先级 | 问题 | 原型中的表现 | 设计影响 |
| --- | --- | --- | --- |
| 1 | 产品主线不够清楚 | 总览、活动、控制分别展示许多信息，“找到应用 → 理解访问 → 改变控制 → 查看效果”没有形成自然连续的体验 | 用户需要自行寻找主要任务，后续页面组织缺少共同依据 |
| 2 | 操作和状态容易产生误解 | `Allow` 容易被理解为保证放行；多个绿色运行标签与观测异常并列；保存与生效未得到足够清楚的区分 | 用户可能误判实际控制效果，影响产品可信度 |
| 3 | 不同概念混在一起 | 规则页展示默认放行的命中结果；配置、历史结果与诊断混杂；句子编辑器把 Block、Explain 等不同性质的操作并列 | 用户难以判断自己正在修改什么、查看什么 |
| 4 | 真正的内容出现太晚 | Control 重复出现 Apps、数量、摘要、Direct apply、搜索和筛选，应用列表被推后；Activity 的时间和网络控件占据大块首屏 | 常用内容被页面框架挤压，扫描与操作效率下降 |
| 5 | 常用操作路径绕行 | 活动先预览再进入列表，同屏重复 View flows / View all flows；应用详情将相关内容分散到多个标签 | 用户需要跨页拼出原因、规则和结果 |
| 6 | 规则编辑增加新的学习负担 | Grammar slots、Scope、Safety、Compiled effect 等术语过多；句子与字段重复表达；未来能力与当前操作并列 | 句子可读的优势被额外概念和选择抵消 |
| 7 | 排版影响阅读和操作辨认 | 本次 Control 渲染中 Wi-Fi 标题断行，Allow 按钮文字挤压；长应用名、地址和按钮文字需要稳定容纳 | 操作对象和标签难以辨认，属于基础完成度问题 |
| 8 | 视觉元素普遍用力过重 | 大量粗体、卡片嵌套、圆角和阴影；辅助内容与主要内容采用近似强调程度 | 页面缺少明确视觉主次 |
| 9 | 颜色和装饰承担过多表达 | 浅色稿大量使用绿色徽章；深色探索稿大量使用荧光绿、等宽字体和描边 | 状态、操作、选中与装饰的区别不够清楚，风格占据过多注意力 |

两套视觉稿是不同探索方向，应分别评价其阅读与操作效果；不能仅因它们外观不同就认定产品必须统一采用其中一套。

本次认为值得保留的设计素材包括：应用快捷控制、从访问记录创建规则、可读的规则摘要，以及明确的异常与恢复入口。保留这些价值不要求保留原有页面结构。

## 5. 设计与补齐功能的建议顺序

用户提出的问题是：先把旧原型改到符合本次设计标准，还是先补齐所有功能再改设计？

本次建议：**先对齐功能与产品语义，再设计核心流程，随后按同一套交互规则逐步补齐页面。功能梳理完整在先，页面建设分批进行。**

后续补充：对齐时同时记录产品价值、首版范围、当前实现和平台适用性。Android/Linux 共享核心任务与规则语义，分别验证触控小屏和桌面窗口；预演、debug 与地图应作为产品层设计对象参与布局，不以数据面是否已有同名功能作为纳入标准。

先美化旧原型，会把已经变化的产品语义与页面结构继续固化；把全部当前功能直接塞进旧页面，会放大原有分类与信息层级的问题。功能与状态应当成为设计输入。

### 第一步：形成完整的功能对应表

以当前能力为底账，对每项功能记录：用户要完成的任务、真实能力与状态、旧原型对应位置、可沿用或需重新设计的部分，以及前端数据接口是否齐备。

完整盘点不要求每项功能都出现在首屏。应区分主要入口、详情或高级入口、仅诊断能力与待确认产品能力。默认不因视觉简化删去已有能力；改变产品范围需单独讨论。

第 4 节是这项盘点的起始材料，后续应依当前代码和验收逐项完善，而非根据旧页面数量定义当前功能范围。

### 第二步：确定产品对象与核心路径

先说清应用、规则、共享规则组、活动记录与运行状态之间的关系，再安排导航与页面。对每项已有能力明确可到达的位置，避免后续补功能时只能继续增加平级入口。

本次提出“应用作为默认入口、顶部紧凑呈现运行状态”作为候选；独立总览是否保留、顶层导航数量、规则库位置和具体视觉风格仍由后续讨论与走查决定。

### 第三步：用少量完整流程验证新设计

第一轮原型建议覆盖三类代表性场景：

1. 日常控制：找到应用 → 查看访问及实际结果 → 调整快捷控制或创建规则 → 查看是否生效。
2. 复杂控制：组合条件或共享规则组 → 明确作用应用和执行模式 → 修改配置 → 检查保存与生效结果。
3. 异常与恢复：授权缺失、启动失败、修改未生效或记录不完整 → 理解影响 → 执行对应恢复动作。

这些场景用于检验设计是否同时容纳简单操作、当前高级能力和真实失败状态。原型使用 mock product state，优先解决本次问题排序中的产品主线、含义与对象关系；排版与视觉规则同步建立。

### 第四步：扩展其他功能并检查一致性

核心流程成立后，将其交互模式用于其他条件、规则维护、导入导出、统计与设置。每加入一类功能，都检查它与已有对象、入口、反馈和异常表达是否一致。

功能扩展与设计验证交替进行。最后检查整套界面的密度、用词、颜色、长文本、字体缩放和状态覆盖，避免把视觉设计拖到所有页面完成后才处理。

### 用户确认的 HTML 原型设计流程

1. 用功能清单确定本轮覆盖范围与平台差异，标明 checkpoint 首版暂缓，以及仍需讨论的范围项目。
2. 直接以 HTML 原型探索导航、页面、操作和真实文案。采用 mock product state，使输入、选择、编辑、查看结果和异常恢复可以实际走查。
3. Android 与 Linux 共用产品对象和设计语言，分别提供手机与桌面布局；在同一原型总览中检查两个平台，包含桌面窗口变化和鼠标/键盘操作的设计。
4. 从核心流程开始，逐步把本轮确认范围内的功能全部补入原型。少量关键页面是设计起点，不代表全部功能设计完成。
5. 每轮用下表评价交互和视觉，用户反馈直接落实到 HTML。每项功能均能定位到入口、操作、结果和相关状态，双端差异可检查后，再确认设计。
6. 原型确认后形成正式规格与 Plane 实施任务，再按已约定流程委派实现并验收。原型需要的新数据或后端行为记录为设计依赖，不能用 mock 演示充当真实能力验收。

原型阶段覆盖功能表达、用户操作与状态，不需要实现真实包处理、持久化、精确规则预演或地理数据服务。预演/debug/地图同样应设计其输入、输出、加载、失败与数据不足状态。演示数据的性质在原型说明中标明。

### 每轮原型的设计评审标准

“乔布斯式”在这里是本次借鉴的设计取向，具体评审标准由本项目负责，不能作为本人会作何决定的断言。

| 原则 | 在原型中检查什么 |
| --- | --- |
| 聚焦 | 当前页面的主要任务能否一眼找到；主要操作是否被摘要、装饰或工具挤压 |
| 直觉 | 入口、文字和控件是否直接表达用户意图；下一步与返回路径是否自然 |
| 精确 | 操作、状态、统计单位和作用范围是否真实；保存与生效、声明与实际动作是否清楚 |
| 克制 | 标题、卡片、颜色与选项是否各有用途；复杂能力能否在需要时出现 |
| 连贯 | 应用、活动、规则、预演和诊断是否能带着上下文自然衔接；双端是否保持一致含义 |
| 完成度 | 正常与异常路径、长文本、未知数据、不同窗口和主要输入方式是否都经过走查 |

## 后续定位讨论：设备掌控、流量理解与 DNS

用户在复查完整原型后明确：运行状态、规则与实际执行、用户理解自身设备的流量，都是核心产品任务。地图只是其中一个视角，流量理解不能降为扩展工具或附属统计。

用户进一步明确 Android 与 Linux 后续会接入 DNS 拦截，应在本轮产品概念中统一考虑；这不是当前 DNS 拦截实现或交付证明。DNS 拦截统计与连接/包规则统计保持明确口径，不随意合并。

用户随后补充的确定关系：

- 域名资料包括用户自行添加、一次性文件导入和基于订阅文件的更新；这些维护方式需要分别表达。
- 域名列表可直接供 DNS 拦截消费，也可供规则/规则组引用为匹配资料，不能只按单用途阻止名单组织。
- 未来可以提供通用规则或规则组，例如用户提到的局域网扫描、跟踪及内容类别控制，但须在交互和含义充分清楚后再设计内置内容。
- 用户给出的愿景是：用户能够控制、明确感知自己设备的流量，形成对自己设备的实际掌控。

本次只校准确定的列表、导入与订阅术语。域名组是否是独立层级、规则组能否直接具有公共条件、订阅更新及本地修改的交互、具体 DNS 动作和内置方案均继续讨论；没有因这段愿景讨论更改原型页面、规则执行合同或实现排期。


## 品味与直觉专项批评：2026-09-29 后续讨论

用户认为此前成熟交互提案虽然方向改善，但失去乔布斯式的品味、用户直觉和友好，再次明确要求子代理按该视角协助批评。本轮复用两个指定的 `gpt-6-sol / xhigh` 子代理，只进行一轮、只讨论、不改原型。

共同批评是：顶层分类迫使用户替系统组织任务；精确范围被展开成通用表单；结果与版本说明占据了操作后的主要体验。建议将熟悉的应用与真实目标作为可直接触碰的对象，范围紧贴当前决定表达，必要复杂性按需展开；保存与失败在原位置持续反馈，保留历史结果和返回位置。

主代理取舍：不采纳将流量可视化整体退入次级入口的建议，这会违背用户已确认的同等核心地位。下一方向应将清楚的流量变化与对应应用/活动放在同一可操作画面，用选择和展开建立关系；同时削减占据首屏的口号、巨型保护图形和重复卡片。

审美参照核对了 [Steve Jobs Archive 收录的本人访谈](https://book.stevejobsarchive.com/)中 “On the Macintosh” 和 Michael Moritz 访谈：熟悉的表达方式、使用中的愉悦、视觉眼光与精确细节。由此进行的 Sakamoto 设计推演属于本次建议，不声称是乔布斯本人会选择的具体方案。

本轮没有重新冻结主导航或完整页面结构。按功能正确性整理好的状态与范围仍是设计约束；用户首先接触的画面、直接操作和反馈手感需要据此重新推敲。


## 完整目标产品前提下继续推敲

用户明确：当前设计图直接按 DNS 拦截与接入、IP 等信息已经存在来设计，不迁就已有功能。产品愿景文档已同步这一原型能力前提；此处没有更改真实实现状态。

复用两个指定子代理进行一轮乔布斯式品味、直觉与友好视角的讨论，保留的设计方向是：传输变化和 DNS 查询沿同一时间轴组织，单位与统计分开；图中选择与真实应用、目标列表直接联动。应用详情先显示去向与结果，再在同一上下文展开名称查询、解析地址和连接的关联，以及对应控制。

对子代理不同动作方案的综合：操作默认范围应贴近用户明确选中的对象。选择目标名称时可表达完整目标控制意图；选择一笔 DNS 查询或某个 IP 时，先呈现该项的精确动作。操作前以自然短句显示对象、目标和作用范围，详细调整保持可达，不要求用户先选择底层执行机制。

共享域名资料与局部控制关系仍需可追溯；DNS 查询被阻止时显示该阶段的实际结果，不把它自动等同于所有相关连接都停止。上述是继续推敲的交互方向，尚未据此冻结导航或重新实现原型。


## 用户纠正：熟悉的应用必须贯穿所有深入页面

用户批评上一方案仍以域名/IP 作为主要理解对象，要求重读乔布斯；随后强调，从首页点击进入到详细活动等完整路径，都必须保持乔布斯式的品味、交互、逻辑与连贯性。

重读 [Steve Jobs Archive〈On the Macintosh〉](https://book.stevejobsarchive.com/)中电报与电话的类比后，复用两个指定子代理作一轮应用优先审视。产品愿景已明确：应用是默认体验的持续主体，流量和控制围绕用户认识的应用组织；域名、IP、DNS 与具体规则在用户深入时作为事实与精细手段出现。

主代理取舍：不采用应用行需要先点选、再点击才能进入的隐含双重操作；手机点应用直接进入，宽屏在旁展开同一应用。也不采用“DNS 拦截所以所有连接都未建立”的因果推断，或将不同记录简单合并为一个“联网次数”。详细活动必须保留区分记录所需的真实目标与结果，应用优先不能变成模糊文案。

本轮只校准已明确的产品设计原则，没有重写原型。此前以目标/地址或 DNS 曲线作为首要认知入口的讨论不再作为默认主线。
