# 新建规则体验：A 席判断与实际互问

2026-10-02，阶段二完成；gpt-6-astra / low / priority（fast）。先独立写稿，父代理读双方后再实际互问。
这份建议未获用户确认；只讨论创作体验，不改变正式边界，不作实现或实测声明。
已读产品愿景、规则 Tab 重开记录、Jobs 方法复查；本轮在线实际读了 2007 员工讲话及 Macworld 节选。

## 首选：从动作开始，第一下就改变同一份内容

我首选让首次用户从可认出的“阻止”动作开始；不先选“隐私保护／省流量／名单规则／高级规则”等目的或模板。
新建出现的核心邀请是“要怎样处理连接？”，可选动作以动词呈现；本案选“阻止”，其他动作的全集不在本轮冻结。
选下后原位置形成“阻止〔选择目标〕”，这是尚未完成的当前规则；不是进入另一种规则类型的通行证。
紧贴内容提供“限定网络”；应用使用范围另以“给哪些应用使用”明确显示，未选就写“尚未选择使用者”。
选择目标时直接认出已有名单 L，旁有稳定可见的“连接：协议、端口…”；不先选名单类别，也不划定整条规则类型。
名单多时在此搜索、滚动，连接入口不被挤到长列表末尾；连接特征展开适用的精确控制，不靠自然语言解析。
我拒绝空白句子加一排同权占位符；也拒绝替用户默选全部应用或把未完成目标解释为全部连接。
这比“同一表达从零构成”多承担一次明确动作选择；所得价值应是人在第一刻知道自己正在做什么。

## 主案：浏览器只在移动网络下阻止名单 L

| 看见与操作 | 当前内容、作用对象与下一步 |
| --- | --- |
| 规则 Tab 无规则，点“新建规则” | 出现上述动作邀请；无使用者、无默认生效内容。 |
| 选“阻止”，点“选择目标”，直接选已有 L | 当前读成“阻止名单 L 中的域名”；网络尚未限定，内容旁明确显示“所有网络”，可点改。 |
| 点“限定网络”，选“移动网络” | 读成“仅在移动网络下，阻止名单 L 中的域名”；名单依旧可点开核对、替换。 |
| 点“给哪些应用使用”，选浏览器 | 规则内容保持上述读法；作用区显示浏览器图标、名称，主完成动作变成“保存并给浏览器使用”。 |
| 执行完成动作 | 同一内容呈现保存结果和真实使用状态；只有实际启用成功才写正在使用，待处理或失败如实呈现。 |
| 按需点相关活动，再返回 | 活动保留该规则、浏览器与查看时间范围；无对应记录就写暂无记录，返回仍是刚完成的内容。 |

“仅在移动网络”约束这条规则，不承诺其他规则不会阻止 Wi-Fi；解释需要时可读，不把无关规则展开成完成门槛。
保存结果与活动证据各说各的事实；成功建立使用关系不是已观察到一次拦截，不能用庆祝文案混成一个成功。
若用户明确持续编写，完成反馈留在当前工作内，允许继续改内容；不强迫离开再打开。

## 反验：三个应用在 Wi-Fi 下禁止 UDP 目的端口 443

同样由“新建规则 → 阻止 → 选择目标”开始；这次选连接特征，选 UDP，再设置“对外连接，目的端口 443”。
这些是实际选择与输入；当前读回“阻止对外 UDP 连接，目的端口 443”，方向和目的端口不缩成含混的“UDP443”。
点相同的“限定网络”选 Wi-Fi，再直接多选浏览器、视频、播客；无须预建 AppGroup 或 RuleGroup。
完成前读到“Wi-Fi 下，阻止对外 UDP 目的端口 443”，作用区逐个认出三个应用，主动作“保存并给 3 个应用使用”。
完成后显示同一内容和真实使用结果；活动可按其中应用查看并返回，没有记录同样不伪造执行证据。
本案对外 UDP 目的端口 443 是演练假设；不借此冻结所有端口创作的默认方向，也不把三选结果定义为持久应用组。

## 待用、改错与最小深度

待用：内容完整却没有使用者时，主完成动作是“保存待用”；完成显示“已保存，尚未给应用使用”，规则仍能直接继续编辑。
已选浏览器时，主动作旁直接有“仅保存待用”，旁注“不用于已选应用”；选它即完成待用，并舍弃本次浏览器候选。
改错：误选 Wi-Fi 后直接点当前内容中的 Wi-Fi 改为移动网络；取消该选择器则保留原值，名单、动作和应用选择不丢。
内容修改在明确完成前不采用；正在使用的旧内容也不因每次点选就改变，当前修改与已使用版本须能辨认。
追加 OR：在主案情况块下可发现“添加另一种情况”；原块“移动网络＋名单 L”原位保留，新块有自己的目标和网络。
新支用相同目标选择器选“对外 UDP，目的端口 443”，网络选 Wi-Fi；读回“以下任一情况阻止：移动网络且命中 L；或 Wi-Fi 且对外 UDP 目的端口 443”。
浏览器仍是整条规则的使用者；保存修改后才采用两支结果，不把 Wi-Fi 条件误挂成两支共有条件，不要求换类型或重写原支。
这里愿付从一句话长成两段的空间代价；原分支可认、或的范围可见，比强挤成一行更重要；规则组仍是内容，应用组仍是作用对象。

## 最强反案、删减与可推翻条件

强反案是新建就出现可直接点改的可读表达，动作、目标、网络随内容渐成；人从已经知道的名单 L 开始也合理，不必先回答动作。
它不是 JSON 表单：已选内容成为主角，空缺只显示当前必要处，复杂分支在原对象上展开；这比目的菜单更统一，也可能比我首选更自然。
我仍暂选动作先行，因为“阻止”给后续名单和连接特征一个可预测的关系；代价是本来握着 L 的人必须先声明显然的动作。
具体删掉：目的卡片、按名单或端口锁死的规则类型、强制命名、强制归组、另一个高级编辑器，以及初始屏上的完整字段全集。
独立稿挑战曾追问 B 空白起步；读稿后撤回这一假设：B 实际同样先选动作，没有把用户留在抽象字段表。
独立稿保留的有效疑问是分支作用范围和内容发现；阶段二按对方实际方案重新发问，完整往返如下。
可推翻我：若同样未经说明的演练中，用户能从可读表达直接选 L 并准确补齐作用，而动作邀请让他们停下猜测规则类型，我应撤掉这道邀请。
Jobs 员工讲话用电话会议说明存在功能不等于人能发现；Macworld 讨论控制适应当前用途。以上取舍是我的推论，不是 Jobs 指定的流程。[一手节选](https://book.stevejobsarchive.com/#speech-to-apple-employees-2007)、[Macworld](https://book.stevejobsarchive.com/#speech-macworld-2007)
精确体现在每次修改能读回真实含义，整体性体现在开始、深入、完成、查看证据与返回始终认得同一规则；它们不是额外装饰。

## 阶段二：四项真实问答与修正

A 问 B：内容选择器到底直接列 L 还是先选名单类别，名单多时如何让 UDP 仍可发现？
B 答：首层直接列 L 等名单，稳定保留“连接：协议、端口…”；名单支持搜索滚动，连接在局部选择区展开，承担额外深入成本。
A 接受：我初稿先选名单类别是可删的分类门，现已删除；这项改变来自真实质询，不把合流记成某席胜利。
A 问 B：已选浏览器后只保存待用，具体做什么，候选去哪，怎样不造永久计划使用对象？
B 答：主动作旁可见“仅保存待用”，说明不用于已选应用；完成显示“已保存，尚未用于应用”，舍弃未提交候选，之后重新选择。
A 接受并收准：采用这个收尾，愿付日后重新选浏览器的代价；当前候选从未是生效范围，不保留模糊的待执行安排。
B 问 A：为何先选名单类别，愿否直接显示 L；动作先行究竟比认出 L 赢在哪里？
A 实答：删除类别选择；动作先行只提供“这份名单将被怎样处理”的明确关系，不证明更熟悉，愿付先声明动词的注意成本。
B 问 A：新增 OR 时移动网络怎样不从全局偷偷迁到分支；改成允许是否锁型？
A 实答：从第一支开始，移动网络与 L 同属一情况块，共同动作在块外；追加只在下方增加“或者”及新块，没有范围迁移。
A 因此改掉“再加一种阻止情况”的写死文案；点共同动作改为允许后，两支保留，读回“允许以下任一情况：……”并待明确完成。
这仅证明编辑动作可逆，不规定允许与其他规则的冲突优先级；双方没有提出同题追问，四项主问答均已实际完成。

## 最终取舍仍须兑现的细节

我保留动作先行作为当前首选，不另造“阻止名单／限制连接”用途菜单；双方的事实共识不能证明这个首选已经自然。
“所有网络”是当前情况没有网络限制的真实读法，内容一选定就可见可改；它属于情况块，不是页面全局开关。
我选择这个可见默认并承担用户必须主动收窄的成本；强制先选网络会把不需限定的人也送入一轮问答，当前不取。
第一支的自然读法仍可一句读完，但其网络和目标在同一块内；新增分支时只增加结构，不重新解释旧句子的范围。
双方已在实际动作层面合流，没有剩余实质二选一争议；动作先行及默认网络是否真能自行发现，仍需后续演练检验。
