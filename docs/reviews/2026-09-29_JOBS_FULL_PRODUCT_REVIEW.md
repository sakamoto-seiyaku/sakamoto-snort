# Sakamoto 完整交互原型产品审视

2026-09-29 · 独立评审 · 目标：`app-first/` 的 46 个产品 HTML 与 `index.html` 总览。判断依据见[一手材料阅读札记](2026-09-29_JOBS_DESIGN_READING.md)，其问题编号在下文简称“准绳 Q”。这里的判断是我从材料推演出的产品批评，不代表乔布斯本人会如何评价 Sakamoto。

## 整体裁决

**主线有价值，整体尚未达到“看得见、能决定、可验证”的可信门槛。** 从首页认出应用，走到连接的近期收发、整条累计、DNS 关联和当时处理依据，再调整这个应用的访问规则，这条路已具备鲜明的产品性格。界面克制，应用图标、名称和可观察范围大多比内部术语先出现。它应成为后续收敛的骨架。

最伤产品的地方发生在用户将要**相信一个决定**时：完整替换配置前看不见条件变化；防火墙不运行时，恢复页却说它仍在判断；一条只观察、实际允许的规则，在高层视图以红色“阻止”主导。它们分别使用户无法审查自己的决定、无法相信运行状态、无法理解控制是否真的执行。细节打磨不能替代这三种语义一致性。

我按已确认愿景评价目标产品：DNS/IP/应用关联能力视为存在；前端样例不接真实后端本身不扣分。下面每项都区分观察事实与设计判断。严重度按误导决定、阻断任务和影响范围排序：P0 是可能使用户作出错误控制判断的主线问题，P1 是重要能力或语境断裂，P2 是较窄路径的完成度问题。

## 按影响排序的发现

### 1. P0 · 配置“审阅”看不见真正将改变的规则

**事实。** 从 `config.html` 导出配置，只把 `configuration.rules` 中 `r2` 的目的地址条件从 `192.168.0.0/16` 改为 `0.0.0.0/0`，规则数量、名称、组、分配和列表数量均保持原样；粘贴到 `config-import.html` 并检查后，`config-review.html` 仍只显示 `5→5 / 1→1 / 3→3 / 2→2` 和五个原规则名称，然后要求“确认替换配置”。[变更后的审阅截图](assets/2026-09-29-jobs-review/import-review.png)。原样导出的配置也经过同一路径成功替换并显示已保存、已生效；保存失败和已保存未生效分别有明确结果，所以问题集中在**确认前**。

**判断与代价。** 审阅页承诺“确认将要改变的内容”，实际只审数量和名字。用户无法发现一个允许规则从局域网扩大到全部 IPv4，仍被要求确认整套配置替换。违反准绳 Q6（可核对结果）、Q8（稳定对象关系）、Q12（重要能力不能在简化时丢失）。

**有限改法与验收。** 保留完整导入、导出和一次性替换；在确认页按“新增 / 删除 / 已改变”列出规则、条件、动作、作用对象、执行方式及域名列表引用，默认展示影响访问范围的差异，技术原文按需展开。验收：导入同名同数量但 `r2` 从 `/16` 改为 `/0` 时，用户在按确认键前能指出具体扩大了什么、影响谁。

### 2. P0 · 恢复页与全局运行事实互相否定

**事实。** 新会话打开 `runtime.html?scenario=permission`，运行页写“等待授权”“当前不执行网络控制，也不记录新访问”；点击该页“恢复与诊断”进入 `recovery.html`，却出现“运行没有待处理故障”“运行与记录状态正常”“无需操作”“防火墙继续判断访问”。[运行页](assets/2026-09-29-jobs-review/runtime-permission.png)与[从运行页进入的恢复页](assets/2026-09-29-jobs-review/recovery-permission.png)。主动暂停及已保存未生效的启动场景也复现相似的正常文案。顶部小状态徽标在待授权、暂停、需处理时仍使用近似运行中的绿色视觉语气。

**判断与代价。** 用户会把恢复页当作故障事实与下一步的权威来源；这里它既没有继承“不保护、不记录”，又给出“继续判断”的相反结论。主动暂停不必叫故障，但必须明确“因你暂停，所以未保护”。违反准绳 Q2、Q6、Q9。

**有限改法与验收。** 从同一运行状态模型生成恢复页的标题、过程、当前影响与行动：待授权→去授权，主动暂停→可恢复，自动恢复中→有限重试，需处理→检查条件，配置待生效→处理配置。视觉状态也随保护是否实际在工作而变。验收：从这五种运行页分别点“恢复与诊断”，任何页都不能同时写“不执行控制”和“继续判断访问”。

### 3. P1 · 规则定义的“阻止”压过实际的“仅观察、允许”

**事实。** `rules.html` 的“观察远程访问”卡片以红色“阻止”标记，并写 1 个控制对象。进入 `rule-detail.html?id=r4`，顶端仍以“阻止”为主；同一首屏下方才看到 Firefox 的分配是“仅观察 · 命中后实际允许”。[规则详情截图](assets/2026-09-29-jobs-review/observe-rule-detail.png)。`app-controls.html?app=s1` 的“正在使用的设置”还列出这条规则，摘要只写“连接 · 用于这个应用”，未告诉用户实际允许。

**判断与代价。** 规则动作确实是“阻止”，但执行方式已把它改成观察；产品必须同时表达这两个事实。现在高层标签让用户以为这条规则会挡住 SSH，关键限定需要在局部文字中重新发现。违反准绳 Q5、Q6、Q8。

**有限改法与验收。** 在规则卡片和应用设置摘要的主信息位显示“Firefox：仅观察，实际允许”，把“规则定义：阻止”作为第二层；若不同对象执行方式不同，显示“作用因对象而异”并逐个展开。保留观察模式、规则动作和完整分配能力。验收：只看列表与 Firefox 设置，用户能正确回答“该访问由这条规则决定时，允许还是阻止”。

### 4. P1 · “订阅”只剩来源标签，资料生命周期没有入口

**事实。** `domains.html` 将“跟踪域名”标为“隐私名单订阅”。[列表详情截图](assets/2026-09-29-jobs-review/domain-subscription.png)呈现条目、引用它的两条规则、编辑和删除；编辑页只有“来源说明”自由文字与域名条目。没有可辨认的订阅地址、上次/下次更新、更新失败、暂停/停止更新、更新与本地改动关系的界面。手动创建和一次性导入已实走成功；导入预览还会指出不支持的 Adblock 行号，这些能力应保留。

**判断与代价。** 用户能看到资料被谁引用，却无法判断“订阅”是否仍新鲜、何时改变、失败后如何处理，或本地编辑会不会被下一次更新覆盖。已确认愿景要求来源和维护方式与使用方式分别表达；目前“订阅”像手动列表加一行来源文案。违反准绳 Q4、Q5、Q8。

**有限改法与验收。** 在列表详情加入明确的“来源与更新”区：来源位置、最近检查与结果、下一次/手动更新、失败处理、本地例外的规则；“被规则/DNS 拦截使用”继续作为独立区。更新频率和例外合并策略仍可讨论，但必须让用户找到它们并知道当前采用什么。验收：一个订阅更新失败、用户又加了本地例外时，他能在列表详情说清当前用的是哪版资料、谁在使用、下一步怎样修复。

### 5. P1 · 所选时段与“现在”的连接状态在同一行混读

**事实。** 首页选 `09:21–09:26` 到 `contributions.html` 后，标题、总量和比例都指这五分钟，天气行却写“09:38 · 正在发送”，Signal 行写“09:36 · 正在接收”。[时段贡献截图](assets/2026-09-29-jobs-review/time-contributions.png)。同一时段的音乐地图显示日本 `0 B`；进入 `location.html`，顶端仍是本时段 `0 B`，下方连接行突出 `09:41` 快照的 `109 KB/s` 与整条累计 `1.7 MB`。[地区详情截图](assets/2026-09-29-jobs-review/time-location.png)。这些数字各自可能正确，连接也应因存续区间相交而继续列出。

**判断与代价。** 问题是三个时间口径没有足够清楚的视觉分层：时段内传输、当前速率、整条连接累计。用户可能以为 09:38 的状态或 1.7 MB 都发生在 09:21–09:26，进而误判图表和规则效果。违反准绳 Q2、Q6、Q8。

**有限改法与验收。** 保留长连接及近期/累计信息；在贡献行先给所选时段的事实，把“最新状态 09:38”放次级位置并明确标签。地区详情先列本时段流量与存在状态，另设“09:41 连接快照 / 整条累计”的清楚分隔。验收：用户能解释“这五分钟日本是 0 B，但该连接现在有传输”，而不以为数字冲突。

### 6. P2 · 总览仍发布一条会丢失筛选的旧路径

**事实。** `index.html` 仍链接独立 `activity-filter.html`。从该页选“已阻止”再点“查看结果”，得到 `activity.html` 的全部 `14` 条连接、`30` 次查询；允许的 Firefox 连接也在列表中，且看不到已启用筛选的摘要。[返回结果截图](assets/2026-09-29-jobs-review/legacy-filter-result.png)。主活动页自己的筛选面板选“被阻止”则正确只显示 1 条被阻止连接和 20 次被阻止查询。

**判断与代价。** 同一产品提供两套名字相近、结果不同的筛选路径；总览给出的可操作页面使用户以为“查不到是因为记录不在”，实际是筛选意图丢了。虽然该入口比主面板窄，仍破坏完整产品的一致性。违反准绳 Q7、Q13。

**有限改法与验收。** 让总览链接进入主活动筛选面板，或让独立筛选页与主列表共用同一筛选状态、结果摘要及返回上下文；保留对象/结果/时间等高级筛选。验收：从两种入口选择“已阻止”后，列表相同且能看见与修改当前筛选。

### 7. P2 · 820px 平板首页把最重要的数字拆散

**事实。** Android `820×1180` 的 `home.html` 已切成两列，但左侧指标卡把 `9.4 MB`、`1.9 MB` 的数值与单位拆成两行，趋势图随之压窄；同屏下方还有大量可用空白。[平板首页截图](assets/2026-09-29-jobs-review/tablet-home.png)。393px 手机和 1440px Linux 首页的这组数据均保持紧凑完整。

**判断与代价。** 首页最先让人读懂“这台设备做了什么”，此处为追求并排而牺牲数字整体性。视觉系统整体干净，但这个断点显出模板优先于内容的选择。违反准绳 Q10、Q11。

**有限改法与验收。** 以指标最小可读宽度决定断点；可让图表跨整行、应用列表下一行，或调整卡片比例/数字排版。保留平板并排查看的能力。验收：820px 上两项“数值＋单位”各成一体，图表仍可辨认时段，首页信息不比手机更难读。

### 8. P2 · 原型自带的配置示例进不了自己的审阅页

**事实。** 在新的独立会话中，于 `config-import.html` 点击“载入一份演示配置”，再点“检查并审阅”，页面停留原处，只说“分配引用的内容不存在”，没有指出哪项分配、引用了什么、如何修复。[错误截图](assets/2026-09-29-jobs-review/import-demo-error.png)。同一入口粘贴原型自己导出的配置可成功审阅并保存；因此不是整个导入能力不可用。

**判断与代价。** 这是具体示例内容的完成度故障，也暴露导入失败反馈不能支持修复。它排在末位，不应掩盖前述信息架构问题。违反准绳 Q9、Q14。

**有限改法与验收。** 修正内置示例；校验失败时指明分配项、缺失的规则/组/对象及可操作修复，保留用户已输入的 JSON。验收：内置示例能到审阅页；故意断开一项引用时，用户不用通读整份 JSON 就能找到它。

## 值得保留的决定

- **应用先于技术名词。** 首页、应用详情、活动、连接详情的主路径使用户先认出音乐、天气、Firefox，再看域名、IP、协议；共享 UID/未知归属也没有伪装成熟悉的应用。
- **DNS、连接、传输量的口径分开。** `view=dns-only` 能呈现 `0 B` 与多次查询阻止；`view=dns-gap` 说明记录缺口；`view=no-activity` 不把无记录说成零风险。连接详情把近 10 秒、整条累计、首次观察与当时规则分别写清。
- **改变后的时间语义较诚实。** 从一条正在接收的连接发起“只对音乐阻止此目标”后，等待生效可看到“新设置已生效”，原 `09:41` 快照仍保留旧结果，并引导看后续活动；这比改写历史有力。
- **高级能力有真实形状。** 规则组、嵌套条件、对象分配、仅观察、批量控制、资料导入、保存/生效分离、预演和诊断不是摆设。诊断停止明确不暂停防火墙，Adblock 不支持项明确报行号。这些能力应在收敛中保留。
- **平台语义基本分明。** Android 平板沿用 Android 授权/前台语义，Linux 宽窄窗沿用本机侧栏与本地运行身份；没有简单把屏宽当平台。

## 下一轮收敛边界

| 处理级别 | 具体工作 | 保持的能力 |
| --- | --- | --- |
| 必须重做 | 导入差异审阅；运行/恢复同一状态事实；规则定义与实际执行方式的主层表达；订阅来源与更新生命周期 | 完整配置替换、观察模式、DNS/连接规则、共享列表与组仍可用 |
