## Jobs 依据与审题尺度

本轮实际在线读官方 Archive：2007 员工讲话从手机困境、会议通话例子到结尾的完整相关段；Macworld 从手机难用、固定按键、动作适配到触摸方案的完整相关段。没有观看原始视频或声称读过未经节选的整场演讲。
Jobs 员工讲话原话是“easy to use and self-discoverable”；他用会议通话说明：能力虽存在，藏在手册和难记按键里仍使人无法使用。[官方讲话](https://book.stevejobsarchive.com/)
Macworld 的 Jobs 发言把固定按键的限制联系到各应用需要不同操作，以及未来功能变化；这是任务适配的论证。[官方演讲节选](https://book.stevejobsarchive.com/#speech-macworld-2007)
档案中的标题、日期背景与编者说明是编辑声音；本报告未使用 Ive 导言作为 Jobs 证据。以下操作模型是我的推论，史料不证明我们的优先级、分组继承或 Tab 数量。
我的尺度：人应能从熟悉对象发现主要动作，说出动作改变谁，并在完成后验证同一件事；少点几次不能补偿一次误判影响范围。

## 整体候选：同一个人的工作连续深入

整体主线建议是：首页看懂变化 → 全部应用快速安排 → 应用已有流 → 必要控制 → 共用与维护 → 回到原应用核对；首页、规则、设置三个 Tab 保留，入口职责仍是候选。
首页把曲线变化与同段应用贡献连起来，用户认出谁在联网；稳定的“全部应用”入口让没有活动的应用也能安排，不必先制造一条流或猜第二次点击。
APP LIST 面对熟悉应用直接改移动、Wi-Fi、有线及明确 VPN 组合的联网安排；完成留在同一应用与条件，保存、使用和实际活动分别可认。
点应用直达已有流与当前拦截内容；默认读真实域名、协议、流量，无名称才 IP，名称来源按需看。正常阅读无需先学 DNS／SNI 的数据分类。
需要控制时继续面对当前应用：直接“拦截这份域名列表”，或按当前连接明确选择协议／端口等非域名条件；没有原流也能创作，不先要求创建四种结构。
从应用建立控制，候选完成动作是“保存并用于这个应用”；随后要共用才从单规则“用于应用／应用组”。从应用或应用组“使用规则”也能得到同一种关系。
规则 Tab 提供主动创作和长期维护；一条规则仍可直接关联，只有确实要几项内容一起维护才用规则组，确实让几个应用共同接受才用应用组，名单仍提供目标名称。
共享维护从当前使用关系继续看内容、来源和“谁会改变”，改个人还是改共享成为可执行选择；不因“维护”二字转去设置或重新搜索全部对象。
完成与返回仍接回原应用、域名搜索、时段与原流；已完成的共享保存不会被取消另一份成员草稿连带撤销，历史与当前安排分别表达。
可自行发现来自熟悉对象贯穿、动作随需要出现和完成可核对；若停一个应用或改一条流仍须先学习规则／规则组／应用组／名单四种结构，这条整体候选失败。局部互辩只修补语义，不能证明整条主线已经好用。

## 故事一：两个视频应用在移动网络上停用，Wi-Fi 按已有安排

意图：通勤时禁止哔哩哔哩、抖音使用移动网络，回家仍按已有规则联网；不因开启 VPN 绕过这个决定。
起点：首页 14:00–14:30 应用贡献中的哔哩哔哩；进入完整应用列表后搜索“视频”，选中哔哩哔哩、抖音，当前排序与滚动位置保留。
主要动作：选择“禁止使用移动网络”；必要选择只问网络条件及两个应用，不要求规则命名、分组或学习完整规则语言。
条件候选：移动／Wi-Fi／有线是接入条件，VPN 是附加状态；此处直接表达“移动网络，包括经 VPN：禁用”，不会把 VPN 冒充互斥的第四种接入。
“VPN 时禁用”另可跨接入网络安排；同一条件同时命中禁用时仍禁用。组合条件可深入选，但不得由一个 VPN 图标让人猜实际范围。
保存前结果句：两个应用在移动网络禁用，Wi-Fi／有线沿用已有安排；哔哩哔哩仍拦截广告域名，抖音仍使用原有非域名规则。
保存作为一次安排更新；本候选在生效时终止这两个应用的现有移动网络流并拒绝新流，Wi-Fi 流不受影响，历史记录不改写。
完成：应用列表每个对象显示移动网络禁用及当前使用来源；若已保存而未生效，保留“尚未生效”的具体对象，不显示成功联网安排。
失败：两个对象及移动条件不丢；未保存留在该操作继续修正，保存失败不把部分成功包装成全体成功，明确哪些应用尚未改变。
取消：丢弃本次未保存安排，回到“视频”搜索、原排序与原滚动位置，两个应用的原值不变；普通返回先退回该输入层，不暗自保存。
返回：首页仍为 14:00–14:30；若进入核对，返回哔哩哔哩原活动位置与原域名流，不跳到规则库或默认“今天”。
恢复动作是“撤销移动网络禁用”，结果直接显示“移动网络按已有规则：仍拦截广告域名”；没有一个声称全面放行的“允许”开关。
撤销只恢复本次涉及的两个应用、对应条件的快捷值；若后来又改过这些值，先展示差异，不能用撤销覆盖后续决定；已有连接需重新尝试，不复活过去的流。
最强反例：用户只想现在看视频，解除禁用后仍遭域名或协议规则拦截；我的候选增加一次找拦截原因的成本，但避免无声撤销所有精细控制。
可继续完成的动作：解除禁用后，哔哩哔哩就地列出当前仍拦截它的列表与 UDP 规则；从实际受阻流进入对应“这个应用怎样使用 R”，不去通用排错首页。
若用户决定移动网络不使用其中两条 R，明确选择这两条及移动条件；预览这两个拦截在本应用移动网络上停止，其他应用、Wi-Fi 与其他规则不变，产品处理同 R 多来源。
完成分别报告两条安排的保存与使用状态，由新记录核对；取消只丢弃这次两条 R 的条件，回原流／域名搜索／14:00–14:30，不撤先前解除禁用；失败保留两条 R 与移动选择，无新记录不报视频可播放。

## 故事二：只改单个应用使用的非域名规则

意图：哔哩哔哩在家 Wi-Fi 的 UDP/443 受阻；希望它仅在移动网络拦截 UDP/443，其他视频应用保持原样。
起点：首页 20:00–20:15 → 哔哩哔哩 → 20:07、video.example、UDP/443 的原流；记录解释命中单条规则 R“拦截 UDP/443”。
R 同时来自“视频应用”组、“出差应用”组及该应用直接使用；应用页合并为一个有效决定，按需展开三处来源，避免三个相同拦截项冒充三件工作。
主要动作是针对 R 的“只调整哔哩哔哩何时使用 R”；R 原本适用于所有接入，必要输入为“仅移动网络”，不先要求复制、命名、排优先级。
保存前结果句：仅哔哩哔哩改为移动网络拦截 UDP/443；Wi-Fi 不再因 R 拦截；组内其他应用及共享 R 的内容不变，其他不同规则仍有效。
改判后的语义候选：对同一 R 的全部当前／后续实际来源收窄使用条件；R 内容继续共享更新，新增相同 R 来源不能抵消局部条件，但不凭空建立已不存在的来源。
R 后续增加 UDP/8443，哔哩哔哩在移动网络仍使用最新内容；共享 R 自己的匹配条件也仍有效，“仅移动使用”不改写它。这是持续条件建议，不是完整继承算法已定。
完成：应用显示“共享 R，仅移动网络使用”，来源按需可查；共享规则端可看局部条件，其他应用维持原样，不额外叠一条无效放行规则。
核对：原 20:07 流仍为受阻；从应用核对当前 Wi-Fi 新尝试，若仍被另一规则阻止，直接列出那条不同规则，不宣称本次修改必然联网。
失败：保留哔哩哔哩、R、已输入的移动条件、原流身份与 20:00–20:15；保存失败留在修改对象，执行失败可核对后回同一输入重试。
取消本次修改不产生局部条件，回 20:07 原流解释／video.example／20:00–20:15；“返回查看原流”则可保留未提交输入，不能和明确放弃混成一个动作。
“重新使用共享全部条件”撤去局部条件以及它对未来同 R 来源的覆盖，使用现有来源下共享最新版本；不复活已删直接关系或旧组成员，也不恢复历史流。
若已无任何来源，提交前改成准确动作“直接使用当前共享 R”：本次建立应用→R 的直接关系并撤去局部条件；取消、失败仍回原恢复输入与原流，不能将零来源报成已恢复。
实际改单个应用的规则内容另有完整路径：从同一原流选“只改哔哩哔哩的规则内容”，保留本应用已选的移动条件、端口 443→8443，明确保存“哔哩哔哩自己维护仅移动网络的 UDP/8443 拦截，替代它对同一 R 的全部来源，不再随共享内容更新”。
产品提供可读名称，命名可选；三处旧 R 不继续拦截 443，其他规则照旧。新记录核对 8443 的真实结果；取消回原流、失败保留 8443 输入，完成不改写历史。
个人内容持续替代同一 R 的当前／后续真实来源，移出组仍保留个人安排，移出影响预览须直接说明；日后明示改用共享内容即撤替代和未来覆盖，认当前来源与最新版本。
我愿承担的成本：改内容才承担长期分叉与审阅差异；仅收窄使用条件保留共享更新。若共享新条件与局部条件不相交，必须直接显示没有适用范围，不能以共享的名义藏掉无效安排。

## 双向关联、解除与域名表达的完整路径

规则起点：规则列表保留搜索“UDP”、非域名筛选与 R；打开 R → “用于应用／应用组” → 选择 Firefox 与“视频应用”组。
选择组时直接显示当前成员和“以后成员变化也跟随”；这是候选动态语义，不是已经确认的应用组规则。可选择几个当前应用而不选组，表达固定名单的另一种意图。
已通过其他来源使用 R 的应用不创建误导性重复项；有局部条件或个人内容时，当场让用户选“保留本应用安排，仅建立关系”或“改用共享全部条件／内容”，不能保存后才透露被旧安排压住。
后者撤去旧局部安排与未来覆盖，使用当前共享最新版本及当前真实来源；若本次从规则端选单应用建立直接使用，就确实建立这处关系，不重新加入已移出的组。
保存后回 R 的使用对象；普通返回再回“UDP”筛选及 R 的原位置；取消选择不新建关系，失败保留搜索、已选 Firefox 和原组。
应用或应用组起点：哔哩哔哩／“视频应用” → 使用规则 → 搜索并选择单条 R → 预览作用条件 → 保存；完成、失败、取消均回原对象，保留成员搜索或原应用时段。
“解除这处使用”只删对应来源；若 R 还来自另一组，结果必须直接是“仍使用 R，来自出差应用”，并另给“这个应用停止使用 R”的完整意图动作。
停止使用同一 R 可由产品处理各来源，保持其他规则；不通过移出整个应用组来停止一条规则，因为那会连带撤去组内其他安排。
从应用选域名列表仍直接是“这个应用拦截这份列表”；列表被多应用使用时，“修改列表内容”显示全部影响者，“这个应用不拦截其中一个域名”进入局部安排而不偷偷改共享列表。
规则组给出使用整套内容的完整路径，但单条 R 的关联不强迫先放进规则组；停止组来源不自动停止从其他来源仍得到的同条规则。

## 最强整体反案与两项最难选择

最强整体反案是把全部控制集中于规则 Tab 的完整安排表：首页负责观察，控制统一在规则、对象、条件和来源中完成；同一处可找齐内容与关系，长期维护更统一。
它的使用成本是每次停应用或修原流都要转换成规则作者，理解结构、切换目的地再找回活动；我的首选愿承担共享前多一次影响核对、复杂匹配必要输入的成本，换取同一应用工作不断线。若应用内深入只剩解释与跳转，反案应赢。
整体最高价值待决定事项：从应用开始创作控制，是否默认以该应用为作用对象，明确一次“保存并用于它”，随后再选择共用；还是先创作共享资产再另建使用。前者最能检验是否把结构成本交给产品，尚未经用户确认。
选择一：快捷“允许”是解除禁用、继续接受完整规则，还是覆盖所有拦截？首选前者且不用含混“允许”；反案更快恢复可用，却可能一并放行广告与其他目标。
选择二：“只改我”按同一 R 的结果范围处理全部来源，还是只改发起来源？改判后首选全部来源的使用条件收窄、内容仍共享；真正改内容才显式个人维护。代价是必须区分使用条件与规则内容，反案则可能让另一来源抵消修改。
这两项优先等用户逐项决定；不顺带批准完整冲突算法、所有组操作或永久默认策略。

## 真实互辩记录与改判

给交互席的实际问题：播放器从影音组、出差组及直接使用得到 R，想只在移动拦截 UDP/443；逐处停止如何保留移动拦截并完成 Wi-Fi 调整，失败／取消怎样回 10:20 原流？
交互席实际回答并改判：初稿只演完“停止这处”，不能替代“只改这个应用”；应由播放器的使用安排一次处理同 R 多来源，保留共享更新，完成回 10:00–10:30／media.example／10:20。
交互席实际反问：共享 R 日后加 UDP/8443，用户仅改 Wi-Fi 却被迫接管整个 R；是否接受先限制本应用何时使用共享 R，把个人维护另作明确选择？
我接受并修改独立稿主路径：只改使用条件不冻结共享内容；三处来源由产品处理。原稿“所有单应用修改都独立维护”被这个长期反例击败，不能继续作首选。
我对其回答唯一跟进：三来源后来都解除，用户重新共享时零来源不能报恢复成功；应明确直接使用最新 R，不复活旧组和已删关系。
交互席实际回答接受，但要求提交动作准确为“直接使用当前共享 R”；取消不建立关系、不撤局部条件，失败保留新关系与条件撤销草案，保存／应用／新记录分开反馈。我接受。
给整体席的实际问题：邮件同 R 来自两组及直接使用，复制后旧三来源仍拦；怎样完成只改邮件、保留共享更新，并在随后重新共享时恢复正确关系？
整体席实际回答并改判：邮件 F81 → 只调整何时使用 R → 仅移动，一次覆盖同 R 所有真实来源，来源按需查；保留 09:00–09:15／calendar.example／UDP 筛选，放弃逐来源作为唯一完成路径。
整体席实际反问：邮件移出办公、加入出差后，从 R 端明确选邮件保存；若旧个人安排仍压住新使用，会不会成功却没用，或误恢复办公关系？
我接受其反例：重新关联就在 R／“邮件”搜索与选中对象处选择保留本应用安排或改用共享；后一选择撤局部、认最新内容和当前关系，不复活办公；取消保留这层搜索、选择和草案。
整体席实际接受上述结果选择与条件／内容区分；这不是一句“仍受规则影响”，而是让后来明示的决定能实际改变结果。
我对其回答唯一跟进：本应用端口 443→8443 的真实内容修改，能否产品处理全部同 R 来源、命名可选，明确个人维护而不留下旧 R？
整体席实际接受，并撤回“先复制命名”作为前提；个人内容替代同 R 来源、移出组仍保留，日后改回共享撤替代。他明确承担内容分叉成本，要求应用上发现自己维护及共享更新差异。我接受这项窄用途。

## 末端有限检验与仍待决定的边界

主代理的实际检验：共享 R 已是“仅 Wi-Fi AND UDP443”，天气要求改成“仅移动阻止 UDP443”；局部使用条件与 R 相交会为空，不能冒充已改成移动且仍共享。
我的结论：局部使用条件只能收窄。天气 12:00–12:15／weather.example／12:07 Wi-Fi 原流 → 只改天气的规则内容 → Wi-Fi 改移动、保留 UDP443 → 明确个人维护及停止共享更新，不改其他应用的 Wi-Fi R。
保存替代天气同 R 全部来源；新 Wi-Fi 流不再因 R 受阻、移动 UDP443 受阻，其他规则照旧。失败保留天气／R／移动输入，取消不产生个人内容，完成回原流，历史不重判。
再次共享撤个人替代及未来覆盖，用现有来源下最新 R；零来源先明确直接使用。这样才兑现改变匹配条件，不能把“何时使用”当成可改写所有共享条件的万能动作。
