## 我的品味选择

我选择**从可认出的处理动作起步，让同一份规则随着具体选择逐渐完整**。新建后先选“阻止／允许”等动作；本案选阻止，眼前内容随即成为“阻止〔选择内容〕”。这是正在形成的规则，尚未保存或使用。
下一步直接认出已有名单 L，也能看见“连接：协议、端口…”的入口。选名单不先经过名单类别；选连接只展开当前内容需要的细节，两者始终回到同一份规则。
我不保留“隐私保护／省流量／名单规则／高级规则”这类目的或类型分流。它们会让人在做决定前先判断自己属于哪一类，并可能让后续组合像换了一条创作路径。

品味上的理由是：动词先把“要怎样处理”说清，后面的具体对象和条件有明确关系；下一动作从当前缺少的内容中出现，完成时仍读得出自己刚刚构成的决定。
我愿付第一次需要声明动作、最初表达尚不完整的代价。已知道 L 的人直接从 L 开始也有吸引力；当前选择来自上述设计判断，没有实测证明动作先行普遍更容易。
“规则逐渐成句”表示选择和修改会形成可读内容，不要求用户自由输入一句话，也不预设 AI 解析。动作全集、具体控件与屏幕布局不在这里冻结。

## 主案：让浏览器只在移动网络下拦截名单 L

起点是规则 Tab、尚无规则、没有未结束任务，已有用户自维护名单 L。

| 用户做什么 | 当下应能读到什么 |
| --- | --- |
| 进入“新建规则”，选择“阻止” | “阻止〔选择内容〕”；当前没有使用者，也没有正在生效的半条规则。 |
| 选择内容，直接选已有 L | “阻止名单 L 中的域名”；紧贴这项内容显示当前网络范围“所有网络”。 |
| 把网络改为“移动网络” | “仅在移动网络下，阻止名单 L 中的域名”；可以直接回改网络或名单。 |
| 选择浏览器作为使用对象 | 相邻位置认得浏览器，说明这份规则将给它使用；规则内容仍保持同一读法。 |
| 选择“保存并用于浏览器” | 同一内容呈现保存结果与实际使用状态，用户看得见这次决定的结果。 |

这里的“所有网络”是尚未限定网络时的真实范围，必须明示且可直接修改。我选择保留这个可见默认，接受需要移动限定的人主动收窄；不让所有创作都必须回答一次网络问题。
没有选择应用不等于全部应用。未选内容也不等于全部连接；不完整内容不能被当作已经成立的控制。选择过程中的改动在明确完成前不自动采用。
完成后可按需要查看浏览器相关的真实后续活动，再回同一规则；没有记录就没有相应执行证据。保存成功、实际使用与观察到拦截分别按事实呈现，不把核对变成每次创建的强制步骤。
“仅在移动网络”表达本条规则的条件，不承诺其他规则不会限制 Wi-Fi。持续创作时，保存反馈保持在当前工作内，不强制退出再进入。

## 反验：几个应用在 Wi-Fi 下禁止 UDP 443

仍从“新建规则 → 阻止 → 选择内容”开始，这次进入“连接：协议、端口…”，选择 UDP 和目的端口 443。
为使本次演练一致，UDP 443 解释为对外连接的 UDP 目的端口 443；这是案例假设，不是批准所有规则的默认方向或端口语义。
把同一个网络范围改为 Wi-Fi，直接选择浏览器、视频、播客。完成前可读回“仅在 Wi-Fi 下，阻止对外 UDP 目的端口 443”，旁边明确这三个应用。
主要动作成为“保存并用于这三个应用”；完成后仍面对这份规则，按真实情况看保存与使用结果。没有先建应用组或规则组的要求，本次多选也不自动变成持续应用组。
协议与端口在当前内容中承担必要的精度；它们不需要另一套高级规则编辑器。连接入口须保持可发现，不能被大量名单挤到列表末尾。
这条路径与主案只在所选内容的细节上不同：同样选择动作、构成内容、限定网络、明确使用对象、完成并读回。

## 待用与改错也应是自然动作

只准备内容时，不选使用对象就可“保存待用”；完成结果为“已保存，尚未用于应用”。这是完整收尾，不把没有应用解释成创建失败。
如果已经选了浏览器，后来只想保存，主要使用动作旁仍有可发现的“仅保存待用”，明确此次不用于已选应用。这个选择只保存规则内容，不建立使用关系。
本轮建议舍弃这次未提交的浏览器候选，日后使用时重新选；不把它显示为作用对象，也不额外引入永久的“计划使用者”。我接受重选成本，保留这个具体取舍供用户判断。
误选网络时，直接改眼前的网络条件；取消局部选择则回到进入前的值，名单和应用选择保留。取消整项创建与完成保存是不同动作，已取消输入不自动复活。

## 简单规则怎样长出复杂能力

主案进一步需要“或者在 Wi-Fi 下禁止 UDP443”时，在当前内容上“添加另一种情况”。从第一项开始，移动网络与名单 L 就属于同一个情况；新增时原项原位保留。
完整读法变成：“阻止以下任一情况：①移动网络下命中名单 L；或者②Wi-Fi 下的对外 UDP 目的端口 443。”使用对象仍是浏览器。
共同动作保持在两种情况之外，每种情况自己的网络和目标在一起。不把原来的移动条件暗中变成两支共有条件，也不在扩展时重新解释旧内容。
我选择为两种情况增加清楚的结构和空间，接受复杂规则不再只有一行的代价；“或者”直接表达关系，不让用户先切换到布尔编辑模式。
动作也能回改：将共同“阻止”改为“允许”，两种情况保留，读法相应改变，明确完成后才采用。这检验入口没有锁死规则类型，不决定允许与其他规则的冲突算法。

## 真实互问改变了什么

| 实际质询 | 实际答复与修正 |
| --- | --- |
| A 问 B：L 是否直接出现，名单很多时怎样找到 UDP？ | B 明确直接列实际名单，连接入口稳定可见；A 删除初稿中的名单类别门。 |
| A 问 B：已选浏览器后仅保存，候选对象怎样处理？ | B 补齐次要收尾及未使用结果，舍弃未提交候选；A 接受，双方承担以后重选的成本。 |
| B 问 A：既然都从动作开始，为什么还需要名单类别，动作又比认出 L 强在哪里？ | A 删除类别选择，收准动词只先明确处理关系，不声称它已被证明更熟悉。 |
| B 问 A：OR 增加时网络范围会不会暗移，改为允许会不会锁型？ | A 明确从第一支开始网络与目标同块；B 接受并修正自己的初稿表述，双方采用中性的“另一种情况”。 |

双方没有使用追加追问。两份独立稿本来就都选择动作起步，因此实际互问没有继续扮演“模板派／空白表达派”的虚假对立，而是削减真实的分类门和范围理解成本。
我也修正自己的初步担心：网络没有主动选择，并不必然需要阻止创作或强迫补答；可见的“所有网络”可以准确表达未限定状态，关键是它紧贴当前情况且不等同默认给全部应用使用。
