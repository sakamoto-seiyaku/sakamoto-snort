## 先演一个人的完整工作

我已看懂天气的查询问题，现在要维护自己的 50 项安排，留 SSH 备用，修改共同处理，并确认修改期间实际怎样判断。
1. 打开联网规则，先读已保存 v43 的 50 条与 8 条未分配；“设备仍使用 v42”是另一个事实。未分配筛选直接找到 SSH，不必先造命中，也不被称为设备正在执行。
2. 从 SSH 的读面修改名称；继续选择共同规则，实际编辑 ANY/NOT 条件树。整份输入保留另一项修改，Firefox observe / Signal enforce 在保存源中仍各自保留。
3. 在健康状态明确选真实身份开始 D1。记录有自己的身份、开始时刻、实际来源与结束动作；返回继续修改，不把候选预计当已采集证据。
4. 外层播放名单自动采用 D13：原输入仍在，相关引用需要重核。实际打开 D12→D13 新增/移出、本地补充/排除、全部用途，再明确更新本次依据；原候选不能直接越过旧基线提交。
5. 一次提交完整候选，模拟保存成功但未使用：已保存 v45 / 实际 v44，已持久化工作立即收口；重新尝试使用后实际 v45。保存、开始使用与有新活动三个结果分开。
6. D1 收到晚到 v42 与新 v45 两行，各自保版本；旧完整条件缺失就保缺失。回原问题实际落到已保存的 SSH 备用检查 / r5，work=null，未分配仍未分配；没有复活旧输入。结束额外记录后播放旧证据不再追加。

这是同一人的深浅迁移。范围扩大时标题与用途真正改变，完成时面对保存物件；稳定入口不是永久编写引导，也不是用两栏数量证明体验。
