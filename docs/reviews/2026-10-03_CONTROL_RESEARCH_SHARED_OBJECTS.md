# 共用对象反查：Figma 的局部差异为何能被直接操作

日期：2026-10-03。状态：结构类比检验，非 Sakamoto 方案或产品决定。
只研究两个成熟机制：组件实例覆盖、变量模式继承；不扩充政策论文目录。
实读现行正式文档，查看官方 Reset/覆盖保留截图及模式切换动画的首、中、末帧。
下列五步是按正式语义串联的具体操作复演；未登录 Figma 实际建立文件，不声称完成现场软件验收。

## 案例一：同一个按钮，在三处使用，只有一处保持不同

用户认识的对象首先是已经设计好的按钮，然后才将它作为共用来源。
实例也不是脱离内容的“应用范围”：它就是画布上某个位置的这个按钮。
[正式概念定义](https://help.figma.com/hc/en-us/articles/360038662654-Guide-to-components-in-Figma)、[原始发布演示，2016](https://www.figma.com/blog/components-in-figma/)

同一设计者在同一文件完成以下过程，取填充色与描边两个可覆盖属性作例：
| 步骤 | 用户实际做什么 | 可见结果 |
|---|---|---|
| 创建共同内容 | 做蓝色、1px 描边的按钮，创建主组件 | 有一个可继续编辑的原件 |
| 多处使用 | 插入三个实例，放在三个已有页面位置 A/B/C | 三个按钮都关联这个原件 |
| 局部改 | 选 A，把填充改绿 | A 绿；B/C 蓝；原件仍蓝 |
| 共同更新 | 进入主组件，把填充改红、描边改 2px | A 仍绿但描边变 2px；B/C 红且 2px |
| 恢复局部 | 在 A 的 More actions → Reset 中只选 Reset fill | A 变成原件当前的红色，重新跟随；不是回到最初蓝色 |

原始官方说明明确区分“被改的属性保持不同”和“其他属性继续跟随”。
现行文档规定可单属性恢复，菜单只列出已修改属性；上表没有使用整体分离。
[原始覆盖说明，2018](https://www.figma.com/blog/figma-feature-highlight-component-overrides/)、[现行编辑与恢复](https://help.figma.com/hc/en-us/articles/360039150733-Apply-changes-to-instances)

这一过程的核心不是先命名一个抽象集合，而是让具体用法保留来源关系。
“只改这里”意味着保留一个属性差异；“恢复”意味着删除这个差异。
局部差异不会自动被共同更新抹掉，也不会阻止其他共同属性继续更新。
这是按属性固定的覆盖语义，不是两个同样地位的规则竞争后决定谁胜出。

长期维护也有明确操作对象：从实例 Go to main component 改共同来源，再返回实例。
同文件立即传播；跨文件先发布库更新，使用文件再审阅并接受。
审阅可以逐实例查看 Side by side/Overlay，接受单个或所有更新；隐藏图层不能视觉比较。
[修改主组件](https://help.figma.com/hc/en-us/articles/360038665934-Edit-main-components)、[审阅库更新](https://help.figma.com/hc/en-us/articles/360039234193-Review-and-accept-library-updates)

**反例。** 覆盖不是无限制：底层图层顺序等结构不能这样局部更改。
现行官方四步图里，粉色填充从 Primary Default 换到 Primary Hover 时保留，换到 Secondary 时不保留。
因此“换来源仍保留一切差异”并不成立；匹配图层及原属性等条件参与覆盖保留。
[现行规则与实际图](https://help.figma.com/hc/en-us/articles/360039150733-Apply-changes-to-instances)

## 案例二：共同主题定义，在一个使用位置显式选不同模式

变量集合保存按模式组织的共用值；对象绑定的是变量，不是一次粘贴的颜色。
官方实际动画选中购物篮 Frame，在 Appearance 中切 Light→Dark，既有页面同时改色。
本次查看了该动画和 Auto(light)/light/dark 的选择菜单，未仅从文字猜测画布操作。
[正式模式文档与原始动画](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables)

同一设计者继续在一个文件中操作，以下是对官方机制的最小复演：
| 步骤 | 用户实际做什么 | 结果 |
|---|---|---|
| 创建共同内容 | 建 Color 集合，surface 在 Light 为白、Dark 为深灰 | 两个集中维护的值 |
| 多处使用 | A/B/C 的背景都绑定 surface，页面选 Light，各 Frame 为 Auto | A/B/C 都白 |
| 局部改 | 只给 A Frame 显式选 Dark | A 深灰；B/C 继续跟随页面 Light |
| 共同更新 | 把 Light 的 surface 改米白 | B/C 米白；A 仍用 Dark 值；改 Dark 值才会更新所有 Dark 用法 |
| 恢复局部 | 将 A 的模式改回 Auto | A 跟随父容器，当前页面 Light，因此米白 |

这里的局部动作是选一套已有值，不是在 A 上创造私有变量定义。
其有效模式由对象显式选择，或沿既有父容器树寻找选择，最后回落集合默认模式。
所以改全页模式后，显式选 Dark 的 A 仍保持 Dark；Auto 的位置才随页面变化。
[模式继承](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables)、[页面切换与显式模式](https://help.figma.com/hc/en-us/articles/15253268379799-Variable-modes-in-prototypes)

**维护反例。** 官方还展示四文件的变量/嵌套组件更新链：新增模式后，最后一个文件接受更新仍可能无效。
必须从变量源、使用它的主组件到下游依次发布/接受，才能解决版本模式冲突。
因此“共用关系”没有消除维护，反而要求来源与使用链能被找到。
[官方冲突场景与链式演示](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables)

## 类比是否比 policy editor 更接近本题

**只在共用维护这一部分，更接近。** 它把共同来源、某个实际用法、这个用法的差异分别变成可操作对象；
用户不必重写一份内容才能形成差异，恢复也有精确含义。以上是研究者判断，不是已验证迁移结论。
但可见的物体与已有结构承担了大量认知工作：选中哪个按钮、哪个属性、哪个 Frame，修改位置都已存在。
画布上有限的使用位置，以及稳定的图层身份，让“同一内容在这里使用”可以直接被指认。

Sakamoto 的 App 可以只是任意条件组合中的一个条件，不能据此变成唯一父容器或固定使用位置。
未来连接并非已经铺在画布上的有限实例；域名名单、网络、协议、端口可形成交叉而非容器树。
实例覆盖天然使局部属性获胜，模式继承天然使显式选择截断父层；两者都没有表达任意策略优先。
若把“局部更具体”直接当“胜出”，就会与用户已强调的优先关系冲突。

**核心判断：类比通过了共同内容长期维护的检验，没有通过联网控制核心表达的检验。**
它值得看的不是“规则就是组件”，而是成熟产品怎样让使用点的差异持续存在、来源更新可预知、恢复不歧义。
本报告不据此规定 Sakamoto 的操作对象，也不把两套机制拼成新的产品概念。
