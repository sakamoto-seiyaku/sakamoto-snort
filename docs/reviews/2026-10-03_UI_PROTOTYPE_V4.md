**后续反馈：** 用户实际操作后认为两版都不成立，给出[首次授权、标准／增强／自定义、后台守护及几步误伤恢复](../product/NETWORK_CONTROL_PRODUCT_VISION.md#2026-10-03-从标准防护与后台守护重新描述普通用户路径)的初步场景。不继续以本报告两案作为待选主方案；下方制作与浏览器走查事实保留，不能将路径可操作等同于设计通过。

用户要求将当前研究中的思路落成V4设计与交互原型。此前“范围表达”和“判断路线”均已被否定；研究材料也没有形成用户认可的key。本轮交付让两条不同的工作起点可被实际操作，没有将制作授权记成概念批准。

## 入口与题目

- [A：改变结果](http://127.0.0.1:4173/v4/index.html?variant=A)

比较题目是：当用户要表达、修正和共同维护联网决定时，眼前主要操作应该是“得到希望的结果”，还是“编辑共同内容并保留自己的差异”？两版共用样例状态、实际判断和历史；允许与禁止对等。

A从研究中的输出约束工作借鉴起点；B从共同来源、局部改写和恢复当前来源借鉴关系。少量边界例子只作核对工具。本轮没有把所有研究机制拼成第三个主方案，也没有恢复被否定的两个候选。

## A：结果是本次工作的入口

规则Tab首先显示几个应用／目标的当前政策结果。用户选择“希望天气在Wi-Fi和移动网络下允许联系api.weather.example”；系统根据当前内容提出需要改变的部分，列出前后结果及其他应用的对照，然后提交。

默认误伤案例只需在隐私名单中为天气单独调整，其他应用、其他目标和共同内容保留。在移动网络保护更优先的案例中，Wi-Fi和移动网络实际采用不同内容，系统提出两处所需修改。取消选择其中一处，预览和完成反馈继续承认残余禁止。

希望已满足时，不新增修改；默认允许且希望禁止时，新增明确的应用、目标与网络内容，显示其位置。这个原型不持久保存第二份“希望”清单，提交的是可找到的实际内容修改。

**代价：** 修复工作较直接，但用户需要理解并接受系统提出的修改；系统的候选解释及后续找回比一句“已允许”更重要。从零表达复杂共同内容仍需要进入已有内容与完整条件创作，本轮没有证明结果输入能自然覆盖所有长期作者工作。

## B：共同内容与个别差异是眼前的对象

规则Tab首先显示共同内容的可读含义，旁边是各应用怎样使用它。天气、阅读和播客共同使用名单L；天气可在这份内容中保留单独允许，不复制整份内容，其他应用继续跟随。

共同动作变化后，明确设置的天气动作仍保留，即使它与共同动作暂时相同；“恢复跟随”移除差异，采用当前来源。没有用旧快照替代恢复，也没有根据动作暂时相同就偷偷删除用户的明确设置。

移动网络保护更优先时，单独修改隐私名单仍不会覆盖它；界面显示真正采用的内容，用户可转去处理对应对象。优先顺序可以明确修改，单独调整本身没有自动更高优先。

**代价：** 共同维护和局部关系可认，但用户需要找到实际采用的对象，可能连续处理两份内容。来源中积累的差异需要持续可见与可恢复；本轮没有证明这种关系是所有人自然理解的核心概念。

## 共同边界与可操作反例

| 工作 | 原型中的实际行为 |
| --- | --- |
| 共同允许、天气单独禁止 | 反向动作使用同一种操作，没有默认“禁止不可被覆盖” |
| 暂停共同内容 | 所属调整同时暂不起作用，没有独立的全局允许／禁止残留 |
| 名单移出／加回目标 | 共同条件不适用时差异保留但不执行；加回后重新适用 |
| 移出／加回作用应用 | 同样保留所属差异；新加入的音乐跟随共同内容，不复制天气差异 |
| OR某一支没有应用条件 | 那一支可作用于音乐等其他应用，不套隐藏的共同应用外框 |
| NOT及端口条件 | 完整条件可继续编辑；A核对支持字段的等价情况，不只检查一条TCP连接 |
| 内容保存待用 | 保存完整草稿但不参与当前判断，之后可明确开始使用 |
| 应用进入共同维护 | 明确跳到规则Tab显示全作用对象，保存或取消后回发起应用 |
| 内层名单独立保存，外层内容取消 | 已完成的名单保存保留，未提交的外层动作修改放下 |
| 政策修改与已有活动 | 保存不新增活动；旧记录保留当时动作、名称和版本 |

单独调整的“所属内容匹配后改动作”是本轮为比较提出的语义假设，尚未成为正式规则模型。两版共同采用这个假设以减少结果差异对操作比较的干扰，不代表它已经由研究或用户批准。

## 最小上下文与补充工具

保留首页、规则、设置三个Tab。首页提供样例时段、曲线及同一时段的应用，应用页以已有连接活动为主，域名是目标，没有名称才显示IP。应用内的修改先只作用于当前应用；共同维护多一步进入规则Tab。它们只提供判断规则操作是否自然的上下文，没有重做整套旧原型功能。

“核对几种情况”允许编辑假设连接与希望结果，显示当前采用的内容及是否一致。希望结果只帮助检查，不自动改变政策，也不成为实际活动；少量例子不能证明任意未来行为。

顶部案例选择器、底部版本切换及状态观察属于评审工具。版本切换保留已提交修改，放下未提交草稿并提示；完整样例状态可查看，切换时也输出到浏览器控制台。

## 本轮实际验证

Chromium在四种窗口大小实际操作A/B完整路径：1440×1000、820×1180、393×852、640×800，八次走查无页面脚本异常或文档／对话框横向溢出。验证了误伤、部分计划、另一份更优先内容、反向动作、恢复当前来源、共享变化、条件生命周期、OR／NOT、待用、原应用返回、历史不改写和核对不修改政策。

截图及[走查收据](../../app/design/prototypes/2026-09-29-interaction-directions/v4/qa/browser-check.json)随原型保存。它们证明本次样例路径可以操作，不证明某一版更直觉，也不构成真实设备、后端规划能力或用户研究的验收。

## 继续判断的标准

优先观察同一个人在两版中是否能自然完成误伤修正，并理解“只改自己、其他应用保留、另一份更优先内容仍可能决定结果”。随后看共同更新、恢复跟随、半年后找回与从零创作，不能凭第一步按钮少就判A胜，也不能凭B关系完整就判B胜。

本轮只把思路变成可比较的交互物。没有宣布key已找到、选择主方案、提升生产代码，或改动规格、ADR、后端与Plane工作项。V3文件继续作为此前阶段原型保留。
