# 性能测量讨论记录（2026-09-28）

本轮只采集和分析，没有修改产品代码、实施优化或提交 Git。下一次会话可从这里继续讨论；本记录不创建新的实施任务。

- 内存：Android `:runtime` 的 RSS 包含大量共享系统映射，不能视作 Rust 堆。进程 PSS、原生堆和映射明细见[首次基线](../testing/2026-09-28_VPN_ROOT_PROFILE_BASELINE.md)。
- 符号：另建保留 Release 优化的带符号版本，已解析产品插件和 Rust 的函数热点；VPP 基础库仍有未知帧。调用链占比不等于函数自身消耗，见[符号化报告](../testing/2026-09-28_VPN_ROOT_SYMBOL_PROFILE.md)。
- 吞吐：普通 `adb shell` 已能让 VPN TCP/UDP 流量经过 VPP；Root 需要使用现有 OUTPUT 规则选中的 UID。正式测试使用小型原生探针，而非标准 iperf，详见[吞吐报告](../testing/2026-09-28_VPN_ROOT_THROUGHPUT_PROFILE.md)。
- 具体热点：VPN TCP 的前 20 秒窗口中，`getenv` 自身占 VPP 样本约 7%；采样调用者为 `product_vpn_tun_product_mode()`，与该函数读取环境变量的源码吻合。没有测定每包调用次数，也没有实施缓存优化。
- 重要发现：Root 持续 TCP 负载两次出现队列 176 监听消失，端点字节与 VPP Flow 记录明显不符。两次高吞吐数字均不能作为正常 NFQUEUE 性能结论。队列消失原因尚未定位，也未修复；不能仅凭 on-CPU 锁或 epoll 栈认定锁竞争。

后续讨论重点是：先理解 Root 队列失效及健康状态的一致性，再判断哪些正常路径热点值得进一步测量。是否进入诊断或实施，由下一次讨论决定；不要自动续跑或恢复先前的优化授权。
