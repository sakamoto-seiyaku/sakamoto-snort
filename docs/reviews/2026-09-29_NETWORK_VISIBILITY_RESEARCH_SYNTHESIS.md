# 网络透视研究综合：应用、整体状态与用户判断

日期：2026-09-29。性质：用户请求的竞品、用户问题和使用心理调查，以及据此形成的设计假设。不是已确认的导航方案、产品规格、实施任务或真实后端验收。

用户反馈：应用中心符合直觉，但当前原型仍不方便透视网络状态。依用户要求，三位 `gpt-6-sol / xhigh` 子代理分别调查竞品交互、公开用户问题、认知研究；主代理复查当前原型、核对关键原始来源并综合。本轮没有修改原型或产品实现。

后续按用户要求，将这些结论与乔布斯设计原则做双向质询；六个焦点、实质修正及下一轮原型建议见[收敛指导](2026-09-29_NETWORK_VISIBILITY_DESIGN_GUIDANCE.md)。该指导继续属于待验证建议，不改变研究证据或已确认产品愿景。

## 1. 主要判断

**保留应用作为用户认识、归属和操作的对象，同时让整台设备随时间发生的活动成为直接可见、可探索的入口。**

当前原型对「我想查看天气这个应用」已有清楚路径。下一步最值得验证的是另一个起点：「刚才网络有点不对，我还不知道该看哪个应用。」用户应能从一个时段、一项变化或一个失败结果开始，逐步认出相关应用、去向和处理依据，作决定后再核对后续事实。

这里的「透视」暂按四个问题理解：现在发生什么；与刚才有什么变化；变化涉及谁、能解释到哪一步；是否需要我行动。这个解释是我们的设计判断，尚未经过 Sakamoto 用户研究验证。

## 4. 用户实际关心的问题

17 条公开原帖只能支持问题类型，无法给出普遍偏好的排名。以下按使用时机整理；其中的引号是问题归纳，不是逐字引用。

| 用户的问题 | 原始证据 | 设计上应帮助完成的判断 |
| --- | --- | --- |
| 「刚才谁在上传／耗流量？」 | PCAPdroid 用户在状态栏看到外发活动，却无法在工具中找到来源；Mac 用户希望不用一直盯屏，也能回看应用累计量。[PCAPdroid #386](https://github.com/emanuele-f/PCAPdroid/issues/386)、[Mac 原帖](https://www.reddit.com/r/macapps/comments/rcfmrd/mac_app_for_tracking_bandwidth_usage/) | 从整台设备及所选时间找到贡献应用；方向、数量和观察范围读得清楚 |
| 「这个功能为什么突然用不了？」 | RethinkDNS 用户看到红色阻止标记却找不到原因，不知道改什么才能允许；NextDNS 用户希望恢复教材网站与音频。[RethinkDNS #2865](https://github.com/celzero/rethink-app/issues/2865)、[NextDNS 原帖](https://help.nextdns.io/t/x2h51l3/cant-access-educational-sites-with-nextdns) | 从具体失败到当时依据，再到有范围的调整和恢复；不让用户先猜所有规则 |
| 「我已经阻止了，为什么图还在动？」 | GlassWire 用户询问峰值表示尝试、实际传输还是待发送数据；RethinkDNS 用户拿上游 DNS 日志核对本地阻止。[GlassWire 原帖](https://forum.glasswire.com/t/why-peak-shows-on-graph-when-network-turned-off/8073)、[RethinkDNS #1993](https://github.com/celzero/rethink-app/discussions/1993) | 区分设置、尝试、查询、实际传输与观察位置，避免一个徽章承担所有含义 |
| 「这条提醒／状态到底需要我做什么？」 | Portmaster 用户不理解反复 DNS 提醒的应用归属；GlassWire 用户困惑于大量自己没设置的阻止状态。[Portmaster #541](https://github.com/safing/portmaster/issues/541)、[GlassWire 原帖](https://forum.glasswire.com/t/v3-7-880-blocking-tons-by-itself/21026/1) | 能解释触发事实与影响；区分已配置的限制和实际发生的阻止 |
| 「这个汇总由哪些活动组成？」 | NextDNS 用户看见安全原因触发计数，却无法进入对应记录。[NextDNS 原帖](https://help.nextdns.io/t/60yt1bl/analytics-allow-blocked-category-drilldown) | 汇总可以追到同一范围的组成记录，并继续按来源、应用与时间调查 |

本轮优先建议试验第一个问题，因为它直接对应用户反馈、现原型首屏缺口，并有竞品交互和用户原帖相互印证；这属于本项目的设计优先判断，不是市场需求排序。其他问题约束整条路径，不能因首页更简洁就丢失。

## 5. 使用心理：从看到事实到能够判断

**看到去向后，仍然可能不知道该怎么办。** Aretha 的三户家庭、六周部署发现，参与者很少创建阻止规则；作者将其与目标过多、评估陌生目的地的负担，以及阻止造成的功能损坏等因素联系起来。这是小样本定性观察，不能推出普遍行为比例。对我们的启发是：具体活动旁边需要有相关依据、清楚的操作范围和恢复路径，不能指望多显示域名就自然带来掌控。[CHI 2020 原文](https://www.cs.ox.ac.uk/files/11850/Aretha.pdf)

**熟悉的对象帮助进入，深入能力仍有价值。** 一项包含 32 位隐私意识较强的智能家居高级用户的焦点小组研究，记录了对设备状态、网络流可见性和更细控制的需求，也记录了高级用户仍无法理解某些目标用途的情况。它提醒我们保留探索空间，并让界面承担信息组织的工作；不能由高级用户愿意研究，推导出他们愿意反复拼接多个页面。[SOUPS 2023 原文](https://www.usenix.org/system/files/soups2023-park.pdf)

据此提出三个待验证的使用方式，而不是给人贴固定类型标签：

- **扫一眼。** 看当前网络和控制是否在工作、有哪些具体变化；没有问题时自然离开。
- **追一件事。** 带着「刚才为什么慢」「这次为什么失败」的疑问，从时段或结果追到相关事实。
- **主动探索。** 比较应用、目的地、网络与时间，保留详细筛选、地图、规则和诊断入口。

同一个人可能在三种方式之间切换。界面应能从简短观察自然展开，而不要求用户先选择自己的技术等级。陌生目标、首次观测和流量增加都只是事实或线索，不能自动着色为危险；同样，没有新记录也不能自动宣告安全。

## 6. 当前原型的具体缺口

主代理检查了 [手机首页截图](../../app/design/prototypes/2026-09-29-interaction-directions/app-first/screenshots/phone-home.png)、[桌面首页截图](../../app/design/prototypes/2026-09-29-interaction-directions/app-first/screenshots/desktop-home.png)、[首页结构](../../app/design/prototypes/2026-09-29-interaction-directions/app-first/home.html)及 [图表交互](../../app/design/prototypes/2026-09-29-interaction-directions/app-first/js/experience-ui.js)。以下是原型观察和设计批评，不是用户测试结果。

| 当前呈现 | 对「整体网络怎样了」的限制 | 保留并调整的方向 |
| --- | --- | --- |
| 手机首屏先给今日累计字节、最近应用及各自最后一条结果；整体图在应用列表之后 | 用户得先猜应用；今日总量也不能表达当前速率或刚才的变化 | 保留直接点击应用，把当前活动和可选时段变成同样直接的入口 |
| 桌面有整体曲线和最多流量应用；图中时段可点 | 已有联动基础，但点击后跳到活动记录，缺少在原处识别变化贡献者的中间解释 | 图、贡献应用与记录共享选区；宽屏原处展开，手机逐层深入并保留时间 |
| 整体图将发送和接收按字节合并表现 | 相同总量可能来自上传或下载；查询被阻止的时段也可能几乎没有传输量 | 收发方向清楚；查询、连接与阻止有各自单位，按同一时段关联 |
| 「运行中」和「联网设置正在执行」占据主要状态表达 | 不能单独回答网络是否可用、某次请求是否成功、记录是否新鲜 | 简短状态应对应可核验事实；能力停用、记录缺口和网络失败分别解释 |
| 从单条记录调整规则已有固定反馈与后续活动入口 | 已解决局部决定，但从全设备问题开始、修改后回到原观察范围的路径还弱 | 全局时段、应用、记录、依据和调整结果贯通；历史不随新规则改变 |

因此，下一轮需要同时改信息顺序和选择关系；仅把现有曲线移到顶部仍不足以验证这条路径。

## 7. 建议试验的一条体验

建议先做一个范围有限的联动原型，继续使用现有应用身份和详细活动页。下面是设计假设，页面名称和导航尚未确定。

1. **打开即看到整台设备的当前活动。** 当前网络、发送/接收变化、所选时间，以及简短的执行/记录状态共同构成起点。正常态保持克制；需要处理的事实直接给出影响和入口。每个数字带自己的单位和范围。
2. **可以从时间或应用进入。** 知道应用名时仍可直接点应用；不知道时，可点一个变化时段。列表随选择解释「哪些应用参与、各自发生什么」，提供清楚的返回全设备动作。图形附近有等价的文字/列表入口，触控不依赖悬停或精确拖拽。
3. **同一时段内看见去向和结果。** 从应用或有依据的共同目标进入，看到 DNS 查询、连接和传输事实。目标用途或组织归属有依据才表达；IP 所有者、实际收件人和地理位置不混同。
4. **由具体事实进入决定。** 保持当前应用和对象，显示适用规则/名单、操作范围和预期作用。诊断表达已知原因与待确认因素，不把同时发生当成因果。恢复或撤销路径靠近原决定。
5. **回到原问题核对。** 修改后分别反馈保存与生效。新增活动是后续证据；旧时段保持原结果。若尚无新活动，说明等待；查看动作不能制造请求或记录。

全局图承担发现和定位，应用承担识别与操作，详情承担解释和精细控制。地图、规则组、名单、完整统计与诊断都保留在这条路径可以到达的位置。

手机依次展开同一范围；平板和 Linux 宽窗口可以并排观察。小窗口仍保留 Linux 的身份与操作语义。实时观察可继续更新；一旦选定时段或正在读记录，视图保持稳定，并明确回到实时的动作。具体刷新策略须由走查验证，不提前固定成一律自动或一律手动。

## 8. 下一轮怎样证伪这个方向

以下是原型比较的任务建议，不是已进行的用户测试，也不建立另一份实施待办。

| 任务 | 要观察什么 |
| --- | --- |
| 只告知「刚才突然有一阵上传」，不透露应用 | 能否从整体时段认出主要贡献应用、方向和实际目标；是否被迫挨个打开应用 |
| 同一时段只有 DNS 查询被阻止，几乎没有传输 | 是否仍能发现事件；能否区分查询阻止、连接阻止与没有连接证据 |
| 某应用功能失败，样例分别是规则阻止、远端失败及证据不足 | 是否先看相关依据，是否将所有失败都误判成防火墙拦截 |
| 画面都是零，分别设置为确实无活动、采集暂停、记录缺口 | 能否正确区分三种情况，并找到适当动作 |
| 调整一个决定，返回查看原时段，再观察新活动 | 是否找得回原处；能否区分旧结果、新配置和新记录的结果 |
| 已知要查看天气应用 | 加入整体观察后，原有直接进入与控制是否仍然自然 |

用相同样例比较当前版与联动版，记录找到相关事实所需时间、无效跳转、错误归因、返回是否成功，以及参与者能否用自己的话说明结果；不把停留更久或点击更多当成成功。原型走查只能淘汰明显不成立的设计，长期信任、通知负担和真实故障恢复仍需真实使用研究。

## 9. 本轮保留的边界

- 产品仍围绕个人设备的网络理解、控制与验证；不扩大成企业网络运维平台。
- 按用户既定前提设计完整 DNS/IP/应用身份能力，真实实现状态另行遵循当前合同。
- 不从目标地址猜测加密内容、不把首次观测称为首次发生、不把规则允许称为远端成功。
- 本轮调查没有确认安全评分、自动异常判定、全量通知、新的后台采集或新的默认阻止策略。
- 原型和产品愿景保持原状；本报告为下一次设计讨论提供可核对的依据。
