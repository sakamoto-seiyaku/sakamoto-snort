# 核心交互独立席 B：把联网范围捏成一块，再放到决定的位置
2026-10-02；阶段二建议，初稿独立完成后实际读完 A/C/D 三稿；未读旧 CONTROL_CONCEPT 稿；不是产品合同。

## 先让三个不同操作方式竞争
1. **接线台**：拖入 App、网络、名单节点；从带标签的输出口接入“全部满足／任一满足／取反”盒，再接允许或禁止。决定盒排在右侧先后轨道。
   它的最强版本不是网络拓扑：线只表示输入关系，端口明确逻辑；点节点可见完整输入、输出和样例，手机按单个盒放大，连线用“选起点→选终点”完成。
   复用真的有优势：同一个 L 节点接多个决定，一眼看到共用；局部调整另分输出，优先仍必须在独立轨道操作。
   致命风险：一次“音乐移动禁用”就要经历对象、逻辑输入、决定、排序四种位置；手机追线时失去否定范围，接对线也不能证明顺序对。
2. **涂色格子**：横列网络、纵列应用，点格子涂允许或禁止；点格子切换到域名维度继续切片，多选格子共同涂色。
   优势是第一次两格操作和批量控制极强；可把格子再分名单、协议、端口，任意组合对应选区并集和挖洞。
   致命风险：第二个 OR 分支不限 App 时要切换坐标，重叠选区的先后无法由颜色表达；有限屏幕外还有多少维成为永久疑问。
3. **范围块与决定叠层**：用户直接拼放条件块，用有标题的边框包住它们；整块附上允许／禁止，放进明确先后排列的决定带。
   不是自由画图：块只能落在有语义的槽位；边框写“全部满足／任一满足／不满足这一整块”，位置表示包含，标签定义逻辑。
   风险是嵌套学习和空间占用；但范围、动作、先后都能在同一可触对象上看见和修改，不需要跟线跨屏。
**阶段一选择 3；阶段二撤销对图的过早淘汰。** 下文保留范围块完整案，末尾构造真正竞争的判断路线；四席选区同属一家族，不是四份独立证据。

## 一手材料怎样改变选择
实际在线读了 Archive 的 2007 Macworld 完整所刊节选，以及 2007 发布前员工讲话完整所刊节选；它们不是未经剪辑的演讲全本。
Macworld 中 Jobs 从固定塑料控件讲到可随任务改变的屏幕，再讲手指。我的推论：手机画布必须有可点选的大块和明确插入槽，不能要求精密接线；因此接线台落败。[原节选](https://book.stevejobsarchive.com/#speech-macworld-2007)
员工讲话拿电话会议作例，指出已有功能却藏在手册深处的失败；原话短引：“easy to use and self-discoverable”。我的推论：不能把括号与顺序藏成专家能力，块的边框操作及相邻顺序必须就在原对象上。[原节选](https://book.stevejobsarchive.com/#speech-to-apple-employees-2007)
这些是 Jobs 本人发言；日期和场景来自档案编者，候选选择是我的判断。没有材料证明他会赞成本方案。
已读 Vision 当前基线、最新重新开题、经验方法复查及统一规格第 2 节；不以规格代替用户理解。

## 用户认得什么、主要操纵什么
最小对象是一块“这些访问 → 这样处理”；未命名也完整，用户不先建立方案或应用根目录。
App 图标、Wi-Fi、名单名称是可点条件块；条件块可选择“同时满足”“或者”“整体不满足”，产生明确边框。
决定带从上到下查找，第一个满足者决定；序号可辅助定位，用户不输入 priority 数字。不同动作完全对等。
收起的块保留可读表达和动作，展开原地出现相同边框；读与改没有两套模式。
“范围块”是设计者术语，界面直接显示内容；不教用户网络形状、管道流向或集合数学。

## 主案例：音乐 App 从零完成，十个动作
进入前用户只知道音乐 App 和移动数据费，不需知道域名、规则或优先级。
1. 从应用列表点音乐；看到实际流和“联网安排”，没有活动也有该入口。
2. 点“调整联网”；出现含音乐图标的小块，页头固定“仅音乐”。
3. 点块内“添加条件”，直接选“移动网络”；它与音乐放进“全部满足”边框。
4. 点边框底端的处理，选“禁止”；马上读回“音乐 + 移动网络：禁止”。
5. 点“再安排一种访问”；在同一页出现第二块，继承当前编辑范围“仅音乐”，不是继承前块条件。
6. 选择 Wi-Fi，点“允许”；两个块同时在屏幕上，移动／Wi-Fi关系显明。
7. 点“预览”；展开两张合成访问样例，分别写“预计禁止／预计允许”，不伪装实际记录。
8. 点“保存用于音乐”；若与已有内容冲突，提交前必须看到插入位置及受影响结果；全新场景没有冲突。
9. 回到音乐页面看到两块已保存安排，状态另写“正在使用”或真实失败原因；不能用保存成功冒充运行成功。
10. 后续点实际流，可从过去的真实结果回到当时决定；当前预计结果另列，返回仍在音乐与原时间段。

## 操作面一：手机上的共同内容和 A 的修改
```text
〈 A                 联网安排 · 正在使用
按以下顺序，首个符合者决定       [调整先后]
┌ 允许 ──────────────────────┐
│ 全部满足： [A] [d.example]  │
│ 针对下方名单控制的调整       │
└───────────────────────────┘
┌ 禁止 ────────────── 共用 ──┐
│ 全部满足：[A/B/C] [名单 L]  │
│ A 有 1 项调整   [看共同内容] │
└───────────────────────────┘
[添加安排]      已保存 · 当前预计 [核对]
```
这里上下不是美术排序；页头明确首个满足者决定。共同块的 A/B/C 表示 OR 条件，不是隐藏的应用外层。
共同制作：规则 Tab 新建块→选 A/B/C→同时加名单 L→禁止→保存使用；应用集合内任一、集合与 L 同时满足，边框分别明示。
误伤时：A 的真实 d.example→调整→保留 A 与该域名→允许→选“放在名单 L 控制之前”，预览 A 改变、B/C 不变后保存。
反向共同允许、A/d 禁止只需交换两个动作，不增加否决语义；关联由“针对哪一块创建”保存，未靠包含位置赋予胜出权。
恢复点“撤销此调整”，明确预览重新由哪个决定获胜；若另一条更早决定会获胜，不能写“恢复为共用结果”。
点共同块进入规则 Tab 才能改共同内容，顶部列 A/B/C；返回 A 保留原访问。共同内容修改后，关联调整仍列出，不偷偷合并删除。

## 操作面二：无活动主动构造 OR、NOT 与括号
```text
〈 新安排                    已保存待用
┌ 任一满足 ─────────────────┐
│ ┌ 全部满足 ──────────────┐│
│ │ [App A] [域名在 L]      ││
│ └────────────────────────┘│
│ 或                        │
│ ┌ 全部满足 ──────────────┐│
│ │ [Wi-Fi] [UDP 目的端口443]││
│ └────────────────────────┘│
│ [+另一块]                 │
└───────────────────────────┘
处理 [禁止 ▾]   [预览]   [保存待用]
```
实操：新建空块→选 App A、域名 L并点“同时”→点外侧“或者”→在新块选 Wi-Fi 与 UDP目的端口443；第二块没有 App，不会默认补入。
要否定第二整块，点其边框标题→“不满足这一整块”；边框外再出现 NOT 壳，读回“不是同时为 Wi-Fi 和 UDP目的端口443”。
要只排除 UDP443，点该条件块→“不满足”；读回 Wi-Fi AND NOT(UDP443)。两种操作不同，选中边界必须高亮且其他区域淡化。
拖动是可选加速：长按条件块拖到边框内的发亮槽，落下前显示完整改变；手机同样能点“移到…”再点目标边框，取消不会改变原式。
修改处理点“禁止”切允许，整个表达不变。预览列 AppB/Wi-Fi/UDP443 能匹配原式，移动网络则不能，证明第二支不限 App。
任意括号由同一种边框递归表达；深处全屏展开当前块，顶部完整祖先路径可逐层返回，不横向无限缩小文字。

## 先后、复用与一个月后
P允许、Q禁止同时满足时，核对页并排列出满足事实，决定带显示 P 在 Q 前，所以允许；拖 Q 到 P 前，提交前预览禁止。
从 A 发起移动时只移动“A 所用的 P”，页头及提交文字都写“仅 A 的先后”；共同 P 内容及 B/C 的顺序不变。
这是新提议：同一共用内容的使用位置可分开安排，不沿用全球一套 priority 的用户模型；必须另行确认，不能暗称现有合同已允许。
在共同内容页选择全体移动才影响其他 App；展示每个使用位置的前后邻项，有差异时逐项选择，不能靠拖动共用图形偷偷广播。
多选决定块→“收为一套”才命名；套是便于拿取的一组决定块，展开仍按实际先后看，不能让文件夹位置产生优先。
准备整套时新块保留当前制作上下文；点“用于…”选择另一批应用，先明确替换哪一个应用条件槽，预览每块，不全局替换表达内全部 App 条件。
跨 App OR 分支保持原样；若没有共同应用槽，不能声称整套已安全重定向，用户逐块指定替换处或明确保留不限 App。
单块及整套均可“共同使用”或“独立副本”；前者后续共同修改会传播、后者不传播，建立时用一句效果说明选择，不自动猜测。
本提案把组公共条件视为持续相交边框：套内每项同时满足它；它有可见外框，移出时预览范围变化。这是待确认新语义。
一个月后从内容找回时，共用块列“另有 A 的调整”；名单 L 更新不擦除调整，点开可见该调整现在是否仍可能参与处理。
记录写当时实际动作、命中对象与当时版本；当前预计按现值计算；待用和正在使用清楚分开。域名已知直接显示域名，无名称才 IP。

## 代价、挑战与真正的弃用条件
保留应用内只改当前应用及跨共同修改多走一步；挑战已接受的“先动作”、固定句子创作和全球顺序呈现，理由是范围整体操作更连贯。
组最多三层仍守基线；布尔括号不是规则组，不能用其无限嵌套偷扩大组复用层级。待确认新语义必须与现状分开呈现。
强反方案是逐句编辑的决定清单：手机文字密度更高，复杂否定可朗读，空间视力负担更低；它不是给本方案另配的高级入口。
若真实手机测试中用户对 NOT整块 与块内NOT 反复混淆，或六块以后找不到第二 OR 分支，我会弃用拼块，改选句子清单。
若多数工作是跨几十应用批量两态分配，且复杂组合只是极少数，涂色格子的效率可能足以反转选择；不能凭少量复杂用例牺牲日常。
本案不承诺任意布尔式一眼懂；它承诺每一次改变都能指出改变的是哪个边界、哪个动作、哪个位置，并可以返回检验。

## 阶段二：真正值得竞争的判断路线，不要求用户接逻辑器件
用户认得的是“这次联网先问什么、是就去哪、否则去哪”；主动作是点路径“先问”、点出口“改去”、选一段“反转”、搬到另一个问题之前。
初始画面已有“本次访问→按现有安排”，用户不创建起点终点；每个问题问一个可认内容，是／否出口有文字，路径表示判断的实际顺序。
音乐案例八步：①音乐页调整→②点当前路径“先问”→③选移动网络→④点“是”的结果改禁止→⑤点“否”路径“继续问”→⑥选Wi-Fi→⑦是改允许、否保留后续→⑧预览两网络并保存，仅音乐。
```text
音乐 · 仅此应用         [试走一次] [保存]
        移动网络？               [改问题]
 是 → 禁止              否 ↓     [继续问]
                         Wi-Fi？
             是 → 允许    否 → 按后续安排
点任一路径 [先问…]；点结果 [改去…]
```
这里没有给移动网络／Wi-Fi以外条件擅定动作；已有更早决定时插入点可见，用户选“在它之前问”才改变优先。
复杂式八步：①空白创建判断段→②先问AppA→③是路继续问L→④L是路改为“本段符合”→⑤AppA否路点“尝试另一条”，选Wi-Fi→⑥L否路点“也走这条”选择已有Wi-Fi问题→⑦Wi-Fi是路问UDP目的端口443→⑧其是设符合，其否及Wi-Fi否设不符合，给段符合出口选允许，保存待用。
“也走这条”选择目标问题而非拖细线；自动显示两个来路，避免复制出两份Wi-Fi判断。上述内容本身就是精确OR，不需另开表达式编辑器。
```text
准备待用          判断段 X          [保存]
App A？ ─是→ 在 L？ ─是→ 符合 → 允许
  否 ↓         否 ↓
  ┌ 第二条尝试：Wi-Fi 与 UDP443 ─────┐
  │ Wi-Fi？ ─是→ UDP目的端口443？   │
  │ 否→不符合       是→符合 否→不符合│
  └ [选这段] [反转符合/不符合] ─────┘
X 不符合 → 继续后面的判断
第二段应用不限；两个来路指向同一段
```
段是用户可选的一串问题，产品把所有终止出口汇成“符合／不符合”；不是动作容器，两种结果可继续问也可处理，故与规则卡编辑确有差异。
NOT第二整块：点第二段标题→反转，自动交换段的两个出口，内部Wi-Fi和UDP问题不变；展开显示各终止路径已换去处，不让用户逐线修改。
NOT其中UDP443只点该问题“反过来判断”；段外路径不变。要把任意子式括起来，点首问题“选到…”再点末端边界，预览进入与两个出口后收成一段。
这里接受约束：只可收起一个入口、两类终止出口的判断段；任意布尔式都能逐问表达，但任意杂乱共享子图未必能被一次圈成合法段，产品须明确选择边界。
P允许与Q禁止重叠：主路线先问P，符合直接允许、不符合继续Q；点Q段→“先问这个”→点P，自动重接，Q符合便禁止，P不会再被问。
在A页页头固定“只改A这条路线”，P共享内容不变，B/C仍先P；共享的是问题内容，使用处拥有先后，这仍是明确待确认的新语义。
A/B/C共用名单L判断时，A/d误伤：从A记录点路径“在名单L之前先问d.example”，是改允许、否接原L；预览A改变/B/C不变后保存。反向只交换动作。
调整与L保留双向“从这里改道”的关联；删除调整恢复接回当前L前的原后续，但若更早问题已经处理，须展示它，不保证一定由L决定。
共同修改仍从A多走一步到规则Tab，列所有来路与使用应用；改问题正文会共同传播，改A入口后的路线只改A，界面不可混用同一种拖动。
多选连续判断段“存为一套路线”；无活动可待用，单段可复用；复用另一批App明确替换指定App问题，原不限App支路不偷偷加范围。
共同使用保留引用，独立副本单独维护；一月后实际记录保留当时走过的路径、版本与结果，当前试走另色并标预计，名称存在显示真实域名。
**真实比较：** 图让NOT表现为出口交换、优先表现为先问哪段；范围块让多支内容同屏并列、共同处理一次改动作。两者的主要操作不同，不再以规则清单换皮凑数。
图的真实代价是两条失败路径的合流、收段边界和“未走到”理解；选区的真实代价是括号作用域、排除与禁止混淆。没有实际用户证据能判绝对胜负。
我仍微倾范围块，但保留判断路线为同等值得测试的第二案；不会将它降为选区内部的专家页，也不同时承诺实现两套完整编辑器。

## 实际互问与改判记录
A问B：整块NOT和Q/P重排究竟改几处，图若一动作反转还输在哪？我答：选第二段反转一次；Q→先问→P三点，自动接续且只改A。选区只剩并列多OR扫读优势假设，我撤回早淘汰。
B问D：自动接线、交换出口、只改A先问Q后，哪一项具体工作证明图必败？D实答：不能证明；只有须手找末端并重接才额外付定位/接续成本，若系统完成则撤回“只适合审计演示”。
B问C：从Wi-Fi记录修复A/d，有限例子如何证明未来范围？C实答：不能证明；候选仅A+精确域名，网络全部、端口不限、不随L变化逐行明示，其他样本事实列“未纳入”；先读范围再保存，试算不显示验证通过。选照片只省找App/域名，不免定义未来范围。
