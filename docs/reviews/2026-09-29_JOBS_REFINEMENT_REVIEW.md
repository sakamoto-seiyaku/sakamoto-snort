# Sakamoto 定向复审：从“有修复”到“用户能确认”

2026-09-29。本次沿用[设计阅读札记](2026-09-29_JOBS_DESIGN_READING.md)的问题准绳，针对[首轮八项发现](2026-09-29_JOBS_FULL_PRODUCT_REVIEW.md)复核当前 `app-first/` 原型。它是一次有边界的只读复审，不是重新评判 47 页的所有状态；文中的判断是我的产品推演，不代称乔布斯本人。

**裁决：八项中六项已自然收敛，一项（订阅）功能补齐但主次仍需调整，一项（配置审阅）已可见差异但影响范围还要翻译成人话。** 主线没有被这轮修复拆散。运行事实、规则实际作用、时段口径和筛选结果都更可信。新问题集中在用户确认“这项变化现在到底意味着什么”及手机首屏的注意力分配；不需要借此推翻整体视觉方向。

## 仍有证据的三个产品问题

### 1. 导入差异能看见，但普通用户未必知道 `/0` 扩大了什么

**动作与事实。** 打开明确样例 `config-review.html?configcase=expanded-scope`，现在能看到一项规则改变、两个涉及应用和旧/新条件：[手机截图](assets/2026-09-29-jobs-review/refinement-config-diff.png)。然而页面只给原始 CIDR 表达和规则旧名“允许局域网发现”，没有说明新条件已覆盖所有 IPv4 目标，而非原来的局域网范围。

**理解代价。** 这比原来的“5→5”有本质进步，但用户若不懂 `0.0.0.0/0`，仍不能在整套替换前判断影响。违反阅读札记 Q6、Q14：差异必须能支持决定，不只证明机器发现了差异。

**有限改法/验收。** 针对此类可确定的条件，先写“目的地址范围从局域网扩大到所有 IPv4 目标；影响 Firefox、Signal 的 UDP 访问”，原条件紧随其后供核对。复杂 `NOT` 或复合规则不要猜整体效果。验收：不了解 CIDR 的用户在确认前能说出这次范围变大到哪里。

### 2. 手机列表详情先展示完整来源台账，实际条目和用途在首屏外

**动作与事实。** Android `393×852` 打开正常的 `domain-detail.html?id=d1`，标题后几乎整个首屏是“来源与更新”的地址、版本、检查时间、频率、采用方式和三个维护动作；“匹配条目”与“使用这个列表的规则”要滚动后才出现。[正常状态首屏](assets/2026-09-29-jobs-review/refinement-domain-firstscreen.png)。失败态也是相同读序。820 平板和 1440 Linux 能并排看使用规则，因此这是手机主次问题。

**理解代价。** 新增的订阅生命周期本身必要，但用户从列表入口来核对“有哪些目标、影响哪些应用”时，先被完整的来源管理面板占据。页面顶部只有应用名概括，看不见具体目标与控制。违反阅读札记 Q2、Q5、Q11。

**有限改法/验收。** 首屏保留订阅状态、上次结果和最重要的更新动作；将地址、频率、采用偏好收进现有“管理来源”，或折叠成可展开的次级摘要。失败提示仍需醒目。验收：393px 正常状态下，不滚动就能看到至少首条匹配目标与一个使用它的规则，同时知道订阅是否健康。

### 3. “自动采用”对已经待审的版本何时生效不明确

**动作与事实。** 先进入 `domain-detail.html?id=d1&subscription=update`，看到新版本待审；点“管理来源”，把“发现新版本时”设为“自动采用更新”并保存。回详情仍使用旧的 `2026.09.29.1`，一处文字说“新版本可用，先核对条目变化再决定是否采用”，同卡另一处却说“发现新版本：自动采用”。[保存偏好后的页面](assets/2026-09-29-jobs-review/refinement-auto-pending.png)。手动审阅并点“使用这个版本”后，新版条目出现，但本次观察的反馈只说“新版本已保存，是否正在使用见下方配置状态”，页面下方没有同名的配置状态区。

**理解代价。** 自动采用是否处理眼前的候选，用户只能猜；采用后又要猜已保存是否等于已生效。这直接影响订阅可能改变的拦截结果。违反阅读札记 Q2、Q6、Q8。

**有限改法/验收。** 保存偏好时明确“仅适用于下次检查；当前待审版本仍须手动采用”，或提供“同时采用当前版本”的选择。采用后的详情就地显示保存的资料版本、正在使用的资料/配置版本及查看入口；未生效时给处理动作。验收：用户改完偏好或采用候选后，能立即回答当前使用哪版、眼前候选是否还需自己处理。

## 本轮实际范围

使用独立的 `jobs-refinement-*` scope，在 Android 393 上实走配置样例、六种运行→恢复、观察规则与 Firefox 设置、订阅失败重试/更新审阅与采用/本地补充和排除/自动采用偏好、选时段、独立筛选往返、导入成功与故意断引用。目视 Android 820 首页及域名详情，Linux 1440 规则和域名详情，Linux 640 配置审阅与订阅来源。未重跑 47 页全状态、真实 URL 拉取、设备权限或后端控制；这些不是本次结论的依据。

本轮建议只收拢上述三处的**用户可理解性**，保留已经补齐的状态模型、差异结构、订阅能力和主线视觉系统；无需另开一轮全面重构。

## 本次复审之后的落实记录（主代理）

用户已授权执行首轮八项修整。以下记录是主代理在这次独立复审后完成的实现与验证，不代表子代理又做了一轮评审。

- 地址差异增加“目的地址条件扩大到所有 IPv4”的说明，保留原条件；NOT、OR、多项条件同时变化不推断整体影响。
- 手机来源区收为状态摘要，完整检查安排可展开；前置一条使用规则，首条目标在首屏内。条目行直接标出本地例外或完全排除。
- 已有候选时改为自动采用，会明确提示并以“保存并采用待更新版本”执行；采用后直接显示正在使用的资料/配置，未生效时继续指出旧资料及处理入口。已停止订阅的编辑不会重新启用。
