# VPP shared-memory options for observability export

Date: 2026-09-23. Status: primary-source research and static inspection only; no implementation, build, benchmark, or device qualification. This report evaluates per-worker VPP C producers and one logical Rust consumer on Android ARM64, minSdk 31, and Linux. Normal and debug are proposed independent bounded channels; a worker may drop on exhaustion and must never wait for the consumer or delivery acknowledgement.

## Recommendation

**Shortlist `svm_msg_q` conditionally if shared memory is justified.** Its bounded record slots, size classes, indexed descriptors, and single-consumer API fit this use case better than the other VPP facilities examined. Reuse would mean a small C facade over the pinned, Android-patched `libsvm`, with explicit nonblocking admission and notification, per-worker/channel ownership, and fresh-generation teardown. It would not mean exposing VPP structs directly as a Rust wire contract. Two static source defects and the default blocking eventfd helper below prevent recommending blind adoption of the convenience APIs.

**Keep `svm_fifo` as a secondary candidate for a genuine variable-length byte-stream requirement.** It supports whole-record publication using an appropriate API, but brings byte framing, chunk allocation/recycling, segment management, and separately implemented wakeup integration. Those costs are difficult to justify for a few bounded record classes.

**Do not select memif solely to export these observations.** `libmemif` is the strongest standalone external-consumer library here: it supplies shared-memory setup, descriptor exchange, queue ownership, notifications, and reconnect-related machinery without linking the consumer to VPP infrastructure. However, memif is a packet-interface transport. Its control protocol, two-direction queue topology, packet-buffer conventions, and VPP device integration are extra mechanisms for this small lossy record-export requirement. Reconsider it if interoperability with an existing memif endpoint becomes a real requirement.

These are relative recommendations within the VPP options. They do not establish a performance win over the dependency-free `SOCK_SEQPACKET` comparator investigated in the [mobile baseline](2026-09-23_OBSERVABILITY_IPC_MOBILE_BASELINE.md). No throughput, latency, energy, or memory superiority is claimed.

## Comparison

| Property | `svm_fifo` | `svm_msg_q` | `libmemif` / stock VPP memif |
| --- | --- | --- | --- |
| Native unit | Byte stream in chunks | 8-byte ring/element descriptor plus fixed-size slot | Packet/buffer descriptors with length and optional chaining |
| Variable record sizes | Product supplies framing; whole record can be published together | Choose configured slot size class; product carries actual payload length | Per-buffer length; chains for larger packets; product supplies observation schema |
| Concurrency | SPSC per FIFO | Single-consumer API; producers serialized when using locking API | One thread per queue; socket/control handling also has ownership rules |
| Exhaustion | Immediate error, or partial write with ordinary enqueue | Immediate busy/full rejection with the appropriate combined nonblocking API | Immediate allocation shortage with completed-prefix count; stock VPP TX retries a bounded number of times then drops |
| Wakeup | Event flags only; caller supplies delivery and wait protocol | Empty-to-nonempty notification plus full-to-not-full notifications; eventfd or pthread mode | Interrupt eventfd or polling; interrupt-mode TX signals each burst |
| Rust dependency burden | `libsvm` + `vppinfra` through a C facade | `libsvm` + `vppinfra` through a C facade | Small standalone C library and FFI; no `vppinfra` dependency in libmemif |
| Address requirement at this pin | Current FIFO MEMFD segment path permits different mapping addresses | Shared slots use indexes; local wrapper rebuilt on attach | Region index + offset; each process maps at its own address |
| Android evidence | Project has an Android-patched SVM build path; this new use unqualified | Same, including removal of robust-mutex assumptions | ARM64 branches exist; reviewed upstream docs/build do not establish Android support |

The following sections give the source evidence and qualifications behind each row.

## `svm_fifo`: usable SPSC machinery, substantial surrounding runtime

The implementation explicitly assumes one producer and one consumer. Each side owns its index and acquires the other side's index; enqueue publishes the tail with release ordering. Map one FIFO to one VPP worker and one logical Rust reader. Multiple workers writing one FIFO violate that model unless another serialization layer is introduced. [Ownership and loads](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/svm_fifo.h#L74-L117), [enqueue](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/svm_fifo.c#L832-L883)

The ordinary `svm_fifo_enqueue` shortens a request to available space. A length prefix followed by a separate enqueue is therefore not sufficient to guarantee an indivisible observation. `svm_fifo_enqueue_segments(..., allow_partial=0)` first checks total capacity, copies its segments, and publishes the final tail once. A product header and bounded body can use that operation, without enabling out-of-order TCP-style features. `svm_fifo_segments` can expose borrowed chunks to a consumer, followed by `svm_fifo_dequeue_drop`; Rust must finish or copy the record before releasing that storage. These are byte-buffer operations, not record-schema or delivery guarantees. [Whole/partial enqueue](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/svm_fifo.c#L957-L1044), [borrowed-chunk contract](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/svm_fifo.h#L411-L428)

Full capacity produces `SVM_FIFO_EFULL`; needing an unavailable chunk can produce `SVM_FIFO_EGROW`. Enqueue may invoke `f_try_chunk_alloc`, and dequeue returns traversed chunks to the segment allocator. `svm_fifo_fill_chunk_list` can provision capacity, but its existence alone does not establish an allocator-free steady-state path: the implementation keeps moving through and recycling chunks. A reuse qualification must bound and inspect that path, reserve all intended capacity before ingress, and distinguish a full FIFO from segment-allocation failure. [Chunk allocation](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/svm_fifo.c#L794-L829), [dequeue/recycling](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/svm_fifo.c#L1091-L1130), [provisioning](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/svm_fifo.c#L1214-L1228)

An important correction to older SVM descriptions: **current FIFO MEMFD segments do not require identical process virtual addresses.** Shared chunk links are offsets from the segment header; the private `svm_fifo_t` contains process-local pointers and lookup state. `fifo_segment_init` clears `ssvm_va`, and the MEMFD client adds `MAP_FIXED` only when that field is nonzero. The legacy named-SHM SSVM client follows a different fixed-address path. This is a qualified claim about the current FIFO/MEMFD path, not every VPP shared-memory subsystem. [Shared/private layouts and offset conversion](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/fifo_types.h#L72-L168), [offset helpers](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/fifo_types.h#L199-L221), [relocatable FIFO segment setup](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/fifo_segment.c#L285-L409), [MEMFD mapping](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/ssvm.c#L284-L340)

A FIFO's `has_event` and dequeue-notification fields are flags, not an eventfd transport. The exporter still needs a complete publish/notify/drain/recheck/sleep protocol or an explicit polling policy. A large packet-throughput claim cannot establish low idle battery cost. [FIFO event operations](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/svm_fifo.h#L679-L716)

**Additional static finding, untested:** the standalone `svm_fifo_alloc` convenience function allocates and zeroes `svm_fifo_t`, then dereferences `f->shr` without assigning it in that function. The visible path is lines 417–423 followed by 438–439. This is a source-level null-dereference concern, not a reproduced product failure. Do not propose that helper as a proven standalone allocator. The current segment allocation/attachment route is a separate API, and this observation does not establish that route is broken. [Exact helper](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/svm_fifo.c#L411-L441)

## `svm_msg_q`: closest record fit, choose the API deliberately

One shared descriptor queue references one or more data rings. Each data ring has a configured element size and count. `svm_msg_q_alloc_msg(nbytes)` chooses the first non-full ring large enough for the request; it does not create an arbitrary-sized allocation. There is no actual message-length field in the queue descriptor, so a versioned observation header must carry length/type. Larger size classes can reduce slot waste, but their reserved memory and maximum accepted record size remain explicit product choices. Shared memory is roughly descriptor count × 8 plus the sum of slot count × slot size, with queue/ring headers and process-private wrappers added. [Structures](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.h#L19-L94), [size calculation](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L93-L116), [size-class allocation](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L253-L272)

`svm_msg_q_attach` reconstructs process-private pointers from the local shared base, and descriptors hold ring and slot indexes. Identical virtual addresses are unnecessary for the queue object. Its shared header does contain `pthread_mutex_t` and `pthread_cond_t`, and the ABI also depends on native layout: offset addressing does not make it a portable cross-libc/cross-version wire format. Prefer a C facade built against the same target VPP headers and libc on each side, rather than reimplementing those internals with Rust structs. The installed SVM target links `vppinfra`, `rt`, and `pthread` upstream; Android alters that link set as described below. [Attach](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L133-L157), [library dependencies](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/CMakeLists.txt#L17-L41)

The consumer functions explicitly require a single consumer. It dequeues a descriptor, processes/copies data, then calls `svm_msg_q_free_msg`; freeing out of ring order asserts. Receiving a descriptor does not immediately release its data slot. Eventfd mode uses a process-private producer spinlock, while non-eventfd mode uses the shared pthread mutex. Thus multiple producer threads must share the same local wrapper/lock; this is not a general multiple-producer-process queue. One queue per worker/channel fits the intended topology and avoids cross-worker lock contention. [Consumer contracts](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.h#L217-L260), [release order](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L281-L308), [lock selection](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.h#L359-L406)

For bounded admission, the relevant API is `svm_msg_q_lock_and_alloc_msg_w_ring(..., noblock=1)`: busy returns `-1`; queue/ring full unlocks and returns `-2`; successful allocation keeps the lock until publication via `svm_msg_q_add_and_unlock`. A wrapper must validate the chosen class and all record sizes before reserving a slot, then complete publication without fallible downstream processing. A drop should update the producer's counter and return. There is no worker wait or reliable-delivery ACK required for that shape. [Combined admission](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L228-L250), [publication](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L381-L387)

**Static finding, untested:** `svm_msg_q_add(..., nowait=1)` acquires its trylock at line 358, checks full at 366, returns `-2` at 369, and only unlocks at 376 on the other path. A full descriptor queue after successful locking therefore skips the visible unlock. No reproducer or upstream bug status was investigated. This exact convenience path is unsuitable as the unexamined foundation for the overload contract. The combined API above explicitly unlocks on its full path at 238 and avoids separately reserving a data slot before discovering descriptor exhaustion. [Exact control flow](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L350-L378)

Notifications occur when adding to an empty descriptor queue, and also when a consumer frees a formerly full descriptor queue or data ring. The notification helper writes an eventfd; `svm_msg_q_alloc_eventfd` creates it with `eventfd(0, 0)`, so it does not itself establish a nonblocking worker write. A candidate must supply an explicitly nonblocking fd, use only nonblocking producer APIs, integrate the Rust wait loop, and qualify write errors and shutdown. Eventfd mode has no per-record wake syscall while the queue stays nonempty, but consumer-side full-transition signals still exist. It is not legitimate to infer a complete phone sleep/wakeup proof from the presence of an eventfd. [Signal helper](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L176-L208), [enqueue/dequeue transitions](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L333-L347), [eventfd creation and blocking helpers](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L472-L585)

Do not represent normal and debug as merely two data rings in one message queue: they would still contend for its shared descriptor capacity and producer lock. Independent queue objects and reserved capacities preserve the proposed separation. Size classes belong within a channel, not in place of channel isolation. This is an architectural inference from the shared descriptor queue and per-ring capacity layout.

## Memif and libmemif: complete transport, packet-oriented scope

The pinned standalone `libmemif` library consists of `main.c` and `socket.c` with C headers and the platform thread library; it does not link VPP infrastructure or DPDK. Its public APIs are suitable for an opaque C FFI facade. The top-level build is less minimal: it unconditionally includes examples/tests, declares an external Unity checkout, parses `/etc/os-release`, and performs Linux package/version work. ARM64 has explicit cache-line selection, but the reviewed build instructions are Linux `apt`/CMake instructions. An Android library-only build integration still needs work and verification. [Library target](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/CMakeLists.txt#L16-L37), [top-level build](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/CMakeLists.txt), [official build instructions at the pin](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/docs/buildinstructions_doc.rst)

The protocol exchanges region and ring file descriptors over a Unix-domain control connection. Descriptors contain region index, offset, length, and a next flag; local mapping uses `mmap(NULL, ..., MAP_SHARED, ...)`, so peers need not use the same address. Default region creation uses `memfd_create(MFD_ALLOW_SEALING)`, shrink sealing, `ftruncate`, and ordinary shared mappings. Huge pages are not required by that libmemif path. [Descriptor layout](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/memif.h#L145-L176), [region creation](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/main.c#L1204-L1253), [FD passing](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/socket.c#L40-L78)

Variable-length data is supported within packet buffers and through chaining. The allocation API's requested size is `uint16_t`; a record envelope must stay within its selected bound or define its own splitting, rather than assuming an unlimited record API. When a chain cannot fit, allocation rolls back that chain and returns `MEMIF_ERR_NOBUF_RING`, potentially after allocating earlier requested packets. Callers must honor the returned count. RX borrows shared buffers; `memif_refill_queue` releases them for peer reuse. That is buffer reclamation, not evidence of durable delivery or a reason for a VPP worker to wait. [API size/chaining](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/libmemif.h#L596-L614), [allocation/rollback](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/main.c#L1530-L1648), [official ownership examples](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/docs/gettingstarted_doc.rst#L93-L164)

Official threading guidance says a queue must not be handled in parallel; threads can own distinct queues. Socket establishment/polling has separate restrictions. One Rust reader can service several worker queues, but control disconnect and shared-memory unmapping must be coordinated with all producer owners. Linking libmemif inside a custom VPP exporter would require that lifecycle integration. Using the stock VPP memif device instead uses packet graph buffers and interface setup: its TX path optionally takes a shared-queue spinlock, performs bounded retries, counts unsent buffers, and frees/drops them. It is not a generic observation enqueue call. [Threading guidance](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/docs/gettingstarted_doc.rst#L209-L227), [VPP TX retries](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/plugins/memif/device.c#L110-L143), [VPP TX ownership and drops](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/plugins/memif/device.c#L659-L730)

Libmemif has nonblocking queue eventfds and either interrupt or polling mode. In interrupt mode `memif_tx_burst` writes the eventfd after each nonempty burst, rather than only the empty-to-nonempty transition. Its built-in polling uses `epoll_pwait`, and custom fd-loop integration is documented. A phone deployment should qualify interrupt/batched consumption, not inherit a permanently busy packet-polling example. The control protocol has ACK messages for connection setup; data buffer reclamation is distinct from those control ACKs. [Queue eventfds](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/main.c#L1303-L1348), [burst notification](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/main.c#L1705-L1805), [custom event loop](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/docs/gettingstarted_doc.rst#L196-L207), [control message types](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/memif.h#L36-L47)

## Android: existing project adaptation is not upstream support

Bionic's official status lists `shm_open`/`shm_unlink` and robust mutexes as missing. Its `memfd_create` wrapper was added for API 30, below this project's minSdk 31. This establishes availability of relevant primitives, not successful use by every target process/kernel/SELinux combination. The [mobile baseline](2026-09-23_OBSERVABILITY_IPC_MOBILE_BASELINE.md) covers the broader public-API, process-policy, and wakeup constraints. [Bionic status at a fixed commit](https://android.googlesource.com/platform/bionic/+/8e631624e9da603e023abe049820eaa830d02815/docs/status.md), [API-30 memfd addition](https://android.googlesource.com/platform/bionic/+/3d24d2b0883ea828443fd7c36d1b262410618aca)

Existing product patches materially change SVM's portability and recovery behavior:

- [0006 shared-queue patch](../../src/product/vpp/android/patches/0006-svm-android-shared-queue-no-robust.patch), lines 26–51, retains process-shared mutex/condition-variable setup, removes robust initialization for Android, and makes setup failures fatal. Lines 173–190 remove `EOWNERDEAD`/`pthread_mutex_consistent` handling from Android message-queue locking. Ordinary process-shared mutexes do not gain robust owner-death recovery from this change. A participant dying while holding one can leave it unusable; the architecture must discard that runtime generation instead of promising repair in place. Eventfd mode's private producer lock is a different path, but initialization still compiles/initializes the shared pthread fields.
- [0007 SVM backend patch](../../src/product/vpp/android/patches/0007-svm-android-file-backend.patch), lines 7–30, removes separate `rt`/`pthread` linkage on Android. Lines 34–66 disable the legacy named-SHM SSVM backend. The old SVM region code uses generation-private regular files at lines 191–202 and refuses existing-region reuse at 245–247. This is not a general upstream `shm_open` implementation, and it should not be conflated with the FIFO MEMFD backend.
- The [Android stage](../../src/product/vpp/android/build-stage.sh) explicitly includes `libsvm.so` in its artifact list at line 248. That reduces the cost of reusing the library on the VPP side, but does not prove this new Rust-facing consumer, mapping, queue, or wakeup path works. The reviewed Android profile's changed-file list contains no libmemif adaptation. [Profile source](../../src/product/vpp/android/apply-profile.sh)

For libmemif, ARM64 support is visible in its architecture/cache-line choice and syscall fallback, and the non-x86 barrier uses `__sync_synchronize`. Its reviewed runtime uses Linux Unix sockets, FD passing, memfd/sealing, eventfd, timerfd, epoll, and shared mappings rather than POSIX named SHM or robust mutexes. **Source-based inference:** a phone port is plausible and avoids those two Bionic blockers. **Not established:** an upstream Android support promise, an Android library-only build, actual app/root process access policy, ARM64 memory-order qualification of the complete integration, idle power, 16 KiB-page packaging, reconnect races, or crash cleanup. Both peers must also agree on the shared ring layout/cache-line build configuration. [ARM64 build choice](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/CMakeLists.txt#L63-L85), [barrier](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/main.c#L61-L66), [syscall fallback](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/memif_private.h#L262-L280)

## Reuse cost and decision gates

All three reviewed facilities are Apache-2.0 at the pinned source, with copyright notices to retain. `svm_fifo` also names its historical ring inspirations in the header. They are C facilities; no C++ compatibility layer is needed or proposed. [SVM FIFO notice](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/svm_fifo.h#L1-L9), [message queue notice](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/src/svm/message_queue.c#L1-L4), [libmemif notice](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/extras/libmemif/src/main.c#L1-L16), [upstream license](https://github.com/FDio/vpp/blob/9258530f3804a152578ce11cc7c8a1e9eab88ed0/LICENSE)

Before selecting conditional `svm_msg_q` reuse, the unresolved work is concrete:

1. Fix the observation schema, maximum lengths, and independent normal/debug capacities; reserve one producer-owned queue per worker/channel. A single Rust task can drain all queues in bounded fair batches without changing the SPSC ownership model.
2. Choose the supported C entry points and check the applicable static finding against the exact artifact. Verify all capacity failures are immediate and counters do not themselves require exporting a record.
3. Freeze target ABI/build configuration behind the C facade; set up mappings/fd transfer once and avoid sharing product pointers or live VPP packet ownership with Rust.
4. Prove and test publication/reclamation ordering and the complete nonblocking notify/drain/sleep protocol on ARM64, including full queues, consumer pauses/death, producer teardown, and new generations. No in-place mutex recovery or reliable replay is part of this proposed lossy channel.
5. Compare the actual bounded workload against `SOCK_SEQPACKET` for phone CPU, memory, idle wakeups, and energy before accepting the extra shared-memory lifecycle. No benchmark threshold or queue capacity is selected by this research.

The static defects are reasons to qualify the exact reuse path, not evidence that the project's current packet domain or VAPI control path has failed. The conclusion is a narrow shortlist, with `svm_msg_q` the first VPP-native record candidate and memif reserved for a future packet-interoperability need.
